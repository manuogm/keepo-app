# Keepo v1 — Remaining Build Roadmap (Phases 5–20)

## Context

Phases 1–4 shipped a working vertical slice: schema for `currencies`/`profiles`/`accounts`/`balance_snapshots`/`categories`/`transactions`/`sync_conflicts`/`fx_rates`, the ledger/valuation balance views, versioned transaction-edit RPCs with conflict-as-data, FX conversion end to end, and a 3-tab SwiftUI app (Accounts | Transactions | Categories) on a `StubAuthProvider`.

Roughly 70% of `keepo-v1-feature-spec.md` is unbuilt: Home/net worth, Sync Ritual, Needs Review, households, recurring, Insights, budgets, FI, CSV import/export, Apple Pay capture, the offline outbox, ops/monitoring, and the security layer. There is also **no account-creation UI beyond onboarding** (flagged as blocking in two phase logs) and **no re-runnable SQL test suite** — the ~23 invariants from Phases 1–4 exist only as prose.

Goal: build every feature listed in the spec, in an order where each phase's foundations are correct before the next is built on them, verified by a suite that survives.

### Decisions taken (confirmed with the user)

- **Households split in two.** Access model + viewer-scoped money early (Phase 7); invites/leave/fork/APNs late (Phase 19).
- **`project.yml` stays at iOS 18.0**; verification runs on the installed iOS 26.5 simulator only. Accepted risk: an iOS-18-only bug surfaces at TestFlight.
- **`app-architecture.md` is authoritative.** Where it contradicts `keepo-v1-feature-spec.md` or CLAUDE.md's non-negotiable money rules, the phase **amends the doc first** (inline, matching its existing defect-history style) and then implements the corrected design. Three known cases are listed under "Doc amendments" below.
- **Hosted Supabase proven from Phase 5, not Phase 17.** `PasswordAuthProvider` (hosted-capable; `StubAuthProvider` has `precondition(config.isLocal)` and has never run against anything but the local stack) plus `supabase link` + `supabase db push` of the four existing migrations land in Phase 5. Every later phase's migration gets pushed to hosted as part of its own exit gate, not deferred to one big push at the end.
- **Apple Developer membership assumed not to arrive until after Phase 20.** Phase 19's two-device household test runs on free-personal-team provisioning (7-day profiles, built and installed from the Mac onto both phones — no TestFlight). Phase 20 stays the separate SIWA + APNs + TestFlight pass, unchanged in scope; revisit only if the membership actually arrives earlier.
- **Cadence — four human review stops, agreed with the user:**
  1. **After Phase 5** — before any feature work, confirm Phases 1–4 hold under the new pgTAP suite and that hosted actually works.
  2. **After Phase 8** (not 7) — Phase 7 (households backend) is a **machine gate only**: proceed to 8 solely if its pgTAP suite is green, stop and report if not. There's little to visually review at the end of 7 (single-member households, a toggle); Phase 8 is where a broken access model becomes *visible* — a wrong or missing number on the Home hero metric — which is what a human review is actually good at catching.
  3. **After Phase 11** — end of the offline-outbox/file-protection work, before capture depends on it.
  4. **After Phase 19** — household lifecycle complete on two physical devices (free-team provisioning); app fully functional except SIWA/APNs/TestFlight.
  Every other phase boundary still runs its full automated exit gate (pgTAP, xcodebuild, swiftlint, simulator walkthrough, version log) — it's just not a stop for human review.

## Hazards this ordering exists to avoid

These were found during exploration and are the reason the phase order is what it is. Each is closed in a named phase.

| # | Hazard | Closed in |

Both views are `security_invoker`, and `profiles_select` is `id = auth.uid()` — so under households a shared account owned by the *other* member has no visible `profiles` row and the inner join **silently drops the row entirely**. Not a wrong rate: a missing account, no error. | 7 |

| H5 | `net_worth(scope)` is `'me' \| 'household' \| 'total'` by spec — uncomputable before households exist. | 7 |

| H14 | The adjustment category can't be a second `is_default` row (partial unique index on `(owner_id, kind) where is_default`). | 9 |
| H15 | `fx_convert` has no same-currency short-circuit — a 365-point single-currency trajectory needs a resolvable rate row on every date or renders `—`. | 8 |

## Phase 5 — Re-runnable SQL test harness & seed fixtures

**Goal:** turn Phases 1–4's prose invariants into a committed suite that runs in one command — *before* households changes what they mean. A harness written inside Phase 7 can't distinguish "households broke this" from "this was never true."

- `supabase/tests/`, pgTAP via `supabase test db --local`. `create extension if not exists pgtap` goes **inside the test transaction**, never a migration — pgTAP must not reach the hosted project.
- Files: `_helpers.sql` (two fixture users, `as_user(uuid)`, `as_anon()`), `01_grants_rls.sql`, `02_accounts_balances.sql`, `03_transactions_integrity.sql`, `04_transaction_editing.sql`, `05_fx.sql`. Target ≥ the 23 documented invariants.
- **Schema-wide assertions pay compound interest** — they auto-cover every table added in Phases 6–20: zero grants to `anon` anywhere in `public` (`information_schema.role_table_grants`), `relrowsecurity` true on every table, zero `DELETE` policies (`pg_policies`), every `prosecdef` function carrying `search_path=` in `proconfig`.
- `supabase/seed.sql` — `config.toml` already points at a file that doesn't exist. Two users, EUR + USD + investment accounts, sample transactions, a few `fx_rates`. Immediately relieves the "every account after the first needs direct SQL" pain.
- Migration: closes **H12** — `unique (id, owner_id)` on `categories`, and the category-owner check added to `set_transaction_derived_columns()` (the trigger is where the household-aware version lands anyway, so no churn later).
- **Harness gotchas to encode as comments in `_helpers.sql`:** the file owns `begin … rollback`, so `DEFERRABLE INITIALLY DEFERRED` triggers (`transactions_check_transfer_integrity`) never fire — testing the 0-or-2-legs rule needs `SET CONSTRAINTS ALL IMMEDIATE`. `select * from f()`, never `select (f()).*` (Phase 3 lesson). `reset role` before switching fixture user. `auth.uid()` reads `request.jwt.claim.sub`, so `set_config(...) + set local role authenticated` suffices — no JWT minting.
- **Hosted, proven now, not deferred to Phase 17:** `KeepoCore/PasswordAuthProvider.swift` — email+password against whatever `SupabaseConfig` it's given, no `isLocal` precondition; `SessionStore` picks stub vs. password provider off a build flag/xcconfig var, defaulting to stub for local dev. `supabase link --project-ref <ref>` (real hosted project the user creates) + `supabase db push` of all four existing migrations. `supabase gen types swift --local --lang swift --swift-access-control public` re-run and diffed against hosted's generated types to confirm they match. Debug/Release `.xcconfig` gains a hosted URL/anon-key pair alongside the local one (still gitignored).
- **Verify:** `supabase db reset` then `supabase test db --local` green, locally. Separately: push to hosted, sign up + sign in with `PasswordAuthProvider` against the hosted URL from the simulator, confirm onboarding and one account/transaction round-trip through RLS with a real (non-local) JWT.

## Phase 6 — Account lifecycle & shared client data layer

**Goal:** accounts are fully manageable from the app, and every screen refreshes correctly.

- **Migration:** `revoke update on accounts from authenticated` (**H4**), then DEFINER RPCs `update_account`, `archive_account`, `delete_account` (refuses when non-deleted transactions exist), each returning `(conflict boolean, …)` as data per Phase 3's convention, each with `default null` on every parameter a Swift `Optional` can omit (the `PGRST202` lesson). Editable: `name`, `subtype`, `include_in_total`, `counts_toward_fi`, `opening_balance`. Not editable: `currency` (composite FKs lock it), `kind` (changes the balance formula). Append `version` to `accounts_with_balances`.
- **Client:** `AccountFormView` (create/edit, mirroring `TransactionFormView`'s `Mode` enum), archive/unarchive, "Everyday"/"Investments" sections with subtotals, extracted `AccountRowView`.
- **KeepoCore (H8):** `DateFormatting.swift` — one Postgres timestamp/date codec replacing all 8 ad-hoc `ISO8601DateFormatter()` sites (`Repositories.swift` ×7, `TransactionFormView.swift:198`). `AmountFormatter.editableString(_:minorUnit:locale:)` as `AmountParser`'s missing inverse, fixing `TransactionFormView.swift:210,224`. Unit-tested.
- **App (H7):** `RefreshCoordinator` + a per-screen-family `DataStore` with `load(force:)`; `.refreshable` on every list; screens key off `.task(id: coordinator.token)` so a write anywhere invalidates everywhere. **This is the seam Phase 11 plugs offline persistence into** — no protocol, no speculative abstraction; `persist`/`restore` are added to the same type once a second behaviour genuinely exists.
- **Verify:** new pgTAP (raw `UPDATE accounts` from `authenticated` denied; stale version → `conflict` + exactly one `sync_conflicts` row + no data change; delete refused with transactions present). Simulator: create three accounts incl. USD + investment, edit, archive, confirm subtotals and cross-tab refresh.

## Phase 7 — Households: access model & viewer-scoped money ⚠️ largest phase

**Goal:** the access model, the viewer's-base-currency rule, and `net_worth(scope)` are correct before anything is built on them.

- **New:** `account_scope` enum; `households`, `household_members` (2-member cap trigger), `household_accounts`, `household_invites` (table only — no RPCs yet, same precedent as `sync_conflicts` in Phase 3). DEFINER `my_household_id()` so `household_members`' own policy can't recurse (Phase 1 lesson, applied pre-emptively). `can_read_account` gains `OR EXISTS (household_accounts JOIN household_members …)`.
- **Retrofits — the phase's real weight:**
  - `accounts_select`/`accounts_insert`/`accounts_update` edited directly (**H3**).
  - The six hardcoded ownership checks re-pointed at `can_write_account` (**H2**).
  - `check_transfer_integrity`'s `count(distinct owner_id) = 1` relaxed to "one owner, or all legs' accounts within one household" (**H10**). `transactions.owner_id` stays the account owner (the composite FK forces it); `created_by` records who entered it, per spec.
  - Both `profiles` joins rewritten to `left join profiles p on p.id = (select auth.uid())` (**H1/H9**). `left`, not inner — a pre-onboarding null `base_currency` must still not drop rows, which Phase 4 explicitly tested for.
  - `set_transaction_derived_columns()`'s category-owner check made household-aware.
- **RPCs:** `create_household()`, `share_account()`, `unshare_account()` (deletes one `household_accounts` row — no copying, ownership never moved, so this is *not* a fork), `net_worth(p_scope account_scope)` — `total` = `me + household` summed from `account_balances_base` under two `WHERE` clauses, never subtraction (**H5**).
- **Client:** new Settings tab with a Household section (create household, per-account share/unshare, member list); shared/private indicator on `AccountRowView`; `created_by` on transaction detail. Plus a **Debug-only dev-identity switcher** in `StubAuthProvider` (env var or launch arg, two fixed emails) — it currently hardcodes one email, so the app can never have two users; ~15 lines that unblock manual household, realtime, and conflict testing for four later phases.
- **Verify:** ~25 pgTAP assertions with two fixture users — private account invisible to the other member (the `SELECT` returns nothing, not filtered in UI); shared readable *and* writable by both; **shared rows still present in `accounts_with_balances`/`transactions_with_details`** (the H9 regression test); two members with different base currencies see the same shared account with different `balance_base`; cross-owner transfer succeeds within a household, rejected across households; `net_worth('total') = net_worth('me') + net_worth('household')`; 2-member cap; no `anon` grants on the four new tables.
- **Split seam if this runs long:** 7a = migration + pgTAP only, zero Swift; 7b = Settings/Household UI + dev switcher. The migration must be green before any client code either way.
- **Known limitation, by design:** the running app has single-member households until Phase 19 (`accept_invite` is what admits a second member). Two-member behaviour is verified by pgTAP, which is better and re-runnable.
- **This phase's exit gate is a machine gate, not a review stop.** Proceed to Phase 8 only if the full pgTAP suite (including the ~25 new assertions) is green against both local and hosted. If anything is red, stop here and report rather than pushing into Phase 8 — but the human review itself happens at the end of Phase 8, where a broken access model is visible as a wrong number rather than a failing assertion.

- **Client:** Sync Ritual screen, per-account enter-balance flow, always-visible one-tap unlogged adjustment, `StalenessBadge`, the factual staleness banner above Home's net worth.

## Phase 10 — Needs Review inbox & transaction filters

- **Migration:** `needs_review` view with a **stable column contract** (`kind`, `item_id`, `account_id`, `occurred_at`, `title`, `subtitle`, `amount`, `currency`) so Phases 12/14/18/19 each append a `UNION ALL` branch without ever changing the client decoder. Initial branches: `sync_conflicts WHERE resolved_at IS NULL`, reconciliation gaps. `resolve_sync_conflict(p_id)`. Index `sync_conflicts (owner_id, resolved_at)` — currently only a PK exists.
- **Client:** `NeedsReviewRow` (one renderer switching on `kind`), inbox screen, tab badge; transaction filters (account/category/kind/date range/search) riding the existing `(owner_id, occurred_at desc, id desc)` keyset index.
- **Delivered (Phase 10 complete):** Needs Review IS a 6th tab with a badge, per this section's own literal wording — unlike Household/Sync Ritual (Phases 7/9), which were deliberately reached via Settings/Home instead. `needs_review`'s two branches: unresolved `sync_conflicts` (account_id resolved through the polymorphic table_name/row_id pair) and `reconciliation_gap` (every non-archived stale account, not gated by include_in_total — broader than Home's banner on purpose). No pagination UI was built for the transaction filters — "riding the keyset index" was read as an ordering constraint, not a mandate for infinite scroll. See version-logs/phase-10-log.md.
- **Required follow-up, found during Phase 11's live review-stop walkthrough (user-confirmed, not deferred as optional):** `sync_conflicts` only stores the two version *numbers* (`client_version`/`server_version`), never the actual field values the rejected write attempted. Resolving a conflict from Needs Review today means swiping it away with **zero information about what the conflict actually was** — not even a "your version vs. the current one" comparison, since the attempted payload was discarded the instant the version check failed. This needs a real fix, not a UI tweak: `sync_conflicts` needs a new column (e.g. `attempted_payload jsonb`) capturing the rejected write's fields at the moment of conflict, and every versioned write RPC that can produce a conflict (`update_transaction`, `update_transfer`, `update_account`, `archive_account` — anything using the conflict-as-data pattern) needs to populate it instead of just logging the two version integers. `needs_review`'s `sync_conflict` branch and `NeedsReviewRow` then need to actually render a diff (attempted value vs. current saved value) before the user resolves, and tapping a `sync_conflict` row should navigate to see it, not just swipe-to-dismiss blindly. Whichever phase next touches Needs Review or the conflict-as-data RPCs should treat this as required work, not a nice-to-have — the current behavior lets a user discard a real conflict with no way to know what it was.

## Phase 11 — Local data protection & offline outbox

**Goal:** offline writes, encrypted at rest, replayed safely. **Client-only phase.**

- **Rejected: a full local-first mirror.** Answering balance reads locally means reimplementing `account_balances`' two-kind CASE and `fx_convert` in Swift — a direct violation of money rule 3 ("all money arithmetic in SQL, never Swift") and the one-place principle.
  - **Superseded 2026-08-12 — see `keepo-local-first-plan.md`.** This rejection assumed the only local option was Swift. It was reversed once the user made offline analytics a core requirement, because a *different* local option exists: integer money plus SQLite on-device, which lets the same SQL be ported rather than rewritten. Rule 3 ends up narrowed, not waived. The reasoning above remains correct for the SwiftData-plus-`Decimal` approach it was actually judging.
- **Built instead:** write-outbox + read-through **payload** cache. The cache stores the *server-computed* decoded rows per query key (`accounts_with_balances`, a page of `transactions_with_details`, the Home summary), written on every successful fetch, replayed cold-start and offline with an "as of HH:mm" marker. Zero arithmetic in Swift — it re-displays numbers Postgres computed. This is the minimum that honors "on-device cache + offline write queue, unsynced writes flagged."
- SwiftData store with `VersionedSchema` + `SchemaMigrationPlan` (the spec's "local cache carries its own schema version and migration path"). `NSFileProtectionCompleteUnlessOpen` on the store file **and** its `-wal`/`-shm` siblings.
- `OutboxItem(id, kind, payloadJSON, expectedVersion, createdAt, attempts, lastError)`, FIFO per row id, keyed by the client-generated UUID that already exists — so a retry is idempotent for free. **Whole-row payloads, never per-field merge.** Drain calls the *same* versioned RPCs, so `conflict = true` already writes the `sync_conflicts` row and version-mismatch-to-Needs-Review needs no new mechanism (this is why Needs Review precedes the outbox). Drain on `scenePhase == .active` and after every successful `signIn()` — "only syncs once a valid session exists" is structural, not a separate check. A transfer's two legs push in one call (`update_transfer` already does).
- `persist`/`restore` added to Phase 6's `DataStore`; unsynced flags; banner for items pending past a threshold.
- **Two calls that must be right first time:** `CaptureIntent` will be declared in the **app target**, not an extension, so the store lives in the app container and needs no App Group (not provisionable on a free personal team). File protection belongs here, not in Phase 17 — it's a property of the store, not the session.
- **Verify:** unit-test the drainer's conflict path against a stubbed client; simulator — airplane mode, create/edit/delete, foreground, confirm exactly one server row per client UUID after a forced double-drain; force a version mismatch via SQL and confirm it lands in Needs Review; assert the protection attribute reads back (real enforcement is device-only).
- **Delivered (Phase 11 migration/client work complete; human review stop below still pending):** outbox scoped to transactions only (create/update/delete, ledger + transfer) — not accounts/categories/households, per this section's own ambiguity about which entity "create/edit/delete" refers to; transactions are the highest-volume write and what Phase 12's capture depends on. Found and fixed a real idempotency gap before the outbox could expose it: `create_transfer` generated both legs' ids server-side, unlike every other write in this codebase — closed via `p_from_id`/`p_to_id` (migration `20260807140000`), so a retried transfer now hits a PK violation (23505) instead of duplicating. Pending items are invisible in every list until drained (no optimistic merge) — the stale-pending banner is the one "unsynced" signal, not a merged UI. `xcodebuild test -only-testing:KeepoTests` (headless, non-interactive) is green — 5 new `OutboxTests` covering conflict-vs-failure-vs-collapse. See version-logs/phase-11-log.md.
- **Human review stop #3.** End of the offline-outbox and file-protection work, before Phase 12's capture depends on it. - `merge_household_categories(p_member_a, p_member_b)` — **descoped from the original two-part design to exact-match only.** Category rows can never literally merge (the composite FK forces every category to stay owned by whoever uses it), so this gives each member a same-named copy of everything the other already has, called once from `accept_invite` with both member ids passed explicitly (not derived from `household_members.joined_at` — that column defaults to `now()`, which is frozen for an entire transaction, so two rows inserted moments apart in the same pgTAP test-file transaction can tie; explicit ids have no such hazard in tests or production). "Near-matches into Needs Review" (fuzzy suggestion) was **not built** — out of scope for this pass.
- `leave_household()`/`erase_own_account()` share `fork_household_accounts()`, the actual split: every account shared in the household gets forked into two fresh private copies (one per member), the original is archived (never deleted, for audit continuity), and only the *caller's* `household_members` row is removed — the remaining member keeps their (now single-member) household, the same state Phase 7 already handles pre-invite. **Design correction from the original plan text:** a forked transfer leg cannot keep its `transfer_group_id` (the sibling leg's account usually isn't part of the same fork), so every forked transfer leg becomes a plain `source = 'adjustment'` entry carrying the same signed amount instead — full details and reasoning in `supabase/migrations/20260810100000_household_lifecycle.sql`'s header comment.
- **The forkable-table registry** (`fork_handled_tables`) is a real table, not a static list in a comment: `fork_household_accounts()` queries `information_schema.columns` (joined to `information_schema.tables` for `BASE TABLE` only — views like `account_balances`/`needs_review` surface an `account_id` column too but hold no data of their own) and **raises** if any registered-nothing table exists, before doing anything else. Four handling strategies (`duplicate_to_both`, `repoint_by_owner`, `cache_recompute`, `deleted_on_leave`) cover the nine current tables. pgTAP proves the guard fires by adding an unregistered table inside a savepoint, then rolling it back.
- `erase_own_account()` = fork, then scrub the caller's *own* resulting copy's free-text fields (`merchant_raw`/`merchant_normalized` on transactions, `card_identifier`, import `filename`/`raw_row`) — never the other member's, which the fork's independence already guarantees.
- **Realtime was not built.** The original plan called for a cache-invalidation-only Realtime signal; this pass skipped it in favor of plain polling (`HouseholdRepository.fetchEvents`, read on `HouseholdView`'s own load) — a reasonable v1 substitute given the no-op-transport framing already means nothing pushes today regardless. Worth revisiting once Phase 20 wires a real transport.
- Notification seam: `household_events` (append-only, `SECURITY DEFINER`-only writes) + `notify_household()` calling the new `notify-household` Edge Function via the existing `ops_http_post` helper — a genuine no-op transport (logs and returns, per its own header comment), gated by a vault secret pair (`notify_household_url`/`notify_household_secret`) that doesn't exist yet in any environment, so it currently degrades to an `ops_events` log entry exactly like a missing FX-sync secret would. **No in-app banner was built** — `HouseholdView` shows recent events in a plain list on its own screen, not a global foreground banner; descoped for time, not a design decision to revisit necessarily.
- **Client:** `HouseholdView` (moved out of `SettingsView` — invites/leave/erase gave it enough of its own concerns), invite generate/share (plaintext code shown once), join-by-code, leave/erase behind a `confirmationDialog` + `session.stepUp(reason:)` immediately before the RPC (Phase 17's precedent).
- **Two-physical-device testing was not performed this session** — the master plan's own framing ("first real two-live-member testing") explicitly calls for physical hardware, which this pass didn't have access to. Server-side correctness (fork, registry guard, RLS, category merge, erasure) is proven by 24 new pgTAP assertions (263 total in the suite) against two fixture users; the client screens were verified to build/lint/compile only.

## Multi-currency transaction entry & capture currency mismatch (workstream, agreed 2026-09-15) ✅ delivered 2026-09-15

User-driven, not a numbered phase. Found while probing the Wallet automation for the onboarding redesign (`keepo-onboarding-redesign-plan.md` §3.8).

**Two real cases, neither expressible today.** (a) *Manual:* travelling in Europe with a USD account, the user wants to enter a EUR purchase — there is no way to say so. (b) *Capture:* Wallet reports `€50.00` on a card mapped to a USD account, and the pipeline **silently records $50**. `app-architecture.md:315` item 2 already specifies the safeguard — *"the symbol is a mismatch check only"* — and it was **never implemented**: `AmountParser.parseFormattedCurrency` strips the symbol at line 64 and returns a bare `Int64`, so there is nowhere for a check to happen.

**The schema constraint that shapes the design.** `transactions` carries `foreign key (account_id, currency) references accounts (id, currency)` (`20260804192805:197`), so a transaction's currency is structurally forced to equal its account's. Whatever is stored must be in the account's currency; that is not the thing to relax, since `balance = opening_balance + SUM(amount)` depends on it.

**Money rule 6 needs amending first, and the user has agreed to the distinction.** Rule 6 bans storing a **display** conversion (account currency → *viewer's base currency*), which must stay on-read so it survives a base-currency change. A conversion from **currency-paid → account currency** is different in kind: it is a fact about what happened, not a derivation. Amend CLAUDE.md rule 6 and `app-architecture.md` §4 to name both conversions and forbid only the first. **Doc first, then implement** — a future agent reading rule 6 as written would correctly conclude this work violates it.

**The hazard the design exists to avoid.** Keepo's ECB rate is *not* the rate the bank used — Revolut, Visa and Amex each add a spread. A silently stored ECB conversion is an estimate of a fact, and since the balance is a running sum, every foreign purchase drifts the account away from reality permanently, with a figure that was never true. So:

- The converted amount is **prefilled and editable**, never a silent result. The user overwrites it with the real charged amount from their bank app. This single property is what makes the feature honest.
- `transactions` gains `original_amount` + `original_currency` (nullable, provenance only, **never summed**) so the record says "€50 paid, $54.23 charged" and a later correction can re-derive.
- Money rule 3 holds: the multiplication happens **in SQL** through the existing `fx_convert`; the form previews via an RPC, never client-side arithmetic. Money rule 5 holds: no resolvable rate for that pair and date renders `—` and forces manual entry — never `0`, never a guessed rate.

**Mismatch behaviour, specified by the user 2026-09-15.** Parse the symbol (and currency *codes* — Wallet renders some currencies as `CHF 10.00` or `10,00 kr`). **Only act when certain:** `$` is ambiguous (USD/CAD/AUD/MXN) so `$` against a CAD account is accepted as-is; `€` against a USD account is a mismatch; an undeterminable string falls back to today's behaviour.

On a genuine mismatch, there are two cases and the second collapses into the first:

- **(A) The account is known** — the card was already mapped, so its currency is known. Keepo converts the detected amount into the account's currency and **sends both values to review**. The form shows **two amount fields**: the original currency amount, and the account-currency amount, which is **editable** so the user can add whatever FX fee their bank charged on top of the reference rate.
- **(B) The account is unknown** — the card was never registered. The amount and detected currency are **captured and held** until the user picks the account for that card. At that moment the account's currency becomes known and the row **falls back to (A)**: convert, show both, let the user adjust.

**This is why the workstream cannot be split into a "small safe fix" and "the feature".** An earlier plan to make the capture path safe by simply refusing to auto-assign a mismatched account was rejected: it throws away a known account, and the user's specification requires the dual-amount form, the stored original, and the conversion — all of which is the feature. One phase, with a migration.

**What case (B) forces.** Today `capture_transaction` inserts `account_id` **and** `currency` as null for an unmapped card — `account_currency_together` (`(account_id is null) = (currency is null)`) requires both or neither — so **there is nowhere to record the detected currency**. Hence the `original_amount` + `original_currency` columns are load-bearing, not merely provenance, plus their own CHECK that the pair is set or null together. Migration → `supabase gen types swift` → pgTAP → `db push`.

**The conversion itself needs no new code.** `fx_convert` / `fx_rate_on` exist in Postgres and are already ported to SQLite (`LocalMoneyConversion`, policed by the referee test in `KeepoTests`). So (A) produces identical numbers online and offline — only call sites are new.

**Four points the specification leaves open, resolved here:**

1. **Which rate date in case (B).** The deferred conversion uses `fx_rate_on(occurred_at)`, **never the mapping date**. A card mapped three weeks after the purchase must still convert at the rate on the day it happened.
2. **Store the original only when it differs.** `original_amount`/`original_currency` stay null in the ordinary same-currency case, so "is this a foreign transaction?" is a null check and the common row stays clean.
3. **No resolvable rate → money rule 5.** Offline with a gap in the mirror, or a genuinely missing rate: the account-currency field renders `—`, never `0`, and the user types it. Never guess a rate.
4. **Editability differs by direction.** On a *capture*, the original amount is a fact from Wallet and is read-only; the account-currency field is editable. On *manual* entry the user types the original and Keepo converts, so both are editable with the converted one prefilled. Same two fields, two modes.

**Form scope — three surfaces, not one.** Called out by the user and easy to under-scope: capture review, **transaction edit** (any transaction whose original currency differs from its account must keep showing both fields for its whole life), and manual entry. That means `TransactionFormView` and `TransactionDetailCard` — the one card shared by all three kind tabs — not just the capture review path.

**Seam status: the separator half landed 2026-09-15, the symbol half is this workstream's.** `parseFormattedCurrency` now takes **no locale at all** and infers the convention from the string, so the 100× bug is closed and the onboarding plan's Stage-3 prerequisite is met. It still returns a bare `Int64` and still discards the symbol: detecting the currency is deliberately left here, where `original_amount`/`original_currency` give a detected currency somewhere to live. Building the richer return type early would have been a value with no consumer.

**Shared seam with the onboarding workstream — do this once, not twice.** Both need `parseFormattedCurrency` to stop discarding information from the Wallet string: the **separator** (currently taken from `Locale.current`, a live 100× money bug — `$1.06` parses as `106` on an `es_ES` device; measured) and the **symbol**. One change makes the function return amount + detected currency and infer the separator from the string itself. That change is the onboarding plan's Stage-3 prerequisite and this workstream's foundation.

**`parseFormattedCurrency`'s design, settled 2026-09-15.** The distinction that matters: **a user-typed amount and a machine-formatted one have different authorities.**

- `AmountParser.parse(_:locale:)` stays **locale-aware and unchanged**. iOS shows a decimalPad carrying the locale's separator, the user types what they see, and reading it back the same way is the Phase 1 bug this type was created to fix.
- `parseFormattedCurrency` stops consulting the locale **entirely**. Its input was formatted by iOS for the *transaction's* currency, not typed by anyone, so the device is the wrong authority. The convention is read out of the string:
  1. Keep digits, `.`, `,`, `-`. Also strip `'` and `’` as grouping — **Switzerland writes `1'234.56`**, and CHF is in the supported set.
  2. Both `.` and `,` present → the **rightmost** is the decimal separator, the other is grouping.
  3. One present: more than once → grouping (`1.234.567`); once followed by **exactly 3 digits** → grouping (`1.234` → 1234); once followed by 1–2 digits → decimal separator.
  4. Normalize to `.`, parse with `en_US_POSIX`.
- Rule 3's three-digit case is safe **because no supported currency has 1 or 3 minor digits** — every row in `currencies` is 0 or 2 (`20260804184433:76`). It stops being a heuristic at all once currency detection lands in this workstream: with the currency known, `currencies.minor_unit` makes it a lookup. The two halves of this workstream reinforce each other, which is the other reason the seam is built once.
- Deterministic, no locale input, unit-tested against a matrix.

**Explicitly not this workstream: per-currency card mappings.** A genuinely multi-currency wallet (a Revolut card paying €50 from a EUR balance) involves **no conversion at all** — converting it would invent a transaction that never happened. The answer there is `card_mappings` keyed `(owner, card_identifier, currency)` routing to one account per currency, which is how Revolut itself models it. Separate, later, and it depends on symbol detection landing here first.

## Merchant matching (workstream, agreed 2026-09-15, approach revised same day) ✅ delivered 2026-09-15

Found via the onboarding probe. Real Square output is `SQ * Equity Park,Llc`; `MerchantNormalizer.corporateSuffixes` lists only space-separated forms, so three spellings of one shop produce three learning keys — `EQUITY PARK,LLC`, `EQUITY PARK`, `EQUITY PARK,` — and a category learned under one never matches the next.

**Decision: fix the normalizer.** An earlier decision to leave it alone and add a fuzzy matching layer was reversed once its consequence was made explicit — several `merchant_category_map` rows per shop, which is the thing normalization exists to prevent. Fuzzy matching becomes an optional later refinement for the long tail, not the mechanism.

**The insight the fix turns on: punctuation *inside* a name is identity; punctuation *at a boundary* is a separator.** Blanket stripping cannot tell them apart, which is why both blanket options were measured and rejected — removing the `*` from `SQ *` stops `stripPrefix` matching so `SQ` survives as noise in every result; replacing punctuation with nothing glues the suffix on (`EQUITY PARKLLC`); and it collides distinct payees (`M&S`/`MS`, `H&M`/`HM`) while still failing `AT&T` vs `AT AND T`. So the punctuation stays and the **matchers** become boundary-aware instead.

Three changes, prototyped and verified before adoption:

1. **Suffix matching becomes a regex with `[\s,]+` as the separator** rather than a literal leading space — `[\s,]+(?:PTY LTD|LLC|S.L.|...)$`. This is the actual defect: `,Llc` now matches where `" LLC"` could not.
2. **Trailing separators are trimmed after each strip**, killing the `EQUITY PARK,` case where the space-form matched and left the comma behind.
3. **The aggregator prefix becomes a regex** — `^(?:SQ|TST|SUMUP|ZETTLE|...)\s*\*\s*` — collapsing the `SQ *` / `SQ*` duplicate pairs, halving the list and tolerating stray spacing.

**Ordering is load-bearing and was not before.** ICU alternation is first-match-wins, so the suffix list must be sorted **longest-first**: with `LTD` ahead of `PTY LTD`, `BONDI CAFE PTY LTD` normalizes to `BONDI CAFE PTY` (measured). `CORP.` precedes `CORP`, `INC.` precedes `INC`.

The repeat/while loop stays — now three strips rather than two — and **idempotency becomes an explicit test**, not a comment.

Prototype output, all idempotent: the three `Equity Park` spellings and `SQ *EQUITY PARK 00042 LLC` all collapse to `EQUITY PARK`; `SUMUP *CAFE BERLIN GmbH` → `CAFE BERLIN`; `BONDI CAFE PTY LTD` → `BONDI CAFE`; `TIENDA MADRID S.L.` → `TIENDA MADRID`; and `AT&T`, `JOE'S PIZZA`, `H&M` are returned untouched.

**Lists move into unit-tested data in `KeepoCore`**, covering the 31 supported currencies, in four groups: aggregator prefixes (add SumUp, Zettle, Stripe, Adyen, Mollie, Viva, Redsys, Nayax, Worldline — SumUp and Zettle are Europe's Square), corporate suffixes, **company-form prefixes** (a category the code does not have today: `PT`/`CV` lead the name in Indonesia, `株式会社`/`(주)` can sit either side — distinct from the aggregator list), and the trailing-separator set.

**Two-letter suffixes are the risk class and are admitted only in punctuated form** (`A.S.`, `B.V.`, `S.A.`, `A/S`). Bare `AB` `AG` `AS` `AD` `NV` `KG` `OG` `OY` `SA` `SL` `ME` `CC` `DD` `MB` stay out: US card descriptors routinely end in a two-letter state code, and `ME` is both a Brazilian company suffix and the code for Maine. **`CO` is kept as the one deliberate exception, at the user's instruction** — accepted cost, `LUCKY CO` normalizes to `LUCKY` and collides with a merchant genuinely named `LUCKY`.

**Why this is roughly a tenth of the fuzzy design's cost, confirmed not assumed:** `capture_transaction` takes `p_merchant_normalized` **as a parameter** — the client computes it in Swift and the server only stores it. The normalizer is therefore one implementation, in one language, already shared by the online and offline paths. Fuzzy matching at lookup time would have needed a Postgres implementation (`resolve_category_for_merchant`) *and* a SQLite one (`CaptureLocalWrite` resolves merchant→category on-device so a capture lands offline), kept in step by a referee test — the same two-implementation burden the money layer already carries.

**What this does not fix, and is fine:** `AT&T` vs `AT AND T`, `MCDONALDS` vs `MC DONALDS`, truncated descriptors, suffixes outside the list. That is the fuzzy layer's remit if it is ever wanted.

**No backfill** — the user is the only account. Note the correction that prompted asking: `merchant_category_map` is a **synced** table (`SyncApply.swift:56`), so reinstalling the app clears only the local mirror and the next pull restores the server rows. Changing the normalizer changes the key, so the pragmatic reset is `delete from merchant_category_map` against hosted, letting it re-learn. **Carry forward: any post-launch change to normalization requires a real backfill**, which `merchant_raw` is retained to make possible.
