# Phase L2 — Sync primitives on the server

Part of the local-first rebuild (`keepo-local-first-plan.md`). Server-side only — the app stays online-first and behaves identically; nothing in the App target consumes this yet. Builds the ticket-based delta cursor, per-domain sync_seq stamping, `pull_changes`, and the gain/loss-of-access signals (re-stamp on share, `sync_epoch` bump on loss) that L3–L6 will build the on-device store and read path against.

## Delivered

- `supabase/migrations/20260816100000_sync_primitives.sql` + a same-day follow-up `20260816100001_sync_primitives_fixes.sql` (see Findings #1 for why two files) — `sync_tickets(domain_id, next_ticket)` + `next_ticket(p_domain_id)` (row-locked via `select ... for update`, held until commit — the actual ordering guarantee); `sync_domain_id(p_user_id)` (household id if the user belongs to one, else their own id) and `sync_global_domain()` (one fixed domain for `currencies`/`fx_rates`, which have no owner of their own); `sync_seq bigint` + a `BEFORE INSERT OR UPDATE` trigger on all 16 syncable tables; `deleted_at` added where missing (`balance_snapshots`, `budgets`, `fi_settings`, `card_mappings`, `merchant_category_map`, `sync_conflicts`, `households`, `household_members`, `household_accounts`, `profiles` — `currencies`/`fx_rates` deliberately excluded, nothing ever deletes from them); a domain-spanning backfill (one unified `row_number()` ranking across all 16 tables together, not per-table — tickets are one counter per domain shared across every table, so a per-table backfill would have corrupted that from the start).
- `sync_epoch bigint` on `profiles`. Bumped on `leave_household`, `erase_own_account`, `accept_invite` (the *accepting* user's own domain changes solo → household), and on `unshare_account` for the *losing* member only when a fork occurs.
- `household_members`/`household_accounts` converted from hard `DELETE` to soft-delete (`deleted_at`) — a hard delete gives the remaining member's next pull nothing to learn the departure from. `my_household_id()`, `can_read_account()`, `accounts_select`/`accounts_update` (the H3 inline-policy exception), and `enforce_household_member_cap()` all updated to filter `deleted_at is null`. `accept_invite` reactivates a tombstoned row (`ON CONFLICT ... DO UPDATE`) rather than colliding on the PK when a former member rejoins.
- `fork_one_account(p_old_account_id, p_member_a, p_member_b)` extracted from `fork_household_accounts`' per-account loop body, so `unshare_account` (now forking when another member is present, closing LH4/LH12 the same way `leave_household` already did) and `fork_household_accounts` share one implementation.
- `restamp_account_for_sync(p_account_id)` — re-stamps an already-shared account and its transactions/snapshots/recurring rules with fresh tickets (LH3: they predate the share and carry old tickets a normal cursor pull would never re-fetch). `bump_version()`/`set_updated_at()` gained a transaction-local `keepo.restamp_only` escape hatch (`set_config`, resets automatically at commit/rollback) so the re-stamp doesn't also bump `version`/`updated_at` on every touched row.
- `pull_changes(p_cursor, p_global_cursor)` — `SECURITY INVOKER` (RLS filters every table for free, no second copy of the access model in an Edge Function). Returns one JSON object keyed by table name plus two advanced cursors and the caller's `sync_epoch`. Two cursors, not one — see Findings #2.
- `create_household()`'s own-membership guard fixed to route through `my_household_id()` (Findings #4).
- `supabase/tests/23_sync_primitives.sql` (new, 21 assertions) — stamping, domain resolution, `pull_changes`' RLS-for-free filtering and cursor idempotency, LH3 re-stamp within one stable domain, LH4/LH12 fork-and-epoch-bump, rejoin-after-leave, and the global domain. `supabase/scripts/two_session_ticket_order.sh` (new) — the cross-transaction ticket-ordering guarantee pgTAP structurally cannot express (one test file is one transaction); run manually against two real overlapping `psql` sessions, confirmed empirically.
- `app-architecture.md` amended: a new "Sync primitives" subsection, the `unshare_account`-is-not-a-fork line corrected (it forks now), `household_members`/`household_accounts` table descriptions updated for `deleted_at`.

## Findings

1. **`supabase db push` tracks applied migrations by filename, not content — editing an already-pushed migration file does nothing on the next push.** Pushed `20260816100000` once, then kept fixing bugs found by pgTAP by editing that same file. `supabase db push` reported "up to date" with zero migrations applied — hosted was silently left running the *original, buggy* versions of `pull_changes`, `restamp_account_for_sync`, `accept_invite`, and was entirely missing the `create_household` fix (added after the first push). Fixed by writing the corrections as a genuinely new follow-up migration (`...100001`), the same pattern this project already used for `20260814100000` + `20260814100100`. **Never edit a migration file after it's been pushed** — even within the same session, even before anyone else could have pulled it.
2. **A single scalar cursor across multiple independent ticket counters is broken by construction.** `currencies`/`fx_rates` were given their own "global" domain (reasonable — a rate has no owner) sharing one ticket counter across every user. `pull_changes`' first draft took `next_cursor = max(sync_seq)` across *all* tables including the global ones. Since the global counter accumulates across every user's `fx_rates`/`currencies` writes and grows far faster than any one household's, a client's cursor was almost always dominated by the global counter's high values — so a fresh LH3 re-stamp in a quiet household domain (ticket, say, #6) sat below a cursor already past #500 from currencies alone, and `sync_seq > cursor` was false forever; the re-stamped row would never actually be delivered. Caught by pgTAP, not by inspection — the test asserted "a pull from before the share now delivers the account" and got 0. Fixed by giving `pull_changes` two independent cursors (`p_cursor` for domain-scoped tables, `p_global_cursor` for currencies/fx_rates), each only ever compared against its own counter. General lesson: any cursor comparison spanning rows stamped from more than one independent counter needs a cursor per counter, not one shared scalar.
3. **`ALTER TABLE ... DISABLE TRIGGER` fails whenever the target table has pending deferred trigger events in the same transaction** — "cannot ALTER TABLE because it has pending trigger events." `restamp_account_for_sync`'s first draft used `disable trigger user` + an explicit `sync_seq` write to avoid bumping `version`/`updated_at` during a re-stamp. This works at fresh-migration-apply time (nothing else has run yet) but breaks the moment the account was created earlier in the *same* transaction — exactly what pgTAP's own test files do, via the `DEFERRABLE INITIALLY DEFERRED` FK triggers on `accounts`/`transactions`. In real (non-pgTAP) usage this specific sequence is unlikely (PostgREST is one transaction per HTTP request, so account creation and a later `share_account` call are normally in separate transactions) but the fragility is real regardless. Fixed with a plain touch `UPDATE` plus a transaction-local `keepo.restamp_only` flag (`set_config`, resets automatically at commit/rollback including on an exception) that `bump_version()`/`set_updated_at()` both check — avoids `ALTER TABLE` entirely rather than working around when it's safe to call it.
4. **A raw `EXISTS` check against a table with soft-deletes needs the same `deleted_at is null` filter as every other membership check, or it never expires.** `create_household()`'s guard (`exists (select 1 from household_members where user_id = auth.uid())`) predates L2's soft-delete conversion and was never updated, so a user who had ever left a household — leaving a tombstoned row — was permanently blocked from ever creating a fresh one again. Every *other* membership check in this migration was written from scratch against `my_household_id()` (which does filter correctly); this one already existed from Phase 7 and was missed until pgTAP's rejoin/fresh-household scenario surfaced it as "you already belong to a household" on a user who very much did not.
5. **Backfilling a shared, cross-table counter needs one unified ranking, not sixteen per-table ones.** Tickets are one counter per domain, shared across *every* table a domain's writes touch — a naive per-table backfill (each independently starting `row_number()` at 1) would have produced sixteen colliding, meaningless numberings instead of one coherent history. Built as a single `UNION ALL` across all 16 tables' `(table_name, row_key, domain_id, timestamp)` tuples, ranked together per domain, then scattered back per table via `ALTER TABLE ... DISABLE TRIGGER USER` (safe here — this runs once at fresh migration-apply time, before anything else in the transaction could leave deferred events pending, unlike Findings #3's later, narrower use inside `restamp_account_for_sync`).
