# Phase 5 — SQL test harness, seed data, hosted proof

## Delivered

- `supabase/tests/`: pgTAP suite (`_helpers.psql` + 5 numbered files, 47 assertions) covering every invariant from Phases 1–4 that previously existed only as prose in the phase logs — grants/RLS/schema-wide hygiene, the ledger/valuation balance formulas, transaction integrity constraints, the versioned edit/delete RPCs' conflict-as-data convention, and FX conversion. Runs via `supabase test db --local supabase/tests`, fully transactional — confirmed the whole run (including `_helpers.psql`'s own `create extension pgtap`) leaves zero trace on the persistent local database.
- `supabase/seed.sql` — `config.toml` has pointed `db.seed.sql_paths` at this file since Phase 1; it never existed. Two users (different base currencies, EUR/USD), three accounts (EUR checking, USD checking, EUR investment with a snapshot), a few transactions, a week of USD fx_rates. Runs on every `supabase db reset`.
- Migration `20260805170000_category_ownership_integrity.sql` — closes H12 (a transaction could reference another user's category id; the accounts equivalent gap was closed in Phase 2 via a composite FK, categories never got the same treatment). Adds `unique (id, owner_id)` on `categories` and `transactions (category_id, owner_id) references categories (id, owner_id) deferrable initially deferred`, mirroring the existing `(account_id, owner_id)` pattern exactly.
- `KeepoCore/PasswordAuthProvider.swift` — hosted-capable `AuthProvider`, same fixed-credentials shape as `StubAuthProvider` but no `isLocal` precondition. `SessionStore.init` now picks stub vs. password provider by `config.isLocal` — the only branch point, nothing else in the app knows which is active.
- **Hosted proven for the first time in this codebase.** The linked hosted project (`keepo-app`, ref `fmogwbadhimwfhhibrau`) already existed with Phases 1–4's migrations pushed; this phase's own H12 migration was pushed (`supabase db push --linked`), and a real end-to-end round trip was driven from the simulator against hosted: sign-in → `handle_new_user()` bootstrap → onboarding write (`base_currency`/`onboarded_at`) → first-account creation → `accounts_with_balances` read, all through RLS with a real (non-local) JWT. Independently confirmed via a direct REST query with `service_role`.

## Bugs found only by building and running this, not by inspection

1. **`supabase test db` globs every `.sql` file in the target directory as a test file, including a shared-setup file with no `plan()`/`finish()`.** The first version of `_helpers.sql` got picked up and run standalone, and because it has no `BEGIN`/`ROLLBACK` of its own, its `create extension pgtap` and fixture-user inserts **committed for real** to the persistent local database — leaking `anon`/`authenticated` grants (via pgTAP's own `tap_funky`/`pg_all_foreign_keys` objects, which grant themselves to `PUBLIC` on install) into the exact schema-wide assertions this phase exists to make reliable. Fixed by renaming to `_helpers.psql` (non-`.sql` extension, invisible to the glob) and cleaning the leaked extension off the persistent db with `drop extension pgtap cascade`.
2. **`now()` is frozen for the whole enclosing transaction, and a whole pgTAP test file IS one transaction.** Inserting a `balance_snapshots` row and then a same-transaction transfer in the same test file gave both rows the *identical* `now()`-derived timestamp, making `occurred_at > created_at` false and silently failing to reproduce the same-day-transfer scenario the test exists to cover — a test-harness artifact, not a real bug (two separate client calls in production never tie down to the microsecond). Fixed by backdating the snapshot's `created_at` explicitly via `clock_timestamp() - interval '1 minute'`.
3. **A `DEFERRABLE INITIALLY DEFERRED` FK/constraint's violation survives past `throws_ok`'s own internal savepoint.** `throws_ok` wraps only the statement that forces the check (`SET CONSTRAINTS ALL IMMEDIATE`) in its own savepoint/rollback — the *earlier* INSERT that actually violates the deferred constraint is untouched by that rollback, so the bad row and its still-pending violation leaked into a later, unrelated assertion in the same file. Fixed with an explicit outer `SAVEPOINT` wrapping both the insert and the immediate-check, rolled back manually afterward.
4. **pgTAP's `throws_ok` never takes a free-text description as an argument after `sql` in its 2-/3-arg forms** — every such argument is matched against the actual error (a 5-character string dispatches as an expected SQLSTATE; anything else is matched as the exact expected message). Confirmed against pgtap's own installed source (`pgtap--1.3.1.sql`) after two different assertions failed expecting a friendly description to match verbatim as the real constraint error text. The 4-arg form (`sql, errcode, null, description`) is the only one that pins a SQLSTATE while leaving the message unchecked and still takes a real description.
5. **Hosted GoTrue's email validator rejects the `.test` TLD** (`email_address_invalid`) that the local stack accepts without complaint for `.local`. `PasswordAuthProvider`'s default identity uses `.dev` instead.
6. **Hosted signups require email confirmation by default; the local stack doesn't.** `PasswordAuthProvider`'s `signIn()` — identical logic to `StubAuthProvider` — got `invalid_credentials` on every attempt because the just-signed-up user was unconfirmed. Rather than disabling email confirmation project-wide (a real, persistent security-policy change to the hosted project, out of scope for a one-time proof), the hosted-proof identity was created directly via the Admin API (`POST /auth/v1/admin/users` with `email_confirm: true`, using `service_role`) — a one-time provisioning step, not a config change.
7. **`supabase gen types --linked` returns empty structs for every table and view**, even though enums come through correctly — the CLI's temporary introspection role (provisioned via the Management API's `cli/login-role` endpoint) apparently lacks column-level `SELECT` privilege on `public`, even though the same role can run `db push`/`migration list` DDL successfully. Confirmed with `--debug`; no CLI flag exists to point it at a different role. **The plan's "diff hosted vs. local generated types" verification step is blocked by this CLI limitation, not a schema problem** — the actually load-bearing verification (hosted round-trip through the real app, and the generated types already matching what local produces, confirmed by there being zero diff between a fresh `--local` generation and the committed `Generated/SupabaseSchema.swift`) is unaffected. Worth a `supabase` CLI issue report if this persists into a later phase that actually needs hosted type generation.

## Notes for the next phase

- The hosted-proof user (`hosted-proof@keepo.dev`, one checking account) is left in place on hosted — harmless, not a secret, documents the proof. No cleanup needed unless it becomes confusing later.
- `Config/Debug.xcconfig` only ever holds one active `SUPABASE_URL`/`SUPABASE_ANON_KEY` pair — proving hosted meant temporarily swapping the file's values and restoring them afterward, not adding a permanent third scheme/config. If hosted testing becomes a recurring need (e.g. once Phase 7's two-fixture-user testing wants a live check against hosted), a dedicated `Hosted` build configuration is worth adding then — not before, per "simplest code that solves the actual requirement."
- `supabase gen types --linked` is unreliable in this environment (see bug 7) — don't rely on it for anything beyond a sanity check; `--local` remains the source of truth for the committed `Generated/SupabaseSchema.swift`, matching CLAUDE.md's existing command list.
- The pgTAP suite's fixture identities (`11111111-...`, `22222222-...`) are distinct from `seed.sql`'s own two seed users — deliberately, so a manual `db reset` + Studio poke-around can never desync a test run. Keep that separation when Phase 7 adds household-specific fixtures.
- `SET LOCAL ROLE` cannot be issued from inside any PL/pgSQL function body, `SECURITY DEFINER` included — a `tests.as_user(uuid)` wrapper was tried and rejected for this reason (see `_helpers.psql`'s inline comment). Role switching in every test file is three plain top-level statements at the call site; there's no way to make it a one-liner without giving `authenticated`/`anon` a role grant that would itself be a security regression.
