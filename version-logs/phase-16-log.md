# Phase 16 — Budgets & FI

## Delivered

- Migration `20260808150000_budgets_fi.sql`: `budgets` (H13 doc amendment — `amount` + `currency` typed, never `amount_base`; a stored converted amount would violate money rule 6 and can't be correct for two household members with different base currencies simultaneously). `period_month` is normalized to the first of the month by a `before insert or update` trigger, never trusted from the client — a mid-month value would silently dodge both partial unique indexes otherwise. Two partial unique indexes stand in for one constraint (`(owner_id, category_id, period_month) where category_id is not null` for a category budget, `(owner_id, period_month) where category_id is null` for the overall budget) since NULL is never equal to NULL in a plain unique constraint — a bare `unique (owner_id, category_id, period_month)` would silently allow unlimited overall budgets per month.
- `budget_progress(period_month)` — the read side. Actual spend excludes transfers via the same `category_id is not null` guarantee every Phase 15 function already relies on. Null-propagates a missing FX rate on any contributing transaction, explicitly distinguished from "genuinely zero spend so far" — both `bool_or(...)` and `sum(...)` return `null` over zero matching rows in plain SQL, so each is coalesced to a real, distinguishable default (`false`/`0`) before the unconvertible check runs, or the two cases (no spending yet vs. can't compute) would be indistinguishable.
- `fi_settings` — one row per user, seeded once at signup (same shape as `profiles`: no INSERT grant/policy at all, only `handle_new_user()`/`ensure_user_bootstrap()` ever create a row) so there's always exactly one editable row, never an upsert-on-first-view code path. `target_annual_spend` nullable → derives from trailing 12 months of real expense activity (excluding transfers, same shape as `savings_rate`) when unset.
- `fi_metrics(scope)` — FI number (`annual_spend / withdrawal_rate`), current net worth (**filtered to `accounts.counts_toward_fi`** — the column existed since Phase 1 but had never been read by anything until this function), % progress, years-to-FI, and Coast FI. Years-to-FI solves the standard compound-contributions formula (`t = ln((fi_number + savings/r) / (net_worth + savings/r)) / ln(1+r)`), with explicit branches for: already-FI (`net_worth >= fi_number` → `0`, skipping the formula entirely), net dissaving (`annual_savings <= 0` → `null`, never a negative or NaN result), and a zero real-return rate (falls back to simple linear division, avoiding `ln(1)` in the denominator). Coast FI is `fi_number / (1+r)^years_to_fi` — the net worth that alone, growing untouched, reaches the FI number by the same date years-to-FI already projects with continued contributions; this is what makes it "crossed years earlier" without needing a separate target-retirement-age input the schema never had in the first place.
- `KeepoCore`: `BudgetRepository`, `FIRepository` — plain RLS-scoped reads/writes for budgets (same reasoning as `RecurringRuleRepository`: infrequent edits, no concurrent-edit hazard worth a versioned RPC layer) and a thin RPC wrapper for `fi_metrics`/`fi_settings`.
- `App`: `BudgetsView`/`BudgetFormView` reached from Settings (Household/Recurring's own precedent — a feature earns a tab only when it's a primary, frequent destination). `FISettingsView` reached from `InsightsView`'s new "Financial Independence" section — the same pattern Home already uses to link out to Sync Ritual from wherever the number it feeds is actually shown.

## Findings

1. **`handle_new_user()`/`ensure_user_bootstrap()` needed a third careful hand-edit this project, and this time nothing was dropped** — confirmed by re-reading the full, already-fixed (Phase 15) version before adding the `fi_settings` insert, rather than editing from memory of what Phase 9/12 originally wrote. Given this function's history (Phase 12 silently dropped the "Other" category seeding when adding Uncategorized, only caught in Phase 15), every future addition to it should be written by reading the current full body first, never appended blindly to what a comment claims is there.
2. **`bool_or`/`sum` both return `null` over zero matching rows** — the exact same money-rule-5 subtlety Phase 15 already found for `savings_rate`, now confirmed to generalize to `budget_progress` too: a category with no spending yet and a category with an unconvertible transaction are both, naively, "null" from the raw aggregate — the `coalesce(bool_or(...), false)` / `coalesce(sum(...), 0)` pattern is what actually tells them apart. Manually verified with a real query before trusting the SQL by inspection (a category with zero transactions correctly returned `0`, not `null`, confirming the coalescing actually does what it's supposed to).
3. **The years-to-FI formula needed explicit branches for edge cases that are the actual common case for a new user**, not corner cases to handle defensively after the fact: already-FI, net dissaving, and a zero real-return-rate assumption are all things a real user will plausibly hit (someone testing FI settings for the first time will absolutely try `real_return_rate = 0` or a `target_annual_spend` that makes them "already there"). Verified each branch manually against real inserted data before writing the pgTAP suite, not just algebraically.

## Notes for the next phase

- **Not a human review stop** — per the master plan's cadence, only Phases 5/8/11/19 are designated stops.
- Budgets have no delete path anywhere — matches this project's schema-wide "zero DELETE policies" invariant (enforced automatically by `01_grants_rls.sql`'s dynamic assertion). A mistaken budget is corrected via `BudgetFormView`'s edit flow (amount only — category and month are locked once created), not removed.
- `BudgetFormView` only ever creates a budget for the *current* calendar month — there is no UI path to create or edit a past or future month's budget in v1, matching "calendar month, no rollover" at face value. If a later phase wants budget history or forward planning, `budget_progress`'s `p_period_month` parameter and `budgets.period_month` column already support it; only the client's create flow is scoped to "this month only."
