# Phase 6 — Account lifecycle & shared client data layer

## Delivered

- Migration `20260805180000_account_lifecycle.sql`: `revoke update on accounts from authenticated` (closes H4 — accounts finally gets the same treatment transactions got in Phase 3); DEFINER RPCs `update_account`/`archive_account`/`delete_account`, all version-checked, all conflict-as-data (never `RAISE` for a stale version), all with no parameter a Swift `Optional` can send as bare `nil` (no optionals in any of the three signatures at all, so Phase 3's `PGRST202` lesson doesn't even come up). Editable: `name`, `subtype`, `opening_balance`, `include_in_total`, `counts_toward_fi`. Not editable, by omission from the parameter list: `currency`, `kind`. `delete_account` refuses (raises, nothing to audit) while non-deleted transactions still reference the account. `accounts_with_balances` gets `version` appended at the end (Phase 3's `CREATE OR REPLACE VIEW` ordering rule).
- `supabase/tests/06_account_lifecycle.sql` — 9 new pgTAP assertions (raw UPDATE denied, correct-version edit applies every column and bumps version, stale-version edit is a no-op conflict with exactly one `sync_conflicts` row, archive/unarchive round-trips, delete refused with transactions present, delete succeeds with none). `02_accounts_balances.sql` updated in place: its cross-user "silent no-op" assertion became a permission-denied assertion, since the raw grant this phase revokes is what that test was exercising — the RLS behaviour it originally checked is real but now unreachable for any caller, not just a cross-owner one.
- `KeepoCore/AccountWrites.swift` — `AccountRepository.update`/`setArchived`/`delete`, mirroring `TransactionWrites.swift`'s `WriteResult` shape (`AccountWriteResult`). `AccountRepository.fetchOne` added to `Repositories.swift` for the raw `accounts` row an edit form needs — `accounts_with_balances` exposes the computed running `balance`, never the stored `opening_balance` a form has to prefill.
- `KeepoCore/DateFormatting.swift` (`PostgresDate`) — one codec replacing all 8 ad-hoc `ISO8601DateFormatter()` call sites (closes H8). Found and fixed a real bug in the process: the `balance_snapshots.as_of` write built a `date` column by slicing an ISO8601 *timestamp* string to its first 10 characters — `ISO8601DateFormatter` renders in UTC by default, so that slice is the UTC calendar day, not the device's local day. Anyone within a few hours of UTC midnight got tomorrow's (or yesterday's) date written silently. `PostgresDate.dateOnlyString` now formats against the device's actual calendar/timezone.
- `KeepoCore/AmountParser.swift` gains `AmountFormatter.editableString(_:minorUnit:locale:)` — the missing inverse. `TransactionFormView`'s edit-mode prefill used `"\(abs(amount))"`, always period-decimal regardless of locale (the Phase 1 bug, in reverse); both prefill sites there and both prefill sites in the new `AccountFormView` now go through it.
- `App/RefreshCoordinator.swift` + `App/DataStore.swift` (closes H7) — `@Observable` token bump + generic load/loading/error wrapper. Every list screen's `.task {}` became `.task(id: session.refresh.token) { await load() }`, and every write site (`TransactionFormView`'s `onSaved`, `CategoriesView`'s add/delete, `AccountsListView`'s create/edit/archive) calls `session.refresh.bump()` instead of directly reloading itself — a write on any tab now invalidates every tab, confirmed live in the simulator (creating an account on the Accounts tab made a brand-new "Investments" section appear with no manual refresh, and the Transactions/Categories tabs both still loaded correctly afterward). Landed in the **App** target, not KeepoCore — `@Observable` requires macOS 14, and KeepoCore's `swift test`/`swift build` host platform floor is pinned to macOS 13 for `supabase-swift`; bumping that floor just to host two App-only UI types wasn't worth it. `RefreshCoordinator`/`DataStore` have no KeepoCore dependency at all, so the move cost nothing.
- `App/AccountFormView.swift` — create/edit, mirroring `TransactionFormView`'s `Mode` enum. Create mode offers all 5 subtypes (kind derived exactly like `OnboardingView`'s first-account step: `subtype == .investment ? .valuation : .ledger`) and a currency picker seeded from the profile's base currency. Edit mode fetches the raw row via `AccountRepository.fetchOne`, locks currency to plain text, and restricts the subtype picker to the account's own kind's allowed subtypes (a single, disabled option for a valuation account — `subtype_matches_kind`'s CHECK makes anything else impossible, so the picker never pretends otherwise). Conflict handling mirrors `TransactionFormView.reloadAfterConflict` exactly: reload the row, repopulate the form, alert.
- `App/AccountsListView.swift` rewritten: "+" toolbar button → `AccountFormView(.create)`; tap a row → `AccountFormView(.edit(id))`; swipe → archive/unarchive (single `setArchived` RPC call, direction inferred from current state); a third "Archived" section (muted text, no subtotal) so an archived account stays reachable for unarchiving instead of disappearing. Per-section subtotals convert every account into the base currency and render `—` (never a partial sum) the instant any account in that section has a missing rate — a subtotal that silently dropped one account's contribution would look like a real total while quietly being wrong.

## Notes for the next phase

- The pre-existing onboarding flow (`OnboardingView` → `AccountRepository.create`) is untouched and still the only path that creates a *brand-new user's first* account; `AccountFormView.Mode.create` is the path for every account after that. Both call the same `AccountRepository.create`.
- `accounts_with_balances`' per-section subtotal (Accounts screen) is deliberately **not** filtered by `include_in_total` — that flag governs the future Home/net-worth total (Phase 8), not "what counts toward this screen's section subtotal." Worth being explicit about this distinction when Phase 8 builds the real net-worth total, so the two don't get conflated.
- `RefreshCoordinator`/`DataStore` intentionally have zero persistence — Phase 11 adds `persist`/`restore` to `DataStore` once offline caching is real, not before.
- The iOS Simulator MCP tool's on-screen keyboard is unreliable for anything beyond short, simple strings in this environment — typed text was repeatedly garbled or partially dropped mid-session (a name field ended up as "Invests - No balance" after typing " Account", apparently via autocomplete/QuickType interference), and toggle taps sometimes landed on the wrong row after a keyboard-dismiss layout shift. None of this reflects an app bug — confirmed by cross-checking the actual DB state via `supabase db query --local` mid-session — but it means simulator-typed text should never be trusted verbatim as an assertion of *what was typed*, only that *some* value round-tripped through the form correctly. Screenshot-and-verify after every text/tap action, not just after the first.
- `supabase db query --local` (not `supabase db execute`/`psql` — neither is available in this environment) is the right tool for ad-hoc data verification against the local stack.
