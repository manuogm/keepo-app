## Findings

1. **Same-process `ModelContainer` hazard, found before it could bite.** `CaptureIntent` and `SessionStore` both need `OfflineStore`'s SwiftData store, and both run in the same process (the entire reason `CaptureIntent` is declared in the app target and not an extension — Phase 11's log). Two separate `ModelContainer`s each opening their own persistent-store coordinator against the identical SQLite file is a real hazard, not a hypothetical one. Fixed by memoizing `OfflineStore.makeContainer()` (an `NSLock`-guarded static, `nonisolated(unsafe)` since the compiler can't see the manual synchronization) — every caller in the process gets the same container; a `ModelContext` per caller (what `Outbox`/`PayloadCache` already do) stays fine.
2. **`MerchantNormalizer` wasn't idempotent on its first pass**, caught by a dedicated idempotency test before it shipped. A store number and a corporate suffix can appear in either order in a real merchant string ("STORE 00042 LLC" vs "STORE LLC 00042"), and a single linear strip-prefix-then-strip-suffix pass only catches the number when it's genuinely at the string's end *after* the suffix is gone — which it isn't yet, on the first pass, if the suffix comes after the number. Fixed by looping the number-strip and suffix-strip together to a fixed point inside `normalize(_:)`, so the result — and the idempotency property merchant learning depends on (`merchant_category_map` keys off the normalized form) — no longer depends on which piece of noise happens to come first.
3. **Capture is expense-only in v1** — `capture_transaction` filters merchant-map lookups to `kind='expense'` and always inserts a negative amount (`-abs(p_amount)`). Refunds (which would need to post as income, or at least a smaller-magnitude expense) are explicitly out of scope; the feature spec itself lists "whether a refund fires the Wallet trigger and how its amount is signed" as a device-only open question for Phase 20's checklist, not something buildable or testable now.
4. **An unmapped card drops the specific purchase, by design, not as an oversight.** `capture_transaction` cannot insert a transaction without an `account_id` (the column is `not null`, and there's no "unmapped" holding account to invent without adding scope nobody asked for). The first tap on a newly-Wallet-automated card creates only the `card_mappings` placeholder; that specific purchase is never captured, even after the card is mapped afterward. Every subsequent capture on that card succeeds normally. This matches `app-architecture.md`'s own accepted-limitations framing for capture generally (Apple Pay only, on-device only, user-built automation) and is now stated plainly in the doc rather than left implied by "the row is still created."

## Update — 2026-08-15: end-to-end fix + local-first capture

The Wallet automation had never actually worked end to end — found and fixed while wiring it up for real:

1. **Root cause: `CaptureIntent` was never authenticated.** It built its Supabase client via a bare `makeSupabaseClient(config:)`, which reads the SDK's own default Keychain storage — a *different* Keychain item than `SessionStore`'s `KeychainSessionStorage()` (custom service/key) for any hosted build. `auth.uid()` was always null inside `capture_transaction`, so RLS rejected every insert. Fixed by mirroring `SessionStore`'s exact branch (`config.isLocal ? nil : KeychainSessionStorage()`). This is almost certainly why the feature "never worked" — everything else (RPC, RLS, rate limiting, merchant learning) was already correct.
2. **`openAppWhenRun` was never set** — Apple defaults it to `true`, so every automation fire force-opened the app UI even with "Ask Before Running" off. Set to `false`; the intent does no UI work.
3. **Trimmed the Shortcuts parameter surface from 5 to 3** (`card`, `merchant`, `amount` — dropped `transaction`/`name`, which never fed the schema and only added fields the user had to see/skip when wiring the automation).
4. **Local-first capture** (`CaptureLocalWrite.swift`): the capture write was the one outbox write that never touched the local GRDB mirror before this — `Outbox.submitCaptureTransaction` attempted the RPC directly, so an offline capture on an already-mapped card was invisible in Needs Review until the next successful sync. Fixed with a resolve-then-write fast path mirroring `capture_transaction`'s own logic (card → account, merchant → category, both already synced locally): if resolvable, writes the pending row locally immediately (`OutboxCaptureResult.appliedLocally`) and fires the RPC attempt in the background via the existing `attempt`/`enqueue` machinery; if not resolvable (brand-new card, or a mapping that hasn't synced down yet), falls straight through to the pre-existing RPC-or-queue path, unchanged. Deliberately never creates the `card_mappings` placeholder row locally (server-generated id — would permanently fork into a duplicate `ambiguous_card` entry the real mapping never resolves).
5. **`notes` column added** (`transactions.notes text`, migration `20260821100000`) — a general freeform field on every transaction, editable in `TransactionFormView`, not capture-specific. Captures auto-fill it with `"Captured automatically — {merchant}"`, so a capture that falls back to the default category still carries the raw merchant name somewhere visible.
6. **Rich, deep-linking notification.** The capture notification is now two lines (bold "New expense logged automatically!" / "$X · Category · Account — tap to review"), sourced from the local-first resolution so it works offline too. Tapping it deep-links straight into `TransactionFormView` prefilled on that row — new `NotificationRouter` (an `@Observable` singleton bridging `AppDelegate`'s `UNUserNotificationCenterDelegate` to `RootView`, which has no other reachable path from a delegate constructed before any view exists) + `AppDelegate` (`UIApplicationDelegateAdaptor`, needed only because `UNUserNotificationCenterDelegate` needs an object to own it). Only the local-first fast path sets the deep-link id — the RPC-only fallback path (unmapped/unresolvable card) has nothing local to open yet, so it still just opens the app normally.
7. **"Uncategorized" → "Other" cosmetic fix.** The fallback category itself was already renamed to "Other" back in migration `20260814100100` (the `system_key`/`Uncategorized` design was fully retired then) — but `needs_review`'s `pending_capture` subtitle and `LocalMoneyQueries.needsReview`'s local mirror of it still hardcoded the old word. Fixed both to say "Other", matching the actual category name.

Verification: `xcodebuild -scheme Keepo build` clean, `swiftlint lint` 0 violations project-wide, `swift test` (KeepoCore) 66/66, `xcodebuild test -only-testing:KeepoTests` 48/48 (2 new: local-first capture resolves and writes locally on a mapped card; an unmapped card still falls through to the queue path untouched).

Docker became available later in the same session — `supabase db reset` replayed the full migration history including the new one cleanly, `supabase test db --local` is 285/285 (one pre-existing pgTAP assertion in `12_capture.sql` still literally checked for the string `'Uncategorized'`, unnoticed until now because nothing had exercised that exact `needs_review` subtitle since the `is_default`/"Other" rename three migrations ago — fixed to expect `'Other'`), and `supabase gen types --lang swift --local` byte-for-byte matches the hand-edited `Generated/SupabaseSchema.swift` (mod `internal`→`public`, which every declaration in the committed file already carries as a repo-wide convention, confirmed by normalizing and diffing — zero real difference). One learning worth keeping: `create or replace view` cannot insert a new column mid-list — Postgres reads that as renaming every column after it (`transactions_with_details`'s new `notes` column had to move to the very end, name-based decoding elsewhere makes the reordering invisible to every consumer).

## Update — 2026-08-15 (same day, follow-up): unmapped captures land locally too, plus card-mapping management

Real device testing (Revolut/Burger King, offline) surfaced that item 4 above still had a gap: local-first only covered a card that was *already* mapped. An unmapped card still fell through to a synchronous, network-only RPC call — exactly the network-dependent path local-first exists to avoid — and a transient failure there looked like the purchase vanished with no local trace. Explicit direction: local-first must apply unconditionally; the only real difference for an unmapped card is that the account is missing until the user reviews it, not that the purchase itself is dropped.

**Schema** (`20260822100000_unmapped_capture_lands_locally.sql`): `transactions.account_id`/`currency` are now nullable — but *only* ever null for `status='pending', source='capture'` rows, enforced by two new CHECK constraints (`confirmed_requires_account`/`confirmed_requires_currency`) so a `confirmed` row can never have either null by construction, not convention. Verified this is safe by reading every money-aggregating RPC (`account_balances`, `spending_by_category`, `income_expense_series`, `budget_progress`) — all already filter `status='confirmed'` first, so none needed to change. Added `transactions.card_identifier` (always stored by `capture_transaction` now, used to auto-link the card once an account is finally assigned). Fixed a real, previously-latent gap the pgTAP suite itself caught: `delete_transaction` had the identical `can_write_account(null)` problem `update_transaction` needed fixing too — both now fall back to checking the row's own `owner_id` when `account_id` is null. Also fixed `transactions_select` RLS the same way (`can_read_account(null)` is `false`, which would've hidden a user's own unresolved capture from `pull_changes` and every `security_invoker` view).

**`capture_transaction`** always inserts the transaction now, account/currency simply null when the card lookup finds nothing. **`update_transaction`** auto-links the card to the account the moment a previously-null capture gets one assigned — via a new shared `link_card_to_account` function `map_card` now also calls (de-duplicated, same ledger/active/owned validation either way). **`confirm_capture_transaction`** refuses to confirm a still-unresolved capture with a clear error, backed by the CHECK constraint. `needs_review`'s `ambiguous_card` branch gained a `deleted_at IS NULL` filter (a real, previously-dormant gap — nothing had ever set that column before `unmap_card` below existed) and a `NOT EXISTS` guard against a `pending_capture` already covering the same card, so a fresh unmapped capture produces one Needs Review item, not two.

**Client**: `CaptureLocalWrite.resolveAndWrite` now always writes the pending row as long as the category resolves (still the one hard requirement — the "Other" fallback) — account/currency/`card_identifier` flow through as optional/always-set respectively; `OutboxCaptureResult.appliedLocally`'s account fields became optional to match. `OutboxLocalWrite.updateTransaction` mirrors the server's auto-link locally too (select-then-update-or-insert by `(owner_id, card_identifier)` — the local `card_mappings` table has no unique index over that pair, unlike Postgres, so no `ON CONFLICT` to lean on). `LocalTransactionRow`'s `build()` had a real crash risk here — `row["account_id"]`/`row["currency"]`/`row["minor_unit"]` were being read as non-optional GRDB decodes, which traps on a NULL column value; rewritten to decode all as optional. `fetchOne` (shared by `RootView`'s notification deep-link and `NeedsReviewView.openForReview`) moved from `INNER JOIN accounts` to `LEFT JOIN` with the visibility check restructured into the `WHERE` clause, so a private/inaccessible account still excludes the row while a genuinely-unresolved-but-owned capture is now reachable. `CaptureIntent`'s notification gained a second wording branch — resolved category, no account yet — that still deep-links (a row always exists locally now) with a plain, un-symboled amount (no account means no currency, and money rule 5 says never fabricate a specific value you don't actually know).

**New, additive: manage mapped cards from the Account edit sheet.** A "Mapped Cards" section (`AccountFormView+Cards.swift`) lists every card currently linked to that account (always shown once editing, even empty, so "nothing mapped" reads as a definitive answer, not a missing section); tapping one opens `CardMappingDetailSheet` to rename the card's identifier text or remove the mapping. Two new RPCs, `rename_card_mapping`/`unmap_card`, both owner-scoped by the mapping's own `id` (not the identifier text itself, which rename is busy mutating). `unmap_card` soft-deletes (`deleted_at`) — deliberately not a hard delete (no tombstone for `pull_changes` to ever communicate to an already-synced client) and not an `account_id=null` reset either (that would immediately resurrect the mapping as an `ambiguous_card` Needs Review item, exactly the nagging "remove" is meant to dismiss). Both writes go through the standard `Outbox` local-first pattern (`RenameCardMappingPayload`/`UnmapCardPayload`, `Outbox+Cards.swift`, `OutboxLocalWrite+Cards.swift`) — no exception carved out for this feature.

## Update — 2026-08-17 (same day, follow-up 3): captured transaction's date reverting to "Dec 31" after review

Real bug, found from a live report: a Revolut/DairyQueen capture dated 17 Aug showed under a "Dec 31" section in the Transactions list after being reviewed. Root cause was one shared function, not the review flow itself: `PostgresDate.date(fromTimestamp:)` (`Packages/KeepoCore/Sources/KeepoCore/DateFormatting.swift`) decoded with a bare `ISO8601DateFormatter()`, whose default `.withInternetDateTime` options **exclude fractional seconds** — and both PostgREST's own `timestamptz` rendering and this codebase's own `sqliteTimestampBoundaryString` *always* carry a 6-digit fractional field (confirmed by reading `sqliteTimestampBoundaryString`'s own doc comment). So this decoder has been silently returning `nil` for essentially every real `occurred_at` value coming from either the server or a local-first write — a gap the existing round-trip test never caught because it only ever exercised `timestampString`'s own (fractional-less) output feeding back into the same decoder.

Every one of this function's callers has a `nil`-fallback that quietly ate the failure: `TransactionsListView.groupedByDay` buckets an unparseable row under `Date.distantPast` for its section header — the actual "Dec 31" the user saw (a UTC midnight `.distantPast` instant, shifted a calendar day earlier by a negative-UTC-offset local timezone when only date components render). `TransactionFormView.apply()` silently leaves `occurredAt` at its `Date()` default (today, "now") instead of the transaction's real captured timestamp — meaning any edit-and-save of a captured row was quietly overwriting its true `occurred_at` with the moment of saving, a real (if usually same-day, easy-to-miss) data-loss bug, not just a display glitch. `ConflictDetailSheet+Loading.swift` and `FxRateRepository`'s `asOf` decode share the same exposure.

Fixed at the one shared decode site (per this project's own reuse principle: money/date logic lives in one place, never re-implemented per screen) — `date(fromTimestamp:)` now tries an `ISO8601DateFormatter` configured with `.withFractionalSeconds` first, falling back to the whole-second formatter for `timestampString`'s own (fractional-less) output. No call site needed to change. Added `decodesFractionalSecondTimestamp` to `DateFormattingTests.swift`, asserting both a 6-digit-microsecond PostgREST-shaped string and `sqliteTimestampBoundaryString`'s own output decode correctly — the exact case the prior test suite never covered.

Verification: `swift test` (KeepoCore) 67/67, `xcodebuild -scheme Keepo build` clean, `swiftlint lint` 0 violations, `xcodebuild test -only-testing:KeepoTests` 54/54 (unaffected — no app-target test exercised a real fractional-second string before this).
