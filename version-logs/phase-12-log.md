# Phase 12 — Apple Pay capture & merchant learning

## Delivered

- Migration `20260807150000_capture.sql` (+ same-phase follow-up `20260807160000_ambiguous_card_subtitle.sql`, both already pushed to hosted — see Notes): `card_mappings` (uuid `id` PK, `unique(owner_id, card_identifier)`, composite FK `(account_id, owner_id) → accounts(id, owner_id)`) and `merchant_category_map` (composite FK to `categories(id, owner_id)`), both owner-scoped RLS, never joined into any household-visible view. A system `Uncategorized` expense category (`system_key='uncategorized_expense'`) seeded alongside the existing Adjustment pair — the fallback when a capture has no merchant match.
- `capture_transaction(p_id, p_card_identifier, p_merchant_raw, p_merchant_normalized, p_amount, p_occurred_at, p_external_id)` — the App Intent's one write. Rate-guarded (≥20 captures/minute for one owner raises — a forged or looping automation is a cost-abuse vector, not just a UX bug). Upserts a `card_mappings` placeholder for a never-seen card, then: if unmapped, returns `mapped=false` and writes **no transaction at all** — there is no account to attach a signed amount to yet (amended into `app-architecture.md` §4, which originally implied the row itself gets created either way). If mapped, resolves `merchant_category_map` (filtered to `kind='expense'` — captures are expense-only in v1, no refund/income handling; see Notes) falling back to Uncategorized, and inserts `status='pending', source='capture'` with no `ON CONFLICT` clause — a retried call with the same client-generated id hits `transactions_pkey` (23505), caught client-side exactly like `create_transaction`/`create_transfer` already do, never a duplicate insert.
- `map_card(p_card_identifier, p_account_id)` — resolves an `ambiguous_card` Needs Review item. Refuses a non-ledger, archived, or deleted account (the `account_kind='ledger' OR transfer_group_id IS NOT NULL` CHECK would otherwise reject the next capture on that card with an opaque constraint-violation error instead of a clear one at mapping time).
- `confirm_capture_transaction(p_id, p_expected_version)` — the review step, versioned like every other write. Flips `status` only; field edits (wrong account/category/amount) go through the existing `update_transaction` first — the review screen is `TransactionFormView` in edit mode, not a bespoke capture-review screen, per `app-architecture.md`.
- `needs_review` gains **two** new branches, not three: `pending_capture` (status='pending', source='capture') and `ambiguous_card` (`card_mappings.account_id IS NULL`). **Deviation from the master plan's original wording, recorded there rather than silently:** "low-confidence category suggestions" folds into `pending_capture`'s `subtitle` (`"Uncategorized"` vs `"Suggested: <name>"`) instead of a third `UNION ALL` branch — `merchant_category_map` has no confidence score anywhere in the schema, and every capture already needs a review tap regardless of where its category guess came from; a separate inbox row for the same fact would just be a second notification for one thing.
- `KeepoCore`: `MerchantNormalizer.normalize(_:)` (aggregator prefixes, trailing store number, corporate suffix — looped to a fixed point, see Findings), `CaptureIdentity.externalId(card:amount:merchant:at:)` (SHA-256 via `CryptoKit`, minute-bucketed), `AmountParser.parseFormattedCurrency(_:locale:)` (strips a currency symbol before delegating to the existing parser — the symbol is never used to infer currency, only as a mismatch check per spec), `CaptureRepository` (KeepoCore wrapper for the three RPCs above), `TransactionRepository.fetchOne(id:)` (single-row fetch Needs Review needs for review/confirm), `SupabaseConfig.fromInfoPlist()` (extracted out of `SessionStore.loadConfig()` so `CaptureIntent` reads the same Info.plist keys through the same code, not a second copy).
- `App`: `CaptureIntent: AppIntent` with the trigger's five named parameters (`transaction`, `card`, `merchant`, `amount`, `name` — only `merchant`/`amount` feed the schema). Routes through a **7th `Outbox` operation**: `OutboxKind.captureTransaction` / `TransactionOutboxSending.captureTransaction(_:) -> CaptureResult` / `Outbox.submitCaptureTransaction(_:) -> OutboxCaptureResult`, generalizing the exact seam Phase 11's log anticipated. A capture has no conflict/applied distinction (it's insert-or-noop keyed by `externalId`, not an edit of an existing row), so `OutboxCaptureResult.applied(mapped:)/.queued` carries the one extra bit the intent needs to compose its local-notification text. `OfflineStore.makeContainer()` is now memoized (`NSLock` + `nonisolated(unsafe)` cache) — see Findings. `NeedsReviewView` renders `pending_capture` (tap → fetch → `TransactionFormView` edit; swipe → `confirmCapture`, fetching version first since `needs_review` doesn't carry it) and `ambiguous_card` (tap → `MapCardSheet`, a ledger-account picker calling `map_card`). Settings gained "Set Up Apple Pay Capture" (`WalletAutomationGuideView`, shared verbatim with onboarding's new post-account-creation step) and a `#if DEBUG`-gated "Simulate Capture" screen that calls the exact same `Outbox.submitCaptureTransaction` path `CaptureIntent.perform()` does — the closest the Simulator can get to proving the write path end to end without a physical device and a real Wallet automation.

## Findings

1. **Same-process `ModelContainer` hazard, found before it could bite.** `CaptureIntent` and `SessionStore` both need `OfflineStore`'s SwiftData store, and both run in the same process (the entire reason `CaptureIntent` is declared in the app target and not an extension — Phase 11's log). Two separate `ModelContainer`s each opening their own persistent-store coordinator against the identical SQLite file is a real hazard, not a hypothetical one. Fixed by memoizing `OfflineStore.makeContainer()` (an `NSLock`-guarded static, `nonisolated(unsafe)` since the compiler can't see the manual synchronization) — every caller in the process gets the same container; a `ModelContext` per caller (what `Outbox`/`PayloadCache` already do) stays fine.
2. **`MerchantNormalizer` wasn't idempotent on its first pass**, caught by a dedicated idempotency test before it shipped. A store number and a corporate suffix can appear in either order in a real merchant string ("STORE 00042 LLC" vs "STORE LLC 00042"), and a single linear strip-prefix-then-strip-suffix pass only catches the number when it's genuinely at the string's end *after* the suffix is gone — which it isn't yet, on the first pass, if the suffix comes after the number. Fixed by looping the number-strip and suffix-strip together to a fixed point inside `normalize(_:)`, so the result — and the idempotency property merchant learning depends on (`merchant_category_map` keys off the normalized form) — no longer depends on which piece of noise happens to come first.
3. **Capture is expense-only in v1** — `capture_transaction` filters merchant-map lookups to `kind='expense'` and always inserts a negative amount (`-abs(p_amount)`). Refunds (which would need to post as income, or at least a smaller-magnitude expense) are explicitly out of scope; the feature spec itself lists "whether a refund fires the Wallet trigger and how its amount is signed" as a device-only open question for Phase 20's checklist, not something buildable or testable now.
4. **An unmapped card drops the specific purchase, by design, not as an oversight.** `capture_transaction` cannot insert a transaction without an `account_id` (the column is `not null`, and there's no "unmapped" holding account to invent without adding scope nobody asked for). The first tap on a newly-Wallet-automated card creates only the `card_mappings` placeholder; that specific purchase is never captured, even after the card is mapped afterward. Every subsequent capture on that card succeeds normally. This matches `app-architecture.md`'s own accepted-limitations framing for capture generally (Apple Pay only, on-device only, user-built automation) and is now stated plainly in the doc rather than left implied by "the row is still created."

## Verification

- `supabase test db --local` — 150/150 assertions (130 prior + 20 new in `12_capture.sql`): unmapped-card placeholder + no transaction; `ambiguous_card` appears/disappears around `map_card`; `map_card` refuses a valuation account; a mapped capture is negative/pending/source=capture in the account's currency; merchant-map categorization + its `needs_review` "Suggested:" subtitle; a same-id retry raises `23505`; the per-minute rate guard rejects the next capture once the threshold is reached; `confirm_capture_transaction` flips status and clears the `pending_capture` row; a stale-version confirm logs a `sync_conflicts` row instead; fixture B sees none of fixture A's card mappings, merchant map, or capture-related Needs Review rows. `supabase db push` applied both migrations cleanly to hosted; types regenerated and diffed clean (only the two new tables' generated structs appear).
- `xcodebuild -scheme Keepo build` (simulator destination) — clean. `swiftlint lint --strict` — 0 violations across 49 files. `swift test` (KeepoCore) — 45/45 (20 new: `MerchantNormalizerTests`, `CaptureIdentityTests`, `AmountParserFormattedCurrencyTests`). `xcodebuild test -only-testing:KeepoTests` (headless) — 9/9 (2 new `OutboxTests`: a failed capture send queues then drains on recovery; an unmapped-card capture is delivered, not queued, since `mapped=false` is data, not a failure).
