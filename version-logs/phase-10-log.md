# Phase 10 — Needs Review inbox & transaction filters

## Delivered

- Migration `20260807090000_needs_review.sql`: `needs_review` — a **view**, not a table, with the stable column contract the plan specifies (`kind`, `item_id`, `account_id`, `occurred_at`, `title`, `subtitle`, `amount`, `currency`) — every later phase (12/14/18/19) appends its own `UNION ALL` branch without ever touching the client decoder. Two branches ship here:
  - **`sync_conflict`** — unresolved `sync_conflicts` rows. `account_id` resolves through the polymorphic `table_name`/`row_id` pair (`accounts` → `row_id` directly, `transactions` → a subquery to that transaction's own `account_id`) — `sync_conflicts` has no `account_id` column of its own, being a generic version-mismatch log across both tables.
  - **`reconciliation_gap`** — every non-archived account `accounts_sync_status.is_stale` currently flags. This is deliberately **not** gated by `include_in_total` (unlike Home's banner, Phase 9) — the inbox is meant to be comprehensive; an excluded-from-total account still deserves a reminder to verify, even though it wouldn't move net worth if it were wrong.
  - `resolve_sync_conflict(p_id)` — the only writer of `resolved_at`. Idempotent (`coalesce(resolved_at, now())`): resolving an already-resolved conflict is a no-op, not an error, so a client retry after a dropped connection can't fail on the second attempt. Raises "not found or not accessible" for a nonexistent id or someone else's conflict, never distinguishing the two in the error message.
  - Index `sync_conflicts (owner_id, resolved_at)` — the plan's stated gap (only a PK existed before).
- **Client:** `NeedsReviewRepository` (KeepoCore) — `fetchAll`, `resolveSyncConflict`. `NeedsReviewView` (App) — one `NeedsReviewRow` renderer switching on `item.kind` for icon selection; a `reconciliation_gap` row is a `NavigationLink` into `SyncRitualView` (Phase 9), a `sync_conflict` row gets a swipe-to-resolve action. Added as a **6th tab with a badge** (`RootView`) — the plan's own wording for this phase ("inbox screen, tab badge") is more specific than Phase 7/9's screens (Household, Sync Ritual), which were deliberately *not* given tabs; followed the plan's literal instruction here rather than defaulting to the "reached from Settings/Home" precedent.
- `needs_review`'s stable contract has no `minor_unit` column (not part of the plan's stated 8-column list) — `NeedsReviewRow` instead fetches `currencies` once via the existing `CurrencyRepository` and builds a local `[String: Int]` lookup, the same "reuse before writing" call as everywhere else money needs its minor unit, rather than widening the view's contract for one row's formatting.
- **Transaction filters** (`TransactionRepository.fetchFiltered`, moved into its own `TransactionFilter.swift` alongside `TransactionFilter` itself — `Repositories.swift` was about to cross the 400-line SwiftLint ceiling, so this followed the same split precedent as `AccountWrites.swift`/`TransactionWrites.swift` rather than suppressing the rule): account/category/kind/date-range, every field optional and AND'd together, `search` matching merchant/category/account name via `ilike`. Ordering is unchanged from `fetchAll` (`occurred_at desc`, now with `transaction_id desc` as an explicit tie-break) — filtering narrows which rows qualify, never the sort, so it rides the existing `(owner_id, occurred_at desc, id desc)` keyset index rather than fighting it. `TransactionsListView` gained `.searchable` (bound to `filter.search`) and a filter sheet (`TransactionFilterView`) for the other four fields; a full cursor-based pagination UI was **not** built — the plan's "riding the existing keyset index" reads as an ordering/performance constraint on the filters, not a mandate for infinite scroll, and no other part of the spec's Transactions screen description asks for one.

## Notes for the next phase

- The `reconciliation_gap` branch currently has no per-item "dismiss" — closing it requires actually reconciling the account (via `SyncRitualView`), which is correct behavior (the point is to fix the staleness, not hide it) but means there's no swipe action on that row type, unlike `sync_conflict`'s "Resolve." Worth remembering if a future review of the inbox UX wants every row to feel equally actionable.
- `needs_review`'s two branches both already tolerate RLS correctly by construction — `sync_conflicts_select` is `owner_id = auth.uid()` (no household clause, by design: a version conflict is inherently the conflicting writer's own problem to resolve) and `accounts_sync_status` inherits `can_read_account`'s household-aware visibility. No new RLS surface was added by this migration; the view just composes two already-correct sources.
- Phase 12/14/18/19, whichever lands first, is the first real test of the "stable column contract" promise — each should be able to add its own `UNION ALL` branch to `needs_review` and a `case` to `NeedsReviewRow`'s icon switch without touching `NeedsReviewRepository`, `NeedsReviewSelect`, or the view's rendering logic at all. If any of those needs to change, the contract wasn't as stable as intended and is worth revisiting rather than patching around.
