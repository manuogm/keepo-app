# Lessons Learned — read before starting a new phase

Consolidated from Phases 1–11. Environment quirks, framework gotchas, and footguns already hit — don't repeat them.

Phase 1 and 2's logs here are reconstructed from `app-architecture.md`'s inline defect history, commit bodies, and old plan files — good enough, but written after the fact. ## Postgres / Supabase

- **`SECURITY DEFINER`, not `INVOKER`, for any function that re-queries the table its own RLS policy is attached to** — `INVOKER` recurses infinitely through the policy. But `SECURITY DEFINER` self-reference has its own trap: it breaks `INSERT ... RETURNING` for a row written earlier in the *same command* (confirmed empirically, Phase 2). `accounts`' own `SELECT`/`UPDATE` policies inline `owner_id = auth.uid()` instead of calling the shared predicate, as the one accepted exception.
- **Supabase's local cluster grants `TRUNCATE`/`REFERENCES`/`TRIGGER`/`MAINTAIN` to `anon`/`authenticated` by default** (`pg_default_acl`) — `TRUNCATE` bypasses RLS. Revoke schema-wide with `ALTER DEFAULT PRIVILEGES ... REVOKE` before the first `CREATE TABLE`.
- **A raised exception aborts the entire enclosing transaction — including any audit-row insert that happened earlier in the same function call.** An RPC call from a client is one top-level statement. If a function needs to log something *and* signal a recoverable condition (a version conflict, say), return the signal as data (`conflict boolean`), don't raise — raising is only for genuine errors with nothing worth persisting.
- **`SELECT (some_function(...)).*` invokes a composite-returning function once per output column**, not once. Use `SELECT * FROM some_function(...)` in the FROM clause instead — this bit SQL test-writing in Phase 3 and looked exactly like a real conflict-detection bug until isolated.
- **`CREATE OR REPLACE VIEW` can add a column only at the end of the SELECT list**, never in the middle — "cannot change name of view column X to Y" if you try to insert one earlier.
- **`numeric`/`timestamptz` function return types under `SET search_path = ''` need explicit `public.` qualification** — `RETURNS transactions` fails with "type does not exist"; `RETURNS public.transactions` is required, same for `DECLARE v_result transactions;` → `public.transactions`.
- **PostgREST named-parameter RPC calls require every non-defaulted parameter to be present in the JSON body.** Swift's synthesized `Encodable` uses `encodeIfPresent` for `Optional` fields, silently omitting `nil` ones from the payload — not sending `null`. Any RPC parameter a Swift client might send as `nil` needs `default null` (or another default) on the Postgres side, or the call fails with `PGRST202` every time that field is nil. `create_transfer`'s `p_to_amount`/`p_occurred_at` already did this; `update_transaction`'s `p_merchant_raw` didn't, and broke on the very first real (non-SQL-test) call.
- **After `supabase db reset`, PostgREST's schema cache sometimes needs an explicit nudge**: `NOTIFY pgrst, 'reload schema';` in psql. It usually reloads automatically, but don't assume it did if a freshly-added RPC comes back "could not find the function."
- **`supabase gen types --local --lang swift` changed its default access level to `internal`** somewhere around CLI v2.100+ (this codebase was built against an older default of `public`). Pass `--swift-access-control public` explicitly every time — the codebase's whole cross-module (`KeepoCore` → `App`) design depends on it, and the failure mode (types silently `internal`) is a build error in the consuming target, not a warning.
- **A conditional `ON CONFLICT ... DO UPDATE ... WHERE`** (Phase 4's "later `fetched_at` wins" rule for `fx_rates`) works exactly as documented — the `WHERE` clause runs against `EXCLUDED` vs. the existing row, and a false result leaves the existing row untouched (not a delete, not an error). Confirmed empirically: calling with an earlier `fetched_at` than what's stored is silently a no-op, not "last write wins." Useful pattern for any future upsert that needs a monotonic guard PostgREST's own `Prefer: resolution=merge-duplicates` can't express.
- **Under `SET search_path = ''`, an unqualified call to another function in `public` fails even inside a `RETURN QUERY`'s embedded SQL, not just in top-level statement bodies** (Phase 8, `net_worth_series` calling `fx_convert` unqualified inside its `RETURN QUERY select ...`). The error ("function fx_convert(...) does not exist") only appears at *call* time, not at `CREATE FUNCTION` time — Postgres doesn't validate the body's function references until it actually runs, so this survives a clean migration apply and only surfaces the first time the function is actually invoked (in this case, by its own pgTAP test). Schema-qualify every function call inside a `search_path = ''` function's body, including ones nested inside `RETURN QUERY`, `CASE`, or aggregate expressions — not just the "top-level" calls that are easiest to spot on review.

## pgTAP (Phase 5)

- **`supabase test db` globs every `.sql` file in the target directory as a standalone test file** — a shared-setup file with no `plan()`/`finish()` gets run anyway, and because it has no `BEGIN`/`ROLLBACK` of its own, anything in it (an extension, fixture inserts) **commits for real** to the persistent database. Name shared-setup files with a non-`.sql` extension (`_helpers.psql`) and `\ir` them from each real test file, rather than relying on a naming convention the CLI doesn't actually enforce.
- **`SET LOCAL ROLE` cannot be issued from inside any PL/pgSQL function body — `SECURITY DEFINER` included.** Postgres rejects it outright ("cannot set parameter 'role' within security-definer function"). There is no tidy `as_user(uuid)` wrapper; role-switching is three plain top-level statements at every call site (`set local role authenticated; select set_config('request.jwt.claim.sub', '<uuid>', true);` / `reset role;`).
- **`now()` is frozen for the whole enclosing transaction, and a whole pgTAP test file IS one transaction.** Two rows inserted in the same file with default `now()`-derived timestamp columns get the *identical* value, not "a moment apart" — this can silently flip a `>` comparison that would never tie in real usage (two separate client calls, two separate transactions each with their own `now()`). Use `clock_timestamp() - interval '...'` for an explicit, provably-ordered timestamp when a test needs one.
- **A `DEFERRABLE INITIALLY DEFERRED` constraint's violation survives past `throws_ok`'s own internal savepoint.** `throws_ok` only rolls back the statement that forces the check (`SET CONSTRAINTS ALL IMMEDIATE`); the earlier statement that actually violates the deferred constraint is untouched and its violation stays pending, ready to fire again — and corrupt an unrelated assertion — the next time anything forces constraints immediate in the same file. Wrap both the insert and the immediate-check in your own explicit `SAVEPOINT` and roll back to it manually afterward.
- **pgTAP's `throws_ok` never takes a free-text description as an argument after `sql` in its 2-/3-arg forms** — every such argument is matched against the actual error itself (a 5-character string dispatches as an expected SQLSTATE; anything else is matched as the exact expected message, confirmed against the installed `pgtap--1.3.1.sql`). To pin a SQLSTATE while leaving the message unchecked and still supply a real description, use the 4-arg form explicitly: `throws_ok(sql, '23514', null, 'a friendly description')`.
- **`supabase gen types --linked`'s temporary introspection role can run DDL (`db push`, `migration list`) but returns empty structs for every table/view column** — enums come through fine, tables/views don't, with no error and no CLI flag to point it at a different role. Treat `--local` as the only reliable source for the committed generated types; a hosted-vs-local diff isn't currently possible in this environment.
- **A `DEFERRABLE INITIALLY DEFERRED` trigger simply never fires inside a whole-file pgTAP test, full stop — not "fires late," never fires at all** (Phase 7, testing `check_transfer_integrity`'s relaxed household rule). The entire test file is one transaction that always rolls back; a deferred constraint only runs at `COMMIT`, which never happens. Without an explicit `SET CONSTRAINTS ALL IMMEDIATE;` right after the statement that should trip it, the assertion that follows passes **vacuously** — it would pass identically whether or not the SQL being tested is even correct, because the trigger it's supposedly exercising never ran. Any test of a deferred constraint/trigger needs this line, not just tests of the *violation* case (gotcha #2 above already covers that half); the *success* case needs it too, or nothing was actually tested.
- **A committed `seed.sql` and the pgTAP suite's own fixture users can silently collide on identity** (Phase 8 — `seed.sql` and `_helpers.psql` had used the *same* two user ids since Phase 5, despite `_helpers.psql`'s own header comment claiming otherwise). Invisible for two whole phases because no test aggregated "everything a fixture user owns" until `net_worth_series` did — a test that sums per-account rows never notices extra accounts belonging to the "same" user from a different file. Any new cross-account aggregate RPC's first pgTAP file should double-check its fixture users' account counts against what the test itself inserted, once, before trusting a sum.

## Hosted Supabase (Phase 5)

- **Hosted GoTrue's email validator rejects the `.test` TLD** (`email_address_invalid`) that the local stack accepts without complaint. Use `.dev` or a real-looking domain for any hosted-only fixture identity.
- **Hosted projects require email confirmation by default; the local stack doesn't** — a fresh `signUp` + immediate `signIn` (the exact pattern `StubAuthProvider`/`PasswordAuthProvider` both use) gets `invalid_credentials` against hosted until the email is confirmed. Don't disable email confirmation project-wide to work around this (a real, persistent security-policy change) — provision the fixture identity directly via the Admin API instead: `POST /auth/v1/admin/users` with `email_confirm: true`, using the `service_role` key.

## SwiftUI / client architecture

- **`ISO8601DateFormatter` renders in UTC by default.** Building a `date`-only column (no time component) by taking `.string(from:)`'s output and slicing the first 10 characters silently produces the *UTC* calendar day, not the device's local day — wrong for any user within a few hours of UTC midnight, wrong direction depending on which side of midnight they're on. Format `date`-only columns with a `DateFormatter` carrying the device's actual `Calendar`/`TimeZone`, never by truncating a timestamp string (Phase 6, `PostgresDate.dateOnlyString`).
- **`@Observable` requires macOS 14+, but a Swift package's `platforms:` floor for `swift build`/`swift test` on the host Mac is independent of its iOS floor.** A type only ever consumed by the App target (no other file in the package needs it) that happens to use `@Observable` will fail `swift test` if the package's macOS floor is below 14, even though the App target itself builds fine against iOS 18. Either bump the package's macOS floor or — simpler, if the type has zero dependencies on the rest of the package — just put it in the App target instead of the shared package (Phase 6: `RefreshCoordinator`/`DataStore`).

## iOS Simulator / dev loop

- **`xcrun simctl uninstall` does not reliably clear Keychain items on the Simulator** — a stale cached Supabase Auth session survives app uninstall/reinstall, so testing "fresh sign-up" after a `supabase db reset` (which wipes `auth.users`) needs `xcrun simctl erase <device>` (full device erase), not just uninstall/reinstall. Symptom: `PostgrestError PGRST116 "Cannot coerce the result to a single JSON object"` on the very first profile fetch, because the cached session belongs to a user that no longer exists.
- Simulator tap/text input can lag by a full screenshot cycle, and text fields sometimes don't show a visible cursor/keyboard even when focused and accepting input — verify by screenshotting after the *next* action, not just immediately after a tap.
- **The Simulator MCP tool's tap/swipe coordinates are device points, not screenshot pixels** — screenshots in this environment render at roughly 2.284x scale (e.g. a 402pt-wide device produces an ~918px-wide image). Feeding raw pixel coordinates read off a screenshot straight into `tap`/`swipe` produces wrong, usually off-target or off-screen, taps that fail silently (no error, just nothing happens). Always divide screenshot pixel coordinates by the scale factor before calling `tap`/`swipe` — or better, cross-check against the tool's own stated "coordinate space" (e.g. "402x874 points") in its response.
- **SwiftUI's `.task {}` fires once per view identity, not once per appearance** — switching `TabView` tabs does not retrigger it if the tab's view instance is kept alive across the switch (no `NavigationStack` pop, no `.id()` change). **Fixed in Phase 6**: every list screen now uses `.task(id: session.refresh.token) { await load() }`, and every write site bumps that shared token — see `RefreshCoordinator` in `App/RefreshCoordinator.swift`. Any new list screen should follow this pattern from the start rather than a bare `.task {}`.
- **XcodeGen must be re-run (`xcodegen generate`) after adding a new source file**, not just after editing `project.yml` — a new `.swift` file dropped into an already-`sources:`-included directory (like `App/`) doesn't automatically appear in the generated `.xcodeproj`'s build phase; `xcodebuild` fails with "cannot find X in scope" until `xcodegen generate` re-syncs file references.
- **The Simulator MCP tool's scripted `swipe` cannot trigger the app switcher** (Phase 8, testing the app-switcher privacy curtain) — a real switcher invocation is "swipe up from the bottom edge *and hold*"; a scripted swipe (any start point, speed, or edge distance tried) completes as a plain "swipe up to home," landing on the home screen instead of the switcher preview. There is no reliable way found so far to script the hold. Verify switcher-dependent UI (privacy curtains, snapshot obscuring) by code inspection of the `scenePhase`/lifecycle logic instead of a captured screenshot, and say so explicitly rather than claiming a visual confirmation that didn't happen.
- **The Simulator MCP tool's typed text is unreliable for anything beyond short, simple strings** — characters get dropped or garbled mid-string, and QuickType/autocomplete can silently substitute a different word than what was typed (confirmed Phase 6: typing " Account" after existing text produced "Invests - No balance" in the field instead). Taps immediately after a keyboard-triggered layout shift (e.g. right after typing, before the keyboard fully dismisses) can also land on the wrong element. Never trust simulator-typed text as a record of *what was typed* — only verify that *some* value round-tripped correctly, and cross-check actual state via `supabase db query --local <<< 'select ...'` when a screenshot's contents look surprising.

## Optional RPC parameters (Phase 9)

- **A `uuid`-typed optional RPC parameter needs `default null` just as much as a string/number one does — and is easier to forget.** Swift's synthesized `Encodable` for an `Optional` property uses `encodeIfPresent`, so a `nil` value omits the JSON key from the RPC call entirely rather than sending `null`; PostgREST then returns `PGRST202` if the SQL function has no default for that parameter. This is the same PGRST202 lesson already documented for every other optional parameter in this codebase, but a `uuid` param reads as "obviously required" at a glance in a way an optional string doesn't — worth a specific second look on any new RPC parameter typed `uuid` that a caller can legitimately omit (Phase 9: `reconcile_ledger_account`/`reconcile_valuation_account`'s `p_expected_last_reconciliation_id`, `null` on a never-reconciled account's first call).
- **Once a migration has been pushed to hosted, fix a bug in it with a new, additive migration — even within the same still-uncommitted phase.** The established precedent (Phase 1→2, correcting `accounts_select`) is about hosted state, not git history: the moment `supabase db push` has run against the linked project, editing the already-applied file and re-running `db reset` only fixes *local*. Hosted needs its own follow-up (`create or replace function ...`) or, if the migration truly must be edited in place, `supabase migration repair --status reverted <version> --linked` followed by manually re-running the corrected DDL — repair alone only touches the tracking table, not the actual database objects.

## Cross-schema view design (Phase 10)

- **A view's "stable column contract" (documented so later phases can each append a `UNION ALL` branch without touching the client) is worth being strict about, including what it deliberately leaves out.** `needs_review`'s 8 columns don't include `minor_unit` — adding it would have made money formatting one line simpler in `NeedsReviewRow`, but would also mean every future branch has to carry it too, growing the "stable" contract by accretion. Fetching `currencies` once and building a local `[code: minorUnit]` lookup client-side (already-established `CurrencyRepository`) kept the view's contract exactly as documented. When a view's contract is written down as an explicit list, treat "just one more column" requests from the client side with real suspicion.
- **A `SwiftLint` file-length violation from adding one new method to an existing repository file is a signal to split, not to suppress.** `Repositories.swift` crossed 400 lines from `TransactionRepository.fetchFiltered`'s addition alone; moved it and its supporting `TransactionFilter` struct into their own `TransactionFilter.swift`, following the same precedent `AccountWrites.swift`/`TransactionWrites.swift` already established for exactly this situation (a repository's *write* surface split out from its *read* surface once either grew enough to justify its own file).

## SwiftData / offline outbox (Phase 11)

- **`SwiftData`'s `@Model` types hit the identical macOS-floor wall `@Observable` did in Phase 6.** `KeepoCore`'s `Package.swift` still floors at macOS 13 for `supabase-swift` compatibility; SwiftData needs macOS 14. Same fix as before — put the models (`OfflineStore.swift`, `Outbox.swift`) in the App target, not the shared package, rather than bumping the package's platform floor. Worth checking for *any* newer SwiftUI/Observation-framework-adjacent API before reaching for KeepoCore: if it's iOS 17+/macOS 14+, it almost certainly can't live in the package as currently configured.
- **A write path that generates its own id server-side, instead of accepting a client-supplied one, is the one thing standing between "idempotent for free" and a silent duplicate.** Found by actually asking, for every existing write, "what happens if the outbox sends this exact call twice" — `create_transfer` was the only one that failed the question (`TransactionRepository.create` already took a client id in spirit, just didn't expose the parameter). Worth asking explicitly for every *new* write path added from here on, not just assumed from "most things already have client ids."
- **A duplicate-key error (Postgres `23505`) on a retried insert is the correct, desired outcome for an idempotent write, not a bug to route around.** The client-side handling is to catch that specific error code and treat it as success ("already applied"), never to avoid triggering it. `PostgrestError.code` (a bare `String?`) is what carries the SQLSTATE through `supabase-swift` — check that field, not the error message text, which isn't guaranteed stable.
- **A generic `Codable` constraint added to an existing generic type (`DataStore<Item>`) is free when every real usage already conforms** — every generated `PublicSchema.*Select` type already derives `Codable`, so adding `Item: Codable` to `DataStore` for Phase 11's persist/restore needed zero call-site changes. Worth checking for this kind of free retrofit before assuming a generic type needs a parallel/wrapper type instead.
- **Running `xcodebuild test` to execute an XCTest/Swift Testing bundle is not the same as interactively using the Simulator app.** It boots a simulator process headlessly to host the test runner; no visual window, no screenshot/tap interaction. When simulator *use* is paused (e.g. by explicit user request, pending a joint walkthrough), automated `xcodebuild test` runs — which several phases' own Verify sections call for — are still the right way to execute a unit-test suite; only the interactive, visual walkthrough is what's actually being deferred.

## Offline verification (Phase 11 live walkthrough)

- **`NSFileProtectionCompleteUnlessOpen` doesn't even read back on the iOS Simulator — it's not just unenforced.** `FileManager.setAttributes([.protectionKey: ...])` returns success on Simulator, but a subsequent `attributesOfItem` read on the exact same path comes back `nil` every time (confirmed by running the identical call in a plain host-Mac `swift` script, where it round-trips correctly). The Simulator has no data-protection subsystem at all, not even as unenforced metadata. Don't write a test that asserts the attribute *value* on Simulator — assert only that the call completes without throwing; the actual read-back and enforcement both need a physical device.
- **To simulate "offline" for an app whose backend is a local Supabase stack, stop the API container (`docker stop supabase_kong_<project>`), not the Simulator's network/Airplane Mode.** The app talks to `127.0.0.1`, which is loopback traffic — Airplane Mode (a radio-layer toggle) doesn't touch it at all. Stopping Kong (the gateway all REST/RPC calls go through) reproduces a genuine "server unreachable" `NSURLErrorCannotConnectToHost` deterministically, restartable with `docker start` the instant the test needs connectivity back.
- **`String(describing: error)` on a bridged `NSError` prints the *entire* `debugDescription`, including every nested `userInfo` entry** — a plain "could not connect to the server" surfaced as a dozen lines of `_NSURLErrorFailingURLSessionTaskErrorKey`/nested-CFNetwork-error text filling the screen, only found by actually triggering the error live (not visible from reading the code — `errorMessage = String(describing: error)` looks completely reasonable in isolation). `error.localizedDescription` is dramatically shorter for the exact same error and is what any user-facing error label should use instead; reserve `String(describing:)` for logs/diagnostics never shown on screen.
- **Scripted `swipe`/`touch_path` gestures did not reliably trigger SwiftUI `List`'s `.swipeActions`/`.onDelete` reveal in this environment**, joining the already-documented app-switcher-gesture limitation as a category of gesture the Simulator MCP tool's scripted input can't reliably reproduce. When a scripted gesture doesn't visibly do anything after several genuinely different attempts (varying start/end points, speed, path curvature), verify the underlying mechanism a different way (direct SQL/file inspection of what the write actually produced) rather than concluding the feature is broken — in this case the user performed the same gesture manually within seconds, confirming the gesture itself was the obstacle, not the code.
- **A live walkthrough surfaces UX gaps invisible in code review** — three of Phase 11's real findings (offline pickers with nothing to pick, a wall of raw `NSError` text, a swiped-away conflict with no way to know what it was) were only found by actually using the built feature end-to-end, not by reading the diff. Budget for this kind of pass, don't treat "it compiles and the unit tests pass" as equivalent to "it's usable."

## Money-rule-adjacent

- `merchant_raw`/`merchant_normalized` are capture-only fields (Phase 12, per the current roadmap — renumbered from an earlier plan draft's Phase 8) — the manual entry/edit form must never show them. On edit, pass the existing value through unchanged rather than exposing an edit control for it.
- A form field that isn't shown in the UI but whose backing column has no explicit default (like `occurred_at`) will silently take `Date()` on every save unless the client explicitly threads through the original value — worth checking for on every "add editing to an existing create-only form" task, not just this one.

## Apple Pay capture (Phase 12)

- **A normalization function that strips multiple kinds of noise in a fixed linear order isn't automatically idempotent — verify it with an explicit idempotency test, don't assume it.** `MerchantNormalizer` strips an aggregator prefix, a trailing store number, and a corporate suffix; a real merchant string can carry the store number and the suffix in either relative order ("STORE 00042 LLC" vs "STORE LLC 00042"), and stripping the number before checking for a suffix only works when the number is genuinely at the string's end *after* the suffix is already gone. A single linear pass silently produces different output depending on ordering; writing `normalize(normalize(x)) == normalize(x)` as an actual test (not just eyeballing a few examples) caught it before merchant-map lookups could quietly miss matches. The fix — loop the noise-stripping steps to a fixed point — generalizes: any normalizer stripping more than one *independent* kind of noise should get an idempotency test as a matter of course, since composability bugs like this don't show up from single-example unit tests.
- **When two call sites in the same process both need `OfflineStore`'s `ModelContainer`, memoize it — don't assume a second `ModelContainer` pointed at the identical SQLite file is harmless just because SwiftData "handles" the file.** `CaptureIntent` (app target, not an extension, specifically so it can reach this store) and `SessionStore` both call `OfflineStore.makeContainer()`; two separate containers each opening their own persistent-store coordinator against one file is a same-process hazard, not a hypothetical one from over-caution. A `NSLock`-guarded static cache (with `nonisolated(unsafe)` on the cached value, since Swift 6 strict concurrency can't see the manual synchronization) fixes it once, for every future same-process caller — this is the kind of fix worth doing proactively the moment a second caller appears, not reactively after a corruption report.
- **An App Intent declared in the app target (not an extension) shares the process's persisted Supabase session automatically — no explicit session hand-off code needed.** Building a fresh `SupabaseClient` from the same `SupabaseURL`/`SupabaseAnonKey` inside `CaptureIntent.perform()` picks up whatever session `supabase-swift`'s local storage (Keychain by default) already has from the last interactive sign-in, the same way relaunching the app itself does. If no session exists (never signed in, or signed out), the capture's network call fails with an auth error like any other unauthenticated request — which the outbox already treats as "queue it," so a capture that fires before first sign-in isn't lost, just delayed until the next successful drain after sign-in. Don't build a separate "does the Intent have a session" check; the existing offline-queue path already covers it.
- **A protocol method returning a plain `Bool` (applied/conflict) doesn't fit every write shape — don't force one on that doesn't have a real conflict concept.** Every existing `Outbox` write (`updateTransaction`, `deleteTransaction`, ...) is a version-checked edit, so `Bool` (applied vs. conflict) was the right shared shape. A capture is an insert-or-noop with no version to conflict against; forcing it through the same `Bool` return would have thrown away the one piece of information (`mapped`) the caller actually needs. Added a dedicated `OutboxCaptureResult` enum instead of stretching the existing one — a second, genuinely different write shape is exactly the signal to add a second result type, not to overload the first one's meaning.

## First real-device run (post-Phase-19, user's own iPhone)

- **iOS hard-crashes, rather than returning an error, the first time any code path touches a Face ID-gated Keychain item without `NSFaceIDUsageDescription` in Info.plist.** `KeychainSessionStorage.retrieve(key:prompt:)`'s `SecItemCopyMatching` call (the one that attaches an `LAContext` for the biometric ACL evaluation) was the trigger — crash message was exactly "attempted to access privacy sensitive data without a usage description," pointing at that line. This was invisible through every check this project ran before a real device existed: the Simulator has no biometric hardware to gate against, so `StubAuthProvider`'s local-dev path (the only path ever exercised pre-device) never calls into this code at all, and even `PasswordAuthProvider`/`KeychainSessionStorage`'s own unit tests (Phase 17) could only exercise the retrieve-miss path (`errSecMissingEntitlement` blocks writes from a plain `swift test` binary — see that phase's own findings), never a real biometric-gated read. Fixed by adding the usage-description key to `App/Info.plist`. **General lesson: any `NSSomethingUsageDescription` key (Face ID, camera, location, contacts, ...) is invisible to every pre-device check this project's tooling can run — `xcodebuild build`, `swift test`, `xcodebuild test`, and the Simulator all silently tolerate its absence until the exact API is hit on hardware with the real subsystem behind it.** Worth an explicit grep for every `LAContext`/`kSecUseAuthenticationContext`/`AVCaptureDevice`/`CLLocationManager`-style API already in the codebase against Info.plist's usage-description keys before the *next* first-real-device milestone, rather than waiting to hit each one via a crash report.
- **A build that silently used the wrong `.xcconfig`** (Debug's `127.0.0.1` instead of Release's hosted URL, diagnosed from the exact same crash log's network-layer noise) is a distinct, unrelated failure mode from the Face ID crash above, surfaced in the same session — worth remembering that a single device run can turn up more than one independent, first-time-only class of bug, and to diagnose each symptom on its own rather than assuming one fix explains everything in the log.
- **Storing the session `supabase-swift` uses as its bearer token behind a biometric `SecAccessControl` is a design bug, not a hardening measure — it re-triggers Face ID on every single authenticated request, not just at login.** This is the real root cause behind the Info.plist fix above only getting the app to a *new*, worse symptom: once the crash was fixed and Face ID could actually run, the app entered a visible loop of repeated Face ID prompts and never reached onboarding. The reason: `supabase-swift` reads the locally stored session before attaching the Authorization header to *every* PostgREST/RPC call, not only at sign-in — `SessionStore.start()` alone makes several such calls in sequence (`restoreSession()`, the profile fetch, the outbox drain), each independently re-triggering the biometric prompt on a session item protected by `.biometryCurrentSet`. A clean delete+reinstall didn't fix it (correctly ruling out stale state) because the bug is structural, not data-dependent. This was invisible through every check this project could run before real hardware existed — the Simulator has no biometric hardware to gate against at all — and the unit tests for `KeychainSessionStorage`/`StepUpAuthenticator` (Phase 17) could only exercise the retrieve-*miss* path (`errSecMissingEntitlement` blocks real writes from a plain `swift test` binary), never a real biometric-gated read succeeding and being reused. **Fix:** decouple "the session used for ordinary API calls" from "step-up assurance" entirely — `KeychainSessionStorage` now stores the session under a plain (non-biometric) `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` ACL, and `StepUpAuthenticator` is a standalone `LAContext.evaluatePolicy(.deviceOwnerAuthenticationWithBiometrics)` call with zero coupling to where or how the session itself is stored. **General lesson: never gate a token/credential *read path that fires on every request* behind a user-presence check — biometric gating belongs on a specific, deliberate action (export, delete, step-up), never smuggled in via the storage layer underneath routine reads.** This is also a strong argument for getting to a real device with the target biometric hardware as early as physically possible in any project using `LAContext`/biometric-gated Keychain items — this exact class of bug is structurally unreachable from Simulator-only testing, no matter how thorough.

## Offline capability audit & category delete fix (post-Phase-19, user's own device testing)

- **A cache-fallback read is only correct if the cache actually holds the shape the caller needs.** `AccountFormView`'s edit sheet needed `AccountsSelect.openingBalance` (the raw stored column), but the only cache already populated for accounts (`accounts_with_balances`, written by the list screen) exposes the computed running `balance` instead — reusing it would have silently substituted a running balance into the opening-balance field, and saving without noticing would have overwritten the real opening balance with the current balance. Fixed with a dedicated per-account cache (`AccountFormCache`, keyed `"account:\(id)"`, written on every successful `fetchOne`) rather than repurposing the list's cache. **General lesson: before wiring any screen's read to an existing cache key, check field-for-field that the cached shape actually matches what that screen decodes — "there's already a cache for this table" is not the same as "there's already a cache for this query."**
- **A read that has a cache/offline fallback needs its own short timeout, or the fallback is technically correct but practically useless.** `TransactionFormView`/`AccountFormView` both already had `try? await ... ?? fallback` fallback logic, but with no custom `URLSessionConfiguration` on the Supabase client, the "try" side waits out the *default* request timeout (well beyond what feels instant) before ever reaching the fallback. Added a generic `withTimeout(seconds:operation:)` (race against `Task.sleep`, `withThrowingTaskGroup`) and wrapped every fallback-eligible read in it — never wrapped around a write, since abandoning a write client-side after a race leaves the caller unsure whether it actually landed server-side.
- **A working delete swipe-action gate is not the same as a working delete.** The category swipe action checked `!category.isDefault` only, missing `systemKey != nil` (the "Adjustment" system category) — so the one category type most likely to be swiped-on in early testing was exactly the one the DB was guaranteed to reject, producing "this category cannot be deleted" regardless of whether the underlying feature worked at all. Always check *every* condition a DB-side guard enforces against the client-side gate meant to pre-empt it, not just the one that happens to be named `is_default`.
- **A soft-delete that works at the DB layer can still be a visible no-op at the UI layer if nothing filters `deleted_at` on read.** Building `delete_category_and_reassign` (the first time category deletion could actually succeed end-to-end) surfaced a latent bug that had never once been exercised: `CategoryRepository.fetchAll()` had no `deleted_at is null` filter anywhere — not in `categories_select`'s RLS (which deliberately allows reading soft-deleted rows, same as `accounts_select`/`transactions_select`), and not in the query itself. `accounts` has the equivalent filter centralized in the `account_balances` view's own `where a.deleted_at is null`; categories have no view of their own, so the filter has to live on the query directly. **General lesson: RLS policies in this schema intentionally allow reading soft-deleted rows (history/detail views may need them) — the "hide it from ordinary lists" filter is always the *query's* job, not the policy's, and a table's list-fetching function needs to be checked for this explicitly rather than assumed from the policy.**
- **Any delete/archive that depends on a live server-side check (e.g. "does this still have transactions?") should never be routed through an offline write queue.** Queuing it would mean the confirmation the user sees is built from a stale or absent count, and the operation executes later, unsupervised, based on a decision made without the real number. Account and category delete/archive were deliberately kept online-only for this reason (they simply fail with the existing "you appear to be offline" message rather than queuing) while their create/edit siblings — which have no such live dependency — were extended into the outbox alongside transactions.

## pg_net and error-message filtering (base-currency-change crash, real-device report)

- **"Preloaded/installed already" (Phase 13's own words about `pg_net`) was true locally, never verified against the actual linked hosted project.** Changing base currency raised `schema "net" does not exist` — `supabase db query --linked` against `pg_extension` showed the hosted project has no `pg_net` at all (only `supabase_vault`/`pg_cron`), while locally it's preinstalled by the CLI's Docker image. Fixed with a plain `create extension if not exists pg_net;` (migration `20260812110000_pg_net_schema_fix.sql`) — deliberately no `schema` clause: pg_net's own install script creates its `net` schema and every `net.*` function as a member of the extension regardless of which schema the *extension* object nominally registers under (confirmed empirically — forcing a schema move with `alter extension ... set schema` fails outright with "the extension contains the schema"). **General lesson: "this extension is preinstalled on Supabase" is an assumption to verify per-project with `supabase db query --linked`, not something to infer from local behavior — this project's own linked instance was the exception.**
- **The real bug wasn't the missing extension — it was that `UserFacingError.describe` had no way to distinguish an intentional, human-readable RPC message from an engine-internal one, so it showed both verbatim.** Every screen in this codebase already routed every error through `UserFacingError.describe` correctly (audited: every `catch` block, zero exceptions) — the gap was inside that one function itself, which fell back to `error.localizedDescription` for anything that wasn't a recognized offline error. For `PostgrestError`, that's just the raw `message` field, so a leaked engine error (missing schema, undefined column, permission denied, ...) was shown to the user exactly as Postgres phrased it internally. Fixed by checking `PostgrestError.code == "P0001"` — Postgres's default SQLSTATE for a plain `raise exception '...'` with no explicit ERRCODE, which is how every single RPC in this schema raises a message actually meant for a human (confirmed by grep: zero uses of a custom `errcode`/`sqlstate` anywhere in `supabase/migrations/`) — and only showing the message verbatim in that one case; everything else gets a generic "Something went wrong" plus an `os.Logger` line for local debugging. **General lesson: a shared error-filtering function is exactly the kind of single point of failure that needs its own test suite (see `UserFacingErrorTests.swift`) — every call site can be individually correct and the leak still happens once, centrally, if the shared function's own fallback is too permissive.**

## Categories redesign — icon/color tiles, delete-in-sheet, global UI conventions

- **Moving delete from a `List` row's swipe action into the edit sheet wasn't a design compromise, it was forced by the layout change.** `swipeActions` only exists on `List` rows; once categories became `LazyVGrid` tiles (icon+color, per this request), there was no swipe gesture to hang delete off any more. Consolidating the existing count-check-then-confirm flow (built for the swipe action, see the delete-reassign work above) into `CategoryFormView`'s own Delete button meant moving it, not duplicating it — there is now exactly one place category deletion is triggered from, not two.
- **A DB-side lock needs to cover every column it implies, not just the one the trigger already checked.** `prevent_default_category_deletion` blocked deleting a default/system category but said nothing about renaming one — extending it to also reject `new.name <> old.name` for those rows was a two-line addition to an existing trigger, not a new one, since "this row is fixed" is one invariant, not two. Icon/color deliberately stay outside that lock: nothing anywhere looks a category up by either, so there's nothing for a color change to break.
- **`ALTER EXTENSION ... SET SCHEMA` and "just create the schema and columns you need" don't always compose** (tangential finding while touching triggers again) — not hit this round, but worth remembering from the `pg_net` fix above: some Postgres extensions manage their own internal schema as an owned member object, and forcing a different one fails outright rather than migrating cleanly.
- **A global UI-convention sweep (icon-only toolbar buttons, inline nav titles) is safe to do with `perl -i -pe` across many files in one pass, but only when the target line's shape is fully uniform first.** Every `.navigationTitle(...)` call in this codebase is a single-line modifier (confirmed by grep before writing the regex) — `s/^(\s*)(\.navigationTitle\(.*\))$/$1$2\n$1.navigationBarTitleDisplayMode(.inline)/` reused the captured indentation exactly, so it was safe to run unattended over 26 files at once. The Cancel/Save → xmark/checkmark swap was `Edit`-per-file instead, deliberately: those blocks weren't textually uniform (some had a trailing `.disabled(...)`, one had a different label like "Map"), so a blind regex would have silently mismatched some and needed the same manual verification anyway.

## Sync Ritual removal & "Other" as the sole default category

- **A user-visible bug report ("categories that aren't the default can't be deleted") turned out to be `system_key` categories — Adjustment ×2, Uncategorized — masquerading as ordinary custom ones with no UI signal that they were special.** They were seeded automatically per user (`handle_new_user`/`ensure_user_bootstrap`) and locked exactly as hard as the default row by the same trigger, but nothing on the tile or in the edit sheet said so. Rather than surfacing that distinction in the UI, the user's actual decision was to remove the whole "system category" tier: reconciliation adjustments no longer exist (Sync Ritual was independently removed — see below), and the capture/CSV-import "no learned merchant mapping" fallback now points at the one true default ("Other") instead of a dedicated system row. One default per kind, full stop — no third tier to explain.
- **When a feature is reported "already removed," verify the backend independently of the client — the client and the DB drift out of sync on removal exactly as easily as on addition.** `SyncRitualView.swift`/`StalenessBadge.swift` were already gone from the App target, but the full backend survived untouched: `reconciliations` table, `reconcile_ledger_account`/`reconcile_valuation_account`, `account_staleness`, `accounts_sync_status`, a `needs_review` branch, and a fork-time code path in `fork_household_accounts` that both duplicated `reconciliations` rows and looked up the now-dead Adjustment category by `system_key`. Grepping for the feature's SQL identifiers (not just its Swift ones) across every migration file was what actually found the full surface area.
- **Never reconstruct a multi-statement SQL function from a partial `sed`/`grep` excerpt read earlier in the session — re-read the authoritative, current definition in full before writing a `CREATE OR REPLACE`.** Caught mid-migration, twice, in this exact piece of work: (1) a `needs_review` view rewrite initially dropped a fifth `csv_import_candidate` branch that simply hadn't been scrolled into view yet; (2) a household-fork rewrite was drafted as `leave_household(p_member_a, p_member_b)` — a signature invented from a stray comment fragment — when the real function is `leave_household()` (no arguments, resolves the other member via `my_household_id()`) delegating to a separate `fork_household_accounts(p_household_id, p_member_a, p_member_b)`, which is the function that actually needed the fix. Both were caught by deliberately re-reading the real migration file end-to-end before trusting the draft, not by the eventual `db reset`/pgTAP run (which would have caught the wrong-signature case by "function does not exist," but would have silently accepted the missing-branch case, since a `needs_review` row simply never appearing produces no error, just a quietly incomplete inbox).
- **`CREATE OR REPLACE VIEW` cannot change a column's resolved type, even when the change is only "no longer resolves through the branch that forced a looser type."** Dropping `needs_review`'s `reconciliation_gap` branch (whose `amount` came from `accounts_sync_status.balance`, plain `numeric`) should have let `amount` resolve back to `numeric(20,4)` from the other branches' explicit casts — instead `supabase db reset` failed outright with `cannot change data type of view column "amount"` (SQLSTATE 42P16). Fixed by `DROP VIEW`+`CREATE VIEW` (re-issuing the `GRANT` afterward, since dropping a view drops its grants too) instead of `CREATE OR REPLACE VIEW`. Worth checking for this whenever a view redefinition removes a branch that was the widest/loosest-typed one for a given column.
- **`supabase db push` can fail on a syntactically and semantically correct `ALTER TABLE` with an opaque, unhelpful error** (`Failed to execute statement / At statement: 16 / <the exact DDL text>`) that persists identically across retries and survives adding `IF EXISTS`/`CASCADE` — with `pg_depend` against the linked project confirming zero real dependents on the constraint being dropped. Splitting the single large migration file into two (moving everything from that `ALTER TABLE` onward into a second, immediately-following migration) let both apply cleanly against the same hosted project with no other change — a batching/statement-count quirk in the push tool itself, not a real SQL problem, and not reproducible locally via `supabase db reset` (which applies the same file through a different codepath and always worked). **General lesson: if `db push` rejects a statement that is independently verified correct (no local repro, no real dependency via `pg_depend`, identical failure across retries with defensive `IF EXISTS`/`CASCADE` added), suspect the push tool's own statement batching before re-diagnosing the SQL — splitting the migration at the failing statement is a legitimate, low-risk fix, not a workaround for a real bug.**

## Account balance edit + offline pending-delta overlay (Option 1)

- **Removing a feature (Sync Ritual) closed off the only path to a real invariant.** A valuation account's balance is defined as "latest snapshot + transfers after it" — with `reconcile_valuation_account` gone and nothing replacing it, there was no way to ever move that number again after the account's opening snapshot. `set_account_balance(p_account_id, p_new_balance, p_id)` closes this for both account kinds in one RPC: for `ledger`, it computes `account_balance_on(id, current_date)` *inside the RPC* (never trusting a client-supplied "current balance") and files the gap as an adjustment transaction under the owner's default "Other"; for `valuation`, a plain new snapshot, no transaction — a valuation change was never income or expense (money rule 1). Computing the gap server-side, at whatever moment the write actually executes, is what makes it correct even when the write was queued offline and replays hours later against a balance that moved in the meantime.
- **A same-transaction pgTAP test can't exercise a same-day tiebreak the way it looks like it should.** Adding `created_at` as a secondary sort to `account_balance_on`'s "latest snapshot" lookup (`order by as_of desc, created_at desc`, matching `unrealized_gain`'s existing pattern) needed a real same-day-two-edits test since this RPC makes that case newly common — but `now()` is frozen for the entire test transaction (this project's own documented `_helpers.psql` gotcha), so two snapshots inserted with the default `created_at` land on the *literal same timestamp*, and even explicit inserts computed as `now() + interval '1 minute'` collided with a snapshot the RPC itself had already written earlier in the same test at that identical frozen `now()`. Fixed by offsetting explicitly *past* the frozen instant (`+ interval '2 minutes'`), not just past each other.
- **`select (f()).field` silently breaks for a `returns table` function; `select field from f()` doesn't** — this project's own harness note ("`select * from f()`, never `select (f()).*`") turned out to generalize to single-field access too, caught by `ERROR: could not identify column "transaction_id" in record data type` on the very first attempt.
- **A pure, decoupled "apply pending deltas on top of a cached balance" engine is cheap to get exactly right and cheap to unit-test, once the input shape is reduced to three primitive-field cases** (`transactionDelta`, `transferDelta`, `accountBalanceOverride`) instead of the app's own `Outbox`/payload types. `KeepoCore/PendingOverlay.swift` has zero SwiftData/SwiftUI dependency and 11 unit tests covering the actual hard cases (edit-as-subtract-then-add, override-then-additional-delta-on-top, two-overrides-in-a-row) — decoding `Outbox`'s SwiftData items into those primitive cases is a separate, App-target-only adapter (`PendingOverlayAdapter.swift`), for the same reason `OfflineStore`/`Outbox` themselves live in the App target and not the package (macOS-floor mismatch for SwiftData). Keeping the money arithmetic in the pure layer and the decoding in the impure layer meant the arithmetic could be tested exhaustively without ever touching a `ModelContext`.
- **An overlay is only as honest as its willingness to bail to the last-known value.** `HomeView`'s net-worth overlay converts each in-scope account's pending balance into base currency using on-device-cached FX rates (`FxRateCache`, mirroring `CurrencyCache`'s timeout-then-fallback shape) — but the moment *any* account in scope can't be converted (no cached rate) or has no computable balance at all, the whole overlay bails to the plain server/cached `netWorth` rather than silently summing a partial total. Same money rule 5 discipline ("—", never a wrong number) applied to a client-side aggregate, not just a server one.
- **Scope cuts are worth stating in the code, not just the conversation.** This pass deliberately does not overlay `updateTransfer`/`deleteTransfer` (need the same old-value lookup pattern as transaction edits, not yet built) or `captureTransaction` (resolves its account via `card_mappings` server-side, uncached client-side) — all three still queue and sync correctly, they just don't move a balance instantly. Recorded directly in `PendingOverlayAdapter`'s header comment so the gap is visible to whoever extends this next, not just to whoever was in the room when the decision was made.

## L1 — money as fixed-point Int64 (local-first rebuild, `keepo-local-first-plan.md`)

- **`sum(bigint)` returns `numeric`, not `bigint`.** Any `plpgsql` function declared `RETURNS TABLE(... bigint)` that does `RETURN QUERY SELECT sum(some_bigint_col) ...` needs an explicit `::bigint` cast — plpgsql requires an exact structural type match for `RETURN QUERY`, unlike `SELECT ... INTO` a local variable, which implicit-casts silently. Four functions broke on this in one pass; all four used `RETURN QUERY`, none of the unaffected functions did.
- **`DROP FUNCTION` drops every grant that function had, including ones untouched by the migration's intent.** A function granted to both `authenticated` and `service_role` came back `authenticated`-only after a routine drop-and-recreate, because the migration's own grant statements only restored what looked relevant. Only surfaced via a pgTAP test running explicitly as `service_role` — a test suite that only ever runs as `authenticated` would never catch this. Before rewriting any function whose grants matter, grep the original migrations for its actual `grant execute` lines first.
- **Idempotent-retry-safety and optimistic-concurrency version checks conflict unless idempotency is checked first.** Adding an `expected_version` parameter to an already-idempotent RPC (`set_account_balance`, keyed by a client-generated id) means a retried write with a now-stale captured version will spuriously "conflict" once the first attempt already succeeded and bumped the version — unless the function checks "does this id already exist?" *before* comparing versions, so a genuine replay short-circuits to success first. General pattern for any future RPC that needs to be both versioned and safely retryable.
- **A missing `security_invoker = true` on a `DROP VIEW` + `CREATE VIEW` rewrite is a silent RLS-bypass bug, not a stylistic omission** — the option isn't preserved automatically and there's currently no pgTAP assertion catching it (unlike the Phase 5 schema-wide checks for tables/functions). Caught this round only by grepping existing migrations for the pattern before pushing; worth adding an automated check in a future phase rather than relying on manual review again.
- **A manual read-through misses functions that access a renamed column through bare `record`/`%ROWTYPE` field access with no local variable to notice** (`v_row.amount`, `new.amount`) — these don't show up when scanning for explicit `numeric(20,4)` declarations. `select proname from pg_proc where prosrc ~ '\mamount\M|\mopening_balance\M|...'` (word-boundary regex against `pg_proc.prosrc`) is the reliable way to find every function actually referencing a renamed column, and found 7 functions a manual pass had missed in this migration.
- **BSD/macOS `sed` silently no-ops on `\b` word-boundary patterns** — `sed -i '' -e 's/\bfoo\b/.../'` makes no change and prints no error. Use substring-anchored patterns or a Python `re`/exact-match script instead on this platform; verify the replacement count matches expectations rather than trusting a clean exit code.
- **A blanket rename script only catches the literal string it targets, not other properties carrying the same value.** Renaming `amount: Decimal)` → `amount: Int64)` via `sed` missed `payload.fromAmount`/`payload.toAmount` entirely, producing a garbled, misleading downstream compiler error with no obvious connection to the real cause. After any broad automated rename, grep specifically for other property names that reference the same underlying value before trusting the pass is complete.

## L2 — sync primitives (local-first rebuild, `keepo-local-first-plan.md`)

- **`supabase db push` tracks applied migrations by filename, not content — editing an already-pushed migration file is silently a no-op on the next push.** Pushed a migration, then kept fixing bugs pgTAP found by editing that same file's already-applied content. The next `db push` reported "up to date" with zero migrations applied — hosted was left running the *original, buggy* function bodies while local (`db reset`, which always replays from disk) had the fixed ones, an invisible drift with no error anywhere. **Never edit a migration file after it has been pushed, even within the same session** — write the fix as a new follow-up migration instead (this project's own established convention: see `20260814100000` + `20260814100100`). If a function's signature also changed, the follow-up migration needs an explicit `drop function if exists old_signature(...)` before the `create or replace` of the new one, or the old overload lingers on hosted.
- **A single scalar cursor compared against rows stamped by more than one independent counter is broken by construction, not by accident.** A "global" domain (shared by every user, e.g. for reference data with no owner) accumulates tickets far faster than any one narrow domain (e.g. a single household) — taking `max(sync_seq)` across both and using it as one cursor means the low-numbered, rarely-updated domain's rows are permanently starved: their ticket sits below a cursor value the fast domain alone already pushed far ahead, so `sync_seq > cursor` is false forever even for a row the client has genuinely never seen. Any design with more than one independent per-domain ticket counter needs one cursor **per counter**, never a shared scalar across them. Caught only by an end-to-end pgTAP assertion ("a pull from before an access change now delivers the row"), not by reviewing the SQL — the bug is invisible until you actually trace two counters through the same comparison.
- **`ALTER TABLE ... DISABLE TRIGGER` fails with "cannot ALTER TABLE because it has pending trigger events" whenever the target table has a `DEFERRABLE` constraint trigger with events still pending in the same transaction** — including from a completely unrelated earlier statement (e.g. the row's own creation, via a `DEFERRABLE` FK). Works fine as the very first thing in a fresh transaction (e.g. a migration's own backfill) but is fragile anywhere it might run later in a longer transaction — exactly the shape of every pgTAP test file (one big transaction) and plausible in real multi-statement RPC bodies too. When the goal is "fire this one specific trigger without also firing that other one," a transaction-local `set_config`-based flag the unwanted trigger checks for and skips is more robust than disabling triggers at the DDL level — no lock-mode surprises, and it composes with `DEFERRABLE` constraints already in flight.

## L3 — on-device GRDB store (local-first rebuild, `keepo-local-first-plan.md`)

- **A `TEXT`-affinity SQLite column silently rounds a numeric value through a 15-significant-digit text cast on every write** — GRDB doesn't warn about this; SQLite coerces per column *type affinity* regardless of what value you hand it. Encoding a `Date` as `timeIntervalSince1970` (a ~10-digit-before-the-point, 6-after Double) into a column declared `.text` was enough imprecision to occasionally round a just-inserted timestamp *forward*, past a `Date()` read a few microseconds later — surfaced as a genuinely flaky unit test (`hasStalePending(threshold: 0)`, ~1-in-5 failures), not a deterministic one. Fixed at the schema level: any column carrying a value that needs to round-trip exactly (not just legibly) should be declared with the matching SQLite affinity (`.double` for a Double, not `.text`) — reserve `.text` date columns for values that are genuinely text-shaped everywhere else in the system (this codebase's server-timestamp columns, which mirror PostgREST's own ISO 8601 strings and are never compared for sub-second precision).
- **`xcodegen generate` stripping the committed `DEVELOPMENT_TEAM` signing setting (documented in the L2 entry above) is not a one-time gotcha — it recurs on every regeneration**, including ones that only add new source files with no `project.yml` change at all. Ran into it twice in one phase (once after adding the GRDB package, once after adding two new `.swift` files). Treat "run `git diff Keepo.xcodeproj/project.pbxproj` and restore `DEVELOPMENT_TEAM` if stripped" as a mandatory step after *every* `xcodegen generate`, not a conditional one.
- **GRDB's `DatabaseWriter.write`/`.read` overload resolution depends on the *caller's* async-ness, not just the closure's own shape** — the same `try? dbQueue.write { db in ... }` call compiled fine inside a non-`async` method (only the sync `throws` overload is a candidate) but failed inside an already-`async` method with "expression is 'async' but is not marked with 'await'" (the `async throws` overload won instead). Always add `await` explicitly to a GRDB write/read call made from inside `async` code, rather than relying on the compiler to silently pick the sync overload.
- **Before porting a planned architecture line literally, grep for whether the thing it names to *replace* actually exists.** The local-first plan's L3 bullet said "`ValueObservation` → SwiftUI, replacing SwiftData's `@Query`" — but a repo-wide grep found zero `@Query` usages anywhere in the app target; nothing needed replacing. Wiring `ValueObservation` anyway (there being only one writer to the table it would observe, refreshing synchronously already) would have been unmotivated abstraction. Investigate and explicitly document *why* a planned step was skipped, rather than silently doing it or silently skipping it.

## L4 — money layer ported to SQLite, and the referee (local-first rebuild, `keepo-local-first-plan.md`)

- **Byte-exact cross-dialect FX conversion needs row-level rounding granularity, not currency-level, whenever the source SQL rounds inside a `sum()`.** `sum(fx_convert(amount, currency, base, date))` rounds once per row before summing; grouping natively by `(currency, date)` and converting the pre-summed total once is close but not guaranteed identical (two independently-rounded same-currency-same-day values can differ from one rounding of their sum). When porting any aggregate that wraps a per-row rounding function, fetch individual rows and reduce with the same per-row round-then-sum order, not a pre-aggregated total.
- **A local `TEXT` timestamp column can only be compared with `<=`/`<`/`>` as a plain string if every value that ever lands in it shares one exact rendering** — this codebase's own PostgREST-sourced strings carry a fixed six-fractional-digit `+00:00` suffix; `ISO8601DateFormatter()`'s default output (`Z`, whole seconds) sorts *before* a same-second fractional row, silently misordering the comparison. Any boundary value built client-side for comparison against a synced `TEXT` timestamp column needs a formatter that reproduces the source system's exact rendering, confirmed against a real row (e.g. via `curl` against the actual API) rather than assumed from documentation.
- **A money value that divides by a rate/percentage parsed from a TEXT column must keep that value as `Decimal` all the way to the division, even if a sibling value in the same struct only ever feeds `Double`-only math (`ln`/`pow`).** Parsing both `withdrawal_rate` and `real_return_rate` as `Double` "for consistency" would have introduced real (if small) drift in `fi_number_e4` — a money output under an exact-to-the-unit contract — since `"0.04"` isn't exactly representable in binary `Double`. Only convert to `Double` at the last possible point, and only for the specific computation that genuinely needs floating point (a transcendental function), never upstream of an exact-arithmetic path that happens to share the same source value.
- **When the target platform has no driver for the source system, "the referee" a plan describes as a live differential test has to become a pinned comparison instead — say so explicitly, in the code and the docs, rather than silently building something narrower than what was asked for.** This iOS test target has no Postgres wire-protocol client, so a genuinely live SQLite-vs-Postgres comparison per test run isn't available from inside `swift test`. The correct move was capturing real Postgres output once (via `docker exec ... psql` in a rolled-back transaction) and pinning those exact numbers as the Swift test's expected values against an identical fixture — real ground truth, just frozen at capture time rather than re-verified live. Document the mechanism and its staleness risk (pinned values need regenerating if the ported SQL changes) directly in the test file's own header comment, not just a commit message.
