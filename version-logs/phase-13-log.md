## Findings

1. **`fx_freshness_check`'s first draft was healthy by default when no `fx_rates` rows existed at all** — `coalesce(max(rate_date), current_date - p_max_age_days) >= current_date - p_max_age_days` reduces to `true` trivially whenever `max()` is `null`, regardless of whether a non-EUR currency is actually in use and genuinely lacking rates. Caught before it shipped by manually deleting `fx_rates` and checking the result rather than trusting the SQL by inspection. Fixed by coalescing the *comparison* to `false`, not the *date*: `coalesce(max(rate_date) >= current_date - p_max_age_days, false) or not exists (...)`.
2. **Local secret provisioning must happen before, not after, other seed data** — Vault secrets seeded at the end of `seed.sql` (its original location) meant the file's own earlier account/profile inserts had already fired the FX-backfill triggers against nonexistent secrets, logging avoidable `missing_vault_secret` events on every single fresh `db reset`. Moved to the top of the file, immediately after the header comment and before the first `auth.users` insert. Worth checking for on any future seed-data addition that depends on a trigger a *later* insert in the same file would otherwise fire first.
3. **A freshly deployed Edge Function defaults to `verify_jwt: true`** unless `supabase/config.toml` has an explicit `[functions.<name>] verify_jwt = false` entry — `sync-fx-rates` already had one from Phase 4; `alert-operator` didn't, and its first deploy silently came up JWT-gated at the platform level, which would 401 every `pg_net`-originated call (no user JWT, only a custom header) before the function's own secret check ever ran. Caught by checking `supabase functions list`'s `verify_jwt` field after the first deploy, not by assuming the deploy succeeded meant the function was actually callable the way it needed to be. Fixed by adding the config entry and redeploying.
4. **`supabase secrets list` redacts every value**, including ones this session needed to know to keep two stores in sync. Phase 4 already set a real `FX_SYNC_SECRET` as an Edge Function secret on hosted; this phase's `vault.create_secret('...', 'fx_sync_secret')` needs the *identical* value in Postgres Vault for `ops_http_post`'s header to authenticate against the deployed function, and there is no way to read the existing value back through the CLI to match it. This is exactly why hosted secret provisioning is left as an explicit manual step (see Notes) rather than attempted here with a fabricated value that would silently never match.
