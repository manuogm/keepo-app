# Phase 9 — Sync Ritual & reconciliations

## Delivered

- Migration `20260806200000_sync_ritual.sql` (+ two same-phase fixups, `20260806200001_reconcile_default_null.sql` and `20260806210000_sync_status_reconciliation_id.sql` — see Notes): **H14 closed** — `categories.system_key text` + `unique (owner_id, system_key)`, orthogonal to `is_default` rather than overloading it. `is_default` means "the fallback category a client uses when none is chosen" (Other); `system_key` means "a category the app itself writes into, off-limits to the user" (Adjustment). Two Adjustment rows exist per user, one per `category_kind` — the same reason "Other" is two rows: `sign_matches_category_kind` requires the category's kind to agree with the transaction's sign, and an adjustment can move a balance in either direction. `handle_new_user()`/`ensure_user_bootstrap()` seed both alongside the two Other rows; backfilled for any pre-existing profile. `prevent_default_category_deletion` widened (same function, same trigger) to treat a system category exactly as undeletable as a default one.
- `reconciliations` — append-only (no update/delete policy, like `balance_snapshots`/`fx_rates`). Deliberately **never stores a balance** — that would compete with `SUM(amount)` as a second source of truth for ledger accounts; it records the *event* of reconciling (`entered_balance`, `computed_balance`, and either `adjustment_txn_id` or `snapshot_id`), which is what "verified X ago" actually renders from.
- `account_staleness(subtype, last_verified_at)` — the one `CASE` holding every per-subtype threshold (checking/cash 3 days, credit_card 7 days, loan/investment 30 days — not specified numerically in the feature spec, chosen as reasonable defaults; revisit if real usage says otherwise). `accounts_sync_status` view joins this against `accounts_with_balances` + the latest `reconciliations` row per account, exposing `last_verified_at`, `is_stale`, and `last_reconciliation_id` (needed by the client as the concurrency guard — see below; missed in the view's first draft, added in the `20260806210000` fixup). A never-reconciled account's clock starts at its own `created_at`, not "infinitely stale from the moment it exists" — the opening balance IS a verification event, per the spec's own reasoning for requiring one at account creation.
- `reconcile_ledger_account(p_account_id, p_entered_balance, p_expected_last_reconciliation_id)` — computes the real gap server-side via `account_balance_on` (Phase 8), posts a real `source='adjustment'` transaction only when the gap is non-zero (never a `$0` adjustment nobody asked for), filed under whichever Adjustment category's kind matches the gap's sign, then writes the `reconciliations` row. `reconcile_valuation_account(...)` is the parallel path for valuation accounts: writes a `balance_snapshots` row directly, no transaction, no adjustment, no review step — exactly the spec's explicit split.
- **The concurrency guard, not a version column**: both RPCs take `p_expected_last_reconciliation_id` — the id of the account's latest `reconciliations` row as the caller last saw it (`null` if never reconciled). If the real latest id has moved since — another household member reconciled the same shared account in between — the call returns `conflict = true` and writes *nothing*, rather than risk two adjustments for the same gap. There is no separate "rebase" code path: the client's natural response to a conflict (reload `accounts_sync_status`, see the new state, recompute) already **is** the rebase the spec describes. This is deliberately identity-agnostic — it protects one owner reconciling twice from two different devices exactly the same way it protects two household members, with the same code path and the same pgTAP assertion covering both (see Verify).
- **Client:** `ReconciliationRepository` (KeepoCore) — `fetchSyncStatus`, `reconcileLedgerAccount`, `reconcileValuationAccount`, mirroring `AccountWrites.swift`'s conflict-as-data decode pattern exactly. `StalenessBadge` (shared component, per app-architecture.md §2's table) — "verified X ago" via `RelativeDateTimeFormatter`, neutral `TextSecondary` when fresh, `BrandSecondary` (Mango Fizz — the brand doc's own token for budget-limit-style reminders) when stale; used by both the Sync Ritual row and the Home banner, never a second re-derivation of the threshold client-side. `SyncRitualView` — per-account list with `StalenessBadge`, on-demand "Sync now," tap-to-reconcile sheet that shows the computed adjustment (sign, amount, category) **before** the user commits (spec: "always visible, never silently absorbed") for ledger accounts, and a bare value field with no preview for valuation accounts. `HomeView` gained a factual staleness banner (any `include_in_total` account that's stale, across the whole net worth regardless of the Total/Me/Household picker's current selection — scoping the banner itself to the picker was considered and skipped as unrequested complexity) and a permanent toolbar link into the ritual, independent of whether anything is currently stale.
- Not added as a 6th tab bar item — reached from Home's toolbar and its banner, the same "not every screen in the spec's list is a top-level tab" precedent Household (Phase 7, reached via Settings) already established.

## Notes for the next phase

- **Two same-phase fixups, both caught before commit, neither a design defect in the reviewed sense:**
  1. `p_expected_last_reconciliation_id` needed `default null` on both RPCs — Swift's synthesized `Encodable` uses `encodeIfPresent` for `Optional` properties, so a `nil` first-reconciliation call omits the JSON key entirely rather than sending `null`, and PostgREST returns `PGRST202` without a default. This is the exact, already-documented lesson (keepo-v1-master-plan.md's cross-cutting rules) for every optional RPC parameter in this codebase — worth specifically checking for on any new RPC parameter typed `uuid` (rather than a string/number) that can be legitimately absent, since a `uuid` parameter's "empty" state is `null`, not an empty string, and is easy to mentally file as "obviously required" when writing the signature.
  2. `accounts_sync_status`'s first draft didn't expose the reconciliation *id* at all, only its timestamp — the client needs the actual id to pass back as the concurrency guard, not just to know how long ago it happened. Both fixed via new, additive migrations rather than editing the already-hosted `20260806200000` — by the time the gap was found, that migration had already been pushed to hosted, so the established "correct forward in a new migration once something's shipped" precedent applied even though it was all within the same uncommitted phase.
- `account_staleness`'s thresholds (3/7/30 days) are a judgment call, not a spec number — the feature spec says only "per subtype... cash drifts in a day, a mortgage does not move in a month," no concrete values. Revisit once real usage data exists.
- The Home banner is deliberately **not** scoped to the current Total/Me/Household picker selection — it fires if *any* `include_in_total` account across everything the viewer can see is stale, regardless of which scope is currently displayed. A scope-aware banner is easy to add later (the picker's own `scope` state and `accounts_sync_status`'s rows are both already in hand) but wasn't asked for and would need a household-membership join this view doesn't currently carry.
- `reconcile_ledger_account`'s adjustment always posts under the account **owner's** Adjustment category, never the calling household member's — required by the existing `(category_id, owner_id) → categories (id, owner_id)` composite FK (Phase 5, H12) and the correct behavior regardless: an adjustment belongs to whoever's account it's correcting, same as every other transaction on a shared account.
