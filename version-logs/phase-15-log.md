# Phase 15 — Insights & savings rate

## Delivered

- Migration `20260808130000_insights.sql`: four `SECURITY INVOKER` read functions — `spending_by_category(scope, from, to)`, `income_expense_series(scope, from, to, granularity)`, `savings_rate(scope, from, to)`, `unrealized_gain(account_id)`. All rely entirely on `transactions`/`categories`/`balance_snapshots`' own RLS (household-aware for free via the same `can_read_account`-derived visibility every other read already gets) — no privilege bypass to reason about anywhere in this phase, same posture as `fx_convert`/`net_worth_series` before them.
- A transfer's `category_id is null` (the CHECK constraint's own "exactly one of `transfer_group_id`/`category_id`" guarantee) is what excludes **both** transfers and valuation-account activity from every function here, with zero separate filtering logic: money rule 1 means every transaction on a valuation account is a transfer, so filtering on `category_id is not null` catches both cases for free.
- Every summed value null-propagates a missing FX rate exactly like `net_worth_series` already does (`bool_or(fx_convert(...) is null) then null else sum(...)`) — a category or a period with one unconvertible transaction renders `—` client-side, never a silently-partial total (money rule 5). `savings_rate` additionally returns `null` (never divides by zero) when there's no income in the window.
- `unrealized_gain(account_id)` = latest `balance_snapshots.value` minus `SUM(all confirmed, non-deleted, non-future transactions on that account)` — free per the spec, since every one of those transactions is already a transfer and the cost basis is already in the ledger. Returns `null` (a bare `SELECT ... WHERE EXISTS(...)` with no matching row) before any snapshot exists, rather than a misleading `0`.
- `KeepoCore`: `InsightsRepository` — thin wrappers mirroring `HouseholdRepository`'s existing `net_worth`/`net_worth_series` pattern exactly (scalar RPCs decode directly to `Decimal?`, no array-wrapping needed — confirmed by checking how `net_worth` itself already decodes before assuming the same for `savings_rate`/`unrealized_gain`).
- `App`: `InsightsView`, reached from Home's toolbar alongside Sync Ritual — not a 7th tab, continuing the precedent Household (Settings) and Recurring (Settings) already established for this project: a feature earns a tab only when it's a primary, frequently-visited destination, and Home's toolbar is where "the other big number screens" already live. Trailing 90-day window matching Home's own `rangeDays`, no date-range picker — bucket granularity is derived from the span via the existing `DateBucketing.granularity(from:through:)`, passed straight into the RPC as a string, never recomputed or bucketed client-side (the actual summing happens once, in SQL, per money rule 3). Savings-rate hero metric, an income/expense grouped bar chart, a category-spending horizontal bar chart (one color throughout, name + value as a text annotation per bar — app-architecture.md §5's "color is never the only identity channel" rule, satisfied trivially here since there's no per-category custom-color feature to validate against in the first place), and an unrealized-gain row per investment account.
- New `IncomeColor` color asset (`#2a78d6` light / `#3987e5` dark) — the palette's income-blue role from app-architecture.md §5 had no existing asset to reuse; `BrandPrimary` (used for expense) already existed from Phase 1.

## Findings

1. **A real, unrelated regression, found by actually running seed data through the new RPCs rather than trusting either side by inspection.** Phase 12's `create or replace function handle_new_user()`/`ensure_user_bootstrap()` carried forward Phase 9's Adjustment-category seeding and added Uncategorized, but silently dropped the original "Other" default-category insert (`is_default = true`) that every version since Phase 1 had. Every real signup since Phase 12 shipped — hosted included — got zero default categories. Invisible until this phase: `seed.sql`'s own transaction inserts use a bare `SELECT ... FROM categories WHERE kind = 'expense'` feeding an `INSERT ... SELECT`, which silently multiplies one intended row into one per matching category. With "Other" missing, that query still matched two other expense categories (Adjustment, Uncategorized) instead of the intended one, tripling every seeded expense transaction — which then silently tripled every category total this phase's `spending_by_category` computed, surfacing as an obviously-wrong number in manual verification rather than a subtle one. Root-caused to `handle_new_user()`, not patched at the display layer: fixed forward via `20260808135000_restore_other_category_seeding.sql` (restores the missing insert in both functions, backfills any existing profile missing "Other," pushed to hosted as part of this phase) and hardened `seed.sql`'s three affected inserts to filter `AND c.is_default`, not just `kind`, so the same class of silent multiplication can't recur as more same-kind categories accumulate per user in later phases.
2. **A scope-filtering test and a null-propagation test must not share fixture state if they're not meant to interact.** The first draft of `15_insights.sql` introduced a GBP (rate-less) transaction, then later tried to assert a scope-filtered total on the same category — but the GBP row's null-propagation had already poisoned every scope's total for that category, failing the scope assertion with `NULL` instead of the expected number. Fixed by reordering: the scope-filtering assertions run immediately after the category's first (clean) sum, before the GBP row is ever introduced. Worth remembering generally for money-rule-5-style null-propagation logic: once a category/bucket's total goes `null`, every later assertion against that same category needs to either expect `null` too or use a different category/bucket entirely.
