# Phase 17 — Security, session & Settings

## Delivered

- `KeychainSessionStorage: AuthLocalStorage` (KeepoCore) — a real `Security`-framework Keychain wrapper (`SecItemAdd`/`SecItemCopyMatching`/`SecItemDelete` directly), not the SDK's own plain `KeychainLocalStorage`. Items are protected by a `SecAccessControl` built from a constructor-supplied `SecAccessControlCreateFlags` (production default `[.biometryCurrentSet]`, `.whenUnlockedThisDeviceOnly` accessibility) — `.biometryCurrentSet` auto-invalidates the moment a new face is enrolled, a genuine device-changed-hands signal the OS enforces, not app logic. `store()` is a delete-then-add, never a `SecItemUpdate` — updating an ACL-protected item's *value* still requires evaluating its current access control (the exact repeated-prompt problem this avoids), while deleting by primary key (service+account) never touches the protected value and needs no evaluation at all.
- `StepUpAuthenticator.requireFreshSession(reason:)` — a forced re-read of the *same* Keychain item the session lives in, via a shared `KeychainSessionStorage.sessionStorageKey` constant that both `SessionStore` (passed to `SupabaseClientOptions.AuthOptions.storageKey`) and the authenticator agree on. Without that shared constant, GoTrue would pick its own default key internally and a step-up re-read would silently target the wrong item forever.
- `AuthProvider` widened by exactly three members: `restoreSession()` (silent, no interactive UI — the biometric-gated cold-start path), `stepUp(reason:)`, `capabilities` (`AuthProviderCapabilities.supportsAppleSignIn`/`requiresBiometricStepUp`). `StubAuthProvider` implements all three trivially (no real security boundary in a fixed-password local dev account — matches every other stubbed security concept already in this project; RLS is still fully enforced server-side regardless of which provider is active). `PasswordAuthProvider` gets a real `StepUpAuthenticator`-backed `stepUp` and `requiresBiometricStepUp = true`.
- `SessionStore.start()` now tries `authProvider.restoreSession()` first, falling back to the full `signIn()` (which may present interactive UI) only when there's genuinely no cached session — matches the spec's "SIWA once, Face ID gates the cached session on every subsequent open" framing, where `start()` previously conflated the two into one unconditional `signIn()` call.
- `Repositories.swift`: `ProfileRepository.updateBaseCurrency` — a plain RLS-scoped `profiles` update (`profiles_update`'s existing policy already allows it). Phase 13's `profiles_backfill_fx_on_base_currency_change` trigger fires automatically server-side; nothing extra to call from the client.
- `App`: `SecuritySettingsView` (reached from Settings) — base-currency picker + save, a Security section with a step-up test button (gated behind `session.authCapabilities.requiresBiometricStepUp`, so it's invisible for the local dev account, which has nothing real to test), and a recovery-email field calling `client.auth.update(user:)`. `MetricKitSubscriber` registered at launch (`KeepoApp.init()`), logging metric/diagnostic payloads via `OSLog` — no third-party SDK, no backend endpoint; Apple delivers to Xcode Organizer automatically regardless of whether the app subscribes at all.

## Findings

1. **A real, unplanned scope decision: `KeychainSessionStorage` is wired in only for a non-local provider, not unconditionally.** The master plan's original text described building and injecting the storage without specifying which providers get it. Wiring it in for *every* provider — including `StubAuthProvider` — would mean the local dev loop this entire project has run on since Phase 1 (a plain `client.auth.signIn()` against a fixed local account) would suddenly require Face ID enrollment just to launch the app, breaking every future phase's fast iteration and every headless `xcodebuild test` run. Decided: `SessionStore.init()` mirrors the exact same `config.isLocal` branch it already uses to choose the provider itself, passing `KeychainSessionStorage()` only for the non-local (hosted-capable) path. `PasswordAuthProvider` is what actually exercises the mechanism today; `AppleAuthProvider` (Phase 20) inherits it unchanged.
2. **A real Keychain *write* (`SecItemAdd`) fails with `errSecMissingEntitlement` (-34018) from a plain `swift test` executable on macOS, regardless of `accessControlFlags`, `kSecUseDataProtectionKeychain`, or whether an access-control object is involved at all** — confirmed empirically across several attempted fixes (adding `kSecUseDataProtectionKeychain`; skipping `SecAccessControl` entirely for an empty flag set in favor of plain `kSecAttrAccessible`). An unsigned SPM test binary simply has no keychain-access-group entitlement, and macOS ties Keychain *write* access to the calling process's code signature — no query construction changes that. `SecItemCopyMatching` against a key that was never written still succeeds cleanly (a legitimate "not found" lookup, no entitlement needed for that path), so `KeychainSessionStorageTests` is scoped to exactly what's actually exercisable: retrieve-miss and the `StepUpAuthenticator` no-session path. Real store/retrieve/remove round-trips and the biometric gate itself are Simulator/device-only, joining `OfflineStoreTests`' identical Phase 11 finding for file protection as the same class of environment limitation.
3. **`SecAccessControlCreateWithFlags` with an *empty* flag set still constructs a real `SecAccessControl` object** — passing `accessControlFlags: []` doesn't mean "no ACL," it means "an ACL object with zero additional flags beyond the accessibility class," and that object still triggers the exact same entitlement check as a non-empty one. The actual fix for testability (before concluding writes aren't testable here at all, per Finding 2) was skipping `kSecAttrAccessControl` from the query entirely when the flag set is empty, using plain `kSecAttrAccessible` instead — a real code branch worth keeping even though it turned out not to be sufficient on its own, since it correctly models "no additional access-control flags" as "no ACL object" rather than "an ACL object with nothing in it."

## Verification

- `swift test` (KeepoCore) — 47/47 (2 new suites: `KeychainSessionStorageTests` — retrieving a never-stored key returns `nil`; `StepUpAuthenticatorTests` — throws `.noSession` when the underlying Keychain item doesn't exist). No pgTAP suite this phase — zero SQL/migration work; every change is App-target Swift or KeepoCore.
- `xcodebuild -scheme Keepo build` — clean. `swiftlint lint --strict` — 0 violations across 64 files (line-length wraps on several multi-parameter Keychain/Settings call sites; `MetricKitSubscriber` needed explicit `@unchecked Sendable` since `NSObject`-derived types aren't automatically `Sendable`-safe for a `static let shared` under Swift 6 strict concurrency). `xcodebuild test -only-testing:KeepoTests` — 9/9 (unchanged; no Outbox/offline-store changes this phase).
- **No manual simulator walkthrough** — this phase's own verify step explicitly calls for interactive Face ID enrollment (Features → Face ID → Enrolled) and both Matching/Non-matching step-up branches, which weren't exercised this session. Deferred to a joint session with the user, the same precedent Phase 11 established for anything genuinely requiring interactive device behavior rather than something `xcodebuild test` can drive headlessly.
