# Phase 14 — Recurring transactions

## Delivered

- Migration `20260808120000_recurring.sql`: `recurring_frequency` enum (`weekly`/`monthly`/`yearly`). `recurring_rules` — household-aware from day one via `can_read_account`/`can_write_account`, not a raw `owner_id` check on the table itself (this project already paid twice for that mistake — accounts in Phase 1, then `update_account`/`archive_account`/`delete_account` again in Phase 7 — recurring rules skip the retrofit entirely by using the household-aware functions from the start). `owner_id` derived from `account_id` by a `before insert or update` trigger, never trusted from the client, same shape as `transactions.account_kind`/`category_kind`. `validate_recurring_rule_sign` trigger catches a wrong-signed rule (positive amount against an expense category, or vice versa) at creation/edit time — the alternative, letting it fail the transactions table's own `sign_matches_category_kind` CHECK inside `materialize_recurring`'s insert, would surface as a mysterious constraint violation deep inside a 2am cron run instead of an immediate, clear error to the person creating the rule.
- `transactions.recurring_rule_id` — nullable, composite FK to `recurring_rules(id, owner_id)`, same pattern as `category_id`/`account_id`. `transactions_with_details` extended (append-only column ordering, per the existing convention) to expose it to the client.
- `materialize_recurring(p_through date)` — the only writer of recurring-sourced transactions. Idempotent by construction: `on conflict (owner_id, source, external_id) where external_id is not null do nothing` against the exact partial unique index Phase 4 already built for `external_id`-bearing rows (`external_id = rule_id::text || '|' || occurrence_date::text`), no new index. Walks every active, due rule in one pass (`security definer`, called by `pg_cron` as `postgres` — RLS is irrelevant to a cross-owner scheduled job, same reasoning as `sync-fx-rates`/`ops_health`). `next_occurrence_date(date, frequency)` relies on Postgres's own `date + interval` arithmetic for month-end/leap-day overflow — confirmed empirically (`Jan 31 + 1 month = Feb 29` in a leap year, `Feb 28` otherwise; re-adding a month from that clamped date lands on `Mar 31`, not a permanently-shifted day) before relying on it, rather than assuming and finding out later. `next_occurrences(rule_id, n)` is pure read-time projection — confirmed via pgTAP that calling it inserts zero rows.
- A `materialize-recurring-daily` cron job (`0 2 * * *`). `recurring_materialization_check()` — Phase 13's deliberate always-healthy stub replaced with a real implementation via `create or replace function` in this new migration (fixed forward, per this project's established precedent for anything already pushed to hosted — never editing the Phase 13 file directly).
- **Client:** `RecurringRuleRepository` (KeepoCore) — plain RLS-scoped table reads/writes, deliberately not a versioned-conflict RPC layer like `TransactionRepository`: a recurring rule is edited far less often, by nobody but its own owner/household in practice, so the concurrent-edit hazard the transaction RPCs exist to close doesn't apply with the same force here. `RecurringRulesView` (list, reached from Settings — not a top-level tab, matching the existing Household/Sync Ritual precedent) + `RecurringRuleFormView` (create/edit; "delete" pauses via `active = false`, never removes a row real historical transactions still point at via `recurring_rule_id`). `TransactionsListView` intercepts a tap on any row carrying a `recurring_rule_id`: a `confirmationDialog` offers "Edit this transaction" (the ordinary edit sheet — unaffected by any future rule change) vs "Edit all future occurrences" (fetches and opens the rule itself in `RecurringRuleFormView`).

## Findings

1. **RLS filters an `UPDATE`'s own visible rows rather than raising** — confirmed while writing the RLS test for fixture B editing fixture A's rule: the `UPDATE` statement itself succeeds, matching zero rows, with no exception at all. The pgTAP suite's first draft used `throws_like` expecting an error here, which failed (`no exception thrown`) — fixed by asserting the correct behavior instead (the row is verifiably untouched when read back as `postgres`), not by forcing an exception to occur. Worth remembering for any future RLS-scoped `UPDATE` test: RLS visibility failures are silent no-ops, not errors, and a test expecting `throws_like` against one is testing for the wrong failure mode.
2. **Calling a `service_role`-only function while still `set local role authenticated`** (left over from the fixture setup that needed `authenticated` for its own RLS-checked inserts) fails with "permission denied," not a test assertion failure — caught immediately on the first `supabase test db` run, fixed by adding an explicit `reset role` before the first `materialize_recurring()` call and keeping the file at `postgres` (which bypasses RLS/grants entirely) until the final RLS section re-establishes fixture identities on purpose.
3. **`psql`'s `SET LOCAL ROLE`/`set_config(..., true)` only last for the current transaction** — confirmed while manually verifying the migration end-to-end via `docker exec psql` (not inside the pgTAP harness, which already wraps everything in one transaction per file): running `set local role authenticated;` as a bare statement outside an explicit `BEGIN...COMMIT` reverted before the very next statement, silently executing the subsequent insert as `postgres` instead. Not a pgTAP-suite bug (the harness's own `BEGIN` already covers this) — a reminder specific to ad hoc manual verification against the raw local stack.
