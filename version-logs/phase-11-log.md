# Phase 11 — Local data protection & offline outbox

## Delivered

- **Rejected, as planned: a full local-first mirror.** Built instead: a write-outbox + read-through payload cache, exactly per the plan's own scoping. Zero balance/FX arithmetic happens on-device anywhere in this phase — every cached value is a server-computed row re-displayed, never recomputed (money rule 3).
- **`OfflineStore.swift`** — `OfflineSchemaV1: VersionedSchema` + `OfflineMigrationPlan: SchemaMigrationPlan` (one stage today, a real migration path from day one) holding two `@Model` types: `CachedPayload` (one row per query key, holding the last successful fetch's raw JSON + `fetchedAt`) and `OutboxItem` (`id, kind, payloadJSON, expectedVersion, createdAt, attempts, lastError`, matching the plan's literal shape). `OfflineStore.makeContainer()` places the store in the app container's own Application Support directory — no App Group, deliberately: `CaptureIntent` (Phase 12) is declared in the app target, not an extension, and an App Group isn't provisionable under the free personal team this project builds against until Phase 20. `NSFileProtectionCompleteUnlessOpen` is applied to the store file and its `-wal`/`-shm` siblings after container creation — `.completeUnlessOpen`, not `.complete`, so a queued write isn't refused mid-write the instant the device locks.
- **`PayloadCache.swift`** — the read-through half. `save(key:data:)`/`load(key:) -> (data, fetchedAt)?`, upserting a `CachedPayload` row per key. No decoding/encoding logic of its own — callers own their own `Codable` shape, this just persists bytes.
- **`DataStore<Item>`** (Phase 6) gained exactly the two members the plan calls for: `restore(from:)` (replays a cached page immediately, stamped with `asOf`) and an updated `load(_:cache:)` that saves on success and — this is the money-rule-5-shaped choice — **leaves `items`/`asOf` untouched on failure** rather than clearing them, so a network blip never blanks a screen that already had something to show. `Item` gained a `Codable` constraint (every existing generated type already conformed, so no call site needed one). Wired into `AccountsListView` (`accounts_with_balances`), `TransactionsListView` (`transactions_page_0` — filtered views intentionally have no cache), `CategoriesView` (`categories` — added mid-phase once the live walkthrough showed it was needed, see below), and `HomeView` (a small dedicated `HomeSummaryCache` struct, cached per scope).
- **`Outbox.swift` + `OutboxPayloads.swift`** — the write path. `TransactionOutboxSending` is the testable seam: a protocol with one method per transaction write, `Bool` returns meaning applied/conflict, thrown errors meaning real failure. `LiveTransactionOutboxSender` wraps `TransactionRepository` for the real thing. Every `submit*` call attempts the network send *immediately* and only falls back to persisting an `OutboxItem` on a thrown error. `conflict = true` is treated as **delivered**, not failed. Repeated offline edits to the **same row** collapse into one `OutboxItem` (keyed by the row's own id/`transferGroupId`).
- **H-adjacent finding, fixed before it could bite:** `create_transfer` generated both legs' ids server-side (`gen_random_uuid()`), unlike every other write in this codebase, which already takes a client-generated id. Closed in migration `20260807140000_idempotent_transfer_ids.sql`: `p_from_id`/`p_to_id` (optional, `default null`), so a retry of an already-applied transfer hits `transactions`' primary key (`23505`) instead of duplicating it. `LiveTransactionOutboxSender` catches that specific error code and treats it as success. `TransactionRepository.create` got the same treatment (`id` now an explicit parameter, defaulting to a fresh `UUID()`).
- **`SessionStore`** owns the `ModelContainer`/`Outbox`/`PayloadCache` trio. Drains happen after a successful `signIn()` and on every `scenePhase` transition to `.active`.
- **`RootView`** gained a factual "N changes waiting to sync" banner (`Outbox.hasStalePending(threshold:)`, 5 minutes). `TransactionFormView`/`TransactionsListView` route every write through `session.outbox.submit*`.
- **Added during the live walkthrough, not originally scoped — user-requested (see Findings below):**
  - `UserFacingError.describe(_:)` (KeepoCore) — every screen's error text now goes through this instead of `String(describing: error)`. Offline-specific `NSURLError` codes get a short, honest message; everything else falls back to `localizedDescription`.
  - `Outbox.pendingCreateTransactions` — a tracked, `@Observable` array of decoded pending *creates* (updates/deletes deliberately excluded — see Findings). `TransactionsListView` renders these as a "Pending sync" section with a `cloud.slash`/"Not synced" badge, resolved against whatever accounts/categories are already loaded.
  - Cache fallback for `TransactionFormView`'s own account/category pickers (`cachedAccounts()`/`cachedCategories()`, reading the same `accounts_with_balances`/`categories` cache keys `AccountsListView`/`CategoriesView` populate) — without this, a fully offline device could queue a write but had no way to populate the form that creates one.

## Findings from the live walkthrough (human review stop #3)

Everything below was found by actually exercising the app against a stopped local Supabase stack (`docker stop supabase_kong_keepo-app`), not by static review. Each was addressed in-session except the last, which the user explicitly asked to defer.

1. **The offline-picker gap** (fixed). The very first offline-create attempt showed empty Account/Category pickers with no way to select anything — `TransactionFormView.load()` had no cache fallback of its own. Fixed by adding `cachedAccounts()`/`cachedCategories()` reading the same on-device cache `AccountsListView`/`CategoriesView` already populate. `CategoriesView` itself hadn't been wired to the cache at all before this — added (`cacheKey: "categories"`).
2. **A cold app *launch* fully offline can't get past sign-in.** `SessionStore.start()` → `signIn()`/`refreshProfile()` has no cached-profile fallback; a fresh launch with zero connectivity shows a hard "Couldn't connect" screen, even for a previously-authenticated session. Session/profile bootstrap was never one of the plan's three named caching targets (accounts/transactions/Home summary) — this is a real, **accepted** scope boundary, not a bug: resuming an *already-running* session offline works fine (proven repeatedly during the walkthrough); only a cold, fully-offline launch is blocked. Worth a line in Phase 17 (session/security) if it comes up again.
3. **Idempotency, proven end-to-end, not just unit-tested.** Three offline creates were queued (one attempted before the fix above with empty pickers — that one never actually reached Save, since `isSaveDisabled` correctly blocked it), then a real one after. `sqlite3` on the raw `Offline.store` showed exactly one `OutboxItem` row per attempt, each with the JSON payload including the client-generated id. After bringing the network back and foregrounding, `psql` against the real `transactions` table showed **exactly one server row per client-generated id** — zero duplicates. Offline edit and offline delete were verified the same way (`sqlite3` showing the queued `updateTransaction`/`deleteTransaction` row mid-flight, then the server-side result after drain: the edited amount landed correctly with no duplicate row; the deleted transaction's row disappeared from the list after the drain).
4. **Raw `NSError` dumps on screen** (fixed, user-flagged as unacceptable mid-walkthrough). Every screen's error text used `String(describing: error)`, which for an `NSError` prints the *entire* `debugDescription` including nested `userInfo` — a plain "could not connect" surfaced as a dozen lines of `_NSURLErrorFailingURLSessionTaskErrorKey`/`_kCFStreamErrorCodeKey` nested-error text, visible mid-screen. Fixed everywhere (14 call sites) via `KeepoCore.UserFacingError.describe(_:)`: a short, honest "You appear to be offline..." for network-unreachable errors, `localizedDescription` (already short for `PostgrestError`) otherwise. Verified live: the same offline scenario that produced the multi-paragraph dump now shows one clean sentence.
5. **Pending creates were invisible, which the user correctly called a real gap.** Discussed in chat rather than silently fixed — the user chose "pending creates only" over full parity (updates/deletes also overlaid) or doing nothing. Implemented: `Outbox.pendingCreateTransactions`, a `TransactionsListView` "Pending sync" section. Deliberately **not** built: overlaying pending *updates* (would need to show "amount changing to X" on an existing row) or pending *deletes* (would need to show "pending removal" on a row that's about to disappear) — both need to reconcile a queued payload against an already-rendered cached row, which is real additional complexity the user agreed to scope out of this pass. **A pending delete today looks identical to no pending action at all** — the row just stays, with no "not synced" indicator — confirmed live (user: "it stayed and prompted an error... I did try delete it"). Explicitly deferred, not fixed.
6. **`sync_conflicts` cannot support a real conflict-resolution UI as built — required follow-up, not deferred-as-optional.** Resolving a Needs Review conflict (swipe-to-resolve) worked exactly as designed — the row disappeared, `resolve_sync_conflict` correctly marked it resolved. But the user immediately asked the right question: *"how can I know what I just reviewed?"* `sync_conflicts` only ever stored two version *integers*; the actual rejected field values were never persisted anywhere, by any phase, ever. There is no way to build a real diff view without a schema change. The user's explicit direction: this must be fixed with real payload storage (not a lighter "just add a details screen" compromise), but the fix itself is out of scope for *this* phase — logged as required follow-up work in `keepo-v1-master-plan.md` (Phase 10's section) for whichever phase next touches Needs Review or the conflict-as-data RPCs.

## Verification

- `supabase test db --local` — 130/130 assertions (125 prior + 5 new in `11_idempotent_transfer.sql`). `supabase db push` applied cleanly to hosted.
- `xcodebuild -scheme Keepo build` — clean. `swiftlint lint --strict` — 0 violations across 43 files. `swift test` (KeepoCore) — 25/25.
- `xcodebuild test -only-testing:KeepoTests` — 7/7: the smoke test, 5 `OutboxTests` (conflict/failure/collapse against a stubbed sender), and `OfflineStoreTests` (below).
- **File protection, corrected finding.** The original plan assumed the attribute would at least read back on Simulator even without real enforcement. Empirically false: `FileManager.setAttributes([.protectionKey: .completeUnlessOpen])` on the Simulator returns success but a subsequent `attributesOfItem` read on the same path comes back `nil`, every time — confirmed both via a real device-vs-host comparison (a plain `swift` script on the host Mac round-trips the same call correctly) and via `OfflineStoreTests.swift`, which now asserts only that the call completes without throwing. The Simulator has no data-protection subsystem at all, not even as unenforced metadata — both the read-back and the real enforcement need a physical device (Phase 20).
- **Manual simulator walkthrough — completed** (not deferred, contrary to this log's earlier draft): airplane-mode-equivalent offline (stopped the local Supabase API container directly, since the app talks to `127.0.0.1` — real Airplane Mode wouldn't touch loopback traffic anyway) create/edit/delete, foreground-drain, a forced version mismatch landing in Needs Review (confirmed via direct SQL bump of a transaction's `version`, then Save in-app → conflict alert → `sync_conflicts` row → visible in Needs Review with the correct "your version 1 vs. the saved version 2" subtitle), and the file-protection question above. Six real findings surfaced (listed above); five fixed in-session, one logged as required follow-up per explicit user direction.

## Notes for the next phase

- **Scoping decision, reconfirmed after the walkthrough:** offline writes route through the outbox for **transactions only** (create/update/delete, ledger and transfer) — not accounts, categories, households, or reconciliations, and not session/profile bootstrap (see Finding 2). `CaptureIntent` (Phase 12) is a straightforward seventh `Outbox` operation once merchant capture exists — the seam already generalizes.
- **Required, not optional, for whichever phase next touches Needs Review or any conflict-as-data RPC:** add `sync_conflicts.attempted_payload jsonb` (or equivalent), populate it from every versioned write RPC that can conflict (`update_transaction`, `update_transfer`, `update_account`, `archive_account`, ...), and give Needs Review an actual diff view before resolve. See `keepo-v1-master-plan.md`'s Phase 10 section for the full writeup.
- **Pending deletes/updates remain invisible** — a deliberate, user-confirmed scoping choice for this phase, but flagged for whichever phase revisits Needs Review/offline UX: a pending delete currently looks identical to "nothing pending," with the only signal being the app-wide stale-pending banner once 5 minutes pass.
