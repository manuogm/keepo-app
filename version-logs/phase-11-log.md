# Phase 11 — Local data protection & offline outbox

## Delivered

- **Rejected, as planned: a full local-first mirror.** Built instead: a write-outbox + read-through payload cache, exactly per the plan's own scoping. Zero balance/FX arithmetic happens on-device anywhere in this phase — every cached value is a server-computed row re-displayed, never recomputed (money rule 3).
- **`OfflineStore.swift`** — `OfflineSchemaV1: VersionedSchema` + `OfflineMigrationPlan: SchemaMigrationPlan` (one stage today, a real migration path from day one) holding two `@Model` types: `CachedPayload` (one row per query key, holding the last successful fetch's raw JSON + `fetchedAt`) and `OutboxItem` (`id, kind, payloadJSON, expectedVersion, createdAt, attempts, lastError`, matching the plan's literal shape). `OfflineStore.makeContainer()` places the store in the app container's own Application Support directory — no App Group, deliberately: `CaptureIntent` (Phase 12) is declared in the app target, not an extension, and an App Group isn't provisionable under the free personal team this project builds against until Phase 20. `NSFileProtectionCompleteUnlessOpen` is applied to the store file and its `-wal`/`-shm` siblings after container creation — `.completeUnlessOpen`, not `.complete`, so a queued write isn't refused mid-write the instant the device locks. Real enforcement (ciphertext unreadable while locked) is device-only, per the plan's own Verify note — a simulator has no data-protection keybag, so this phase can only confirm the attribute reads back, not observe actual encryption; that's Phase 20's device checklist.
- **`PayloadCache.swift`** — the read-through half. `save(key:data:)`/`load(key:) -> (data, fetchedAt)?`, upserting a `CachedPayload` row per key. No decoding/encoding logic of its own — callers own their own `Codable` shape, this just persists bytes.
- **`DataStore<Item>`** (Phase 6) gained exactly the two members the plan calls for: `restore(from:)` (replays a cached page immediately, stamped with `asOf`) and an updated `load(_:cache:)` that saves on success and — this is the money-rule-5-shaped choice — **leaves `items`/`asOf` untouched on failure** rather than clearing them, so a network blip never blanks a screen that already had something to show. `Item` gained a `Codable` constraint (every existing generated type already conformed, so no call site needed one). Wired into the three examples the plan names explicitly: `AccountsListView` (`accounts_with_balances`), `TransactionsListView` (`transactions_page_0` — filtered views intentionally have no cache, since caching every filter permutation would be pointless), and `HomeView` (a small dedicated `HomeSummaryCache` struct, since the Home summary isn't an array of one `Item` type the way the other two are — cached per scope, `home_summary_total`/`_me`/`_household`, so switching the picker doesn't show one scope's stale numbers under another's label).
- **`Outbox.swift` + `OutboxPayloads.swift`** — the write path. `TransactionOutboxSending` is the testable seam (per the plan's explicit Verify line): a protocol with one method per transaction write, `Bool` returns meaning applied/conflict, thrown errors meaning real failure. `LiveTransactionOutboxSender` wraps `TransactionRepository` for the real thing. `Outbox` itself: every `submit*` call attempts the network send *immediately* and only falls back to persisting an `OutboxItem` on a thrown error — an online save behaves exactly as it did before this phase; an offline one queues instead of erroring. `conflict = true` is treated as **delivered**, not failed — the DB already wrote the `sync_conflicts` row in the same call, so nothing about that needs a new mechanism, exactly as the plan predicted ("this is why Needs Review precedes the outbox"). Repeated offline edits to the **same row** collapse into one `OutboxItem` (keyed by the row's own id/`transferGroupId`) rather than piling up — "whole-row payloads, never per-field merge" means only the latest desired state is worth sending at all.
- **H-adjacent finding, fixed before it could bite:** `create_transfer` generated both legs' ids server-side (`gen_random_uuid()`), unlike every other write in this codebase, which already takes a client-generated id — the one place a retry-safe outbox's "idempotent for free" claim would have been false. Closed in migration `20260807140000_idempotent_transfer_ids.sql`: `p_from_id`/`p_to_id` (optional, `default null` → the old behavior), so the outbox generates both ids once, before the first send attempt, and a retry of an already-applied transfer hits `transactions`' primary key (`23505`) instead of duplicating the transfer. `LiveTransactionOutboxSender` catches that specific error code and treats it as success. `TransactionRepository.create` (single transactions) got the same treatment — `id` is now an explicit parameter (defaulting to a fresh `UUID()`, so no online caller changes) rather than generated inside the function where the outbox couldn't reuse it across retries.
- **`SessionStore`** now owns the `ModelContainer`/`Outbox`/`PayloadCache` trio, built once at session start alongside the Supabase client. Drains happen after a successful `signIn()` ("only syncs once a valid session exists" is structural — the call is literally the next line after `signIn()` succeeds, not a separate guard) and on every `scenePhase` transition to `.active` (`RootView`), so a write made offline syncs the moment the app is foregrounded again, not just at the next cold start.
- **`RootView`** gained a factual "N changes waiting to sync" banner (`Outbox.hasStalePending(threshold:)`, 5 minutes) — long enough that a momentary blip never flashes it, short enough to be a real signal. `TransactionFormView`/`TransactionsListView` route every write (create/update/delete, both ledger transactions and transfers) through `session.outbox.submit*` instead of calling `TransactionRepository` directly; a `.queued` result is treated the same as success from the form's perspective (dismiss, `onSaved()`) — the banner, not a per-save error, is what surfaces "this hasn't reached the server yet."

## Notes for the next phase

- **Scoping decision, worth restating for Phase 12:** offline writes route through the outbox for **transactions only** (create/update/delete, ledger and transfer) — not accounts, categories, households, or reconciliations. The plan's Verify section names "create/edit/delete" without specifying which entity, and transactions are both the highest-volume write and the one `CaptureIntent` (Phase 12) will depend on; extending the same pattern to account/category writes is straightforward (the `Outbox`/`TransactionOutboxSending` shape generalizes) but wasn't built speculatively ahead of an actual need.
- **Pending items are invisible in every list until drained** — no optimistic merge of a queued write into `TransactionsListView`/`AccountsListView`. This was a deliberate scoping call: merging a raw queued payload into a page of server-computed, already-joined rows (category name, running balance, base-currency conversion, ...) would mean either re-deriving some of that display data client-side (a money-rule-3 violation in spirit even if not in the strict arithmetic sense) or showing a visibly degraded row, and the plan's own "unsynced flags" language reads as a general-awareness signal, not a mandate for a merged optimistic UI. The global stale-pending banner is the one place this phase surfaces "something hasn't synced yet."
- **A known, accepted gap**: creating a transaction/transfer while offline, then editing or deleting it again before it ever syncs, is unreachable through the current UI (nothing renders a not-yet-synced row to tap), so the outbox's id-based collapsing was only built and tested for edit-after-edit and delete-after-a-prior-sync, not create-then-edit-while-still-queued. If a future phase adds any optimistic rendering of pending items, this combination needs its own test before shipping — right now it's structurally impossible to trigger, not handled.
- `CaptureIntent` (Phase 12) should be a straightforward seventh `Outbox` operation once merchant capture exists — the seam (`TransactionOutboxSending`, `OutboxKind`, the collapsing-by-id `enqueue`) already generalizes; it doesn't need its own design.
