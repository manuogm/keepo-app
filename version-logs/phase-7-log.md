# Phase 7 — Households: access model & viewer-scoped money

## Delivered

- Migration `20260806090000_households.sql`: `account_scope` enum (`me`/`household`/`total`); `household_invite_status` enum (pulled forward from its originally-planned Phase 19 slot — `household_invites` needs a typed column now, per money rule 4); `households`, `household_members` (2-member cap trigger, `my_household_id()` predicate so the cap trigger's own policy can't recurse), `household_accounts`, `household_invites` (table only, no RPCs yet — same precedent as `sync_conflicts` landing in Phase 3 before anything read it).
- **H1/H9 closed**: `account_balances_base` and `transactions_with_details` both had their `profiles` join rewritten from the row's `owner_id` to the *viewer's* `(select auth.uid())`, `left join` so a pre-onboarding null `base_currency` still can't drop a row. Regression-tested directly: a shared account owned by the other household member still appears in both views (it previously would have silently vanished — not a wrong number, a missing row, no error).
- **H2 closed**: `can_read_account` gained the household-membership `OR EXISTS` clause; `can_write_account` needed no change (already delegates). The six hardcoded `owner_id <> auth.uid()` checks across `update_transaction`/`update_transfer`/`delete_transaction`/`delete_transfer` re-pointed at `can_write_account`. `create_transfer` needed **zero changes** — contrary to the original H2 write-up, it never hardcoded an ownership check; it already relies entirely on `accounts_select`'s own RLS visibility (to read `owner_id`/`currency`) and `transactions_insert`'s `WITH CHECK` (to gate the write), both of which upgrade automatically once the predicates do. Confirmed by inspection and by the pgTAP suite's own cross-owner-transfer assertion. Phase 6's three account-lifecycle RPCs (`update_account`/`archive_account`/`delete_account`) weren't on the original H2 list — they didn't exist when H2 was catalogued — but hardcoded the identical pattern and got the identical fix.
- **H3 closed**: `accounts_select`/`accounts_update` edited directly (the documented Phase 2 exception — a `SECURITY DEFINER` self-reference breaks `INSERT ... RETURNING` for a row written earlier in the same command), inlining the household-membership check rather than calling the shared predicate, exactly as migration 002's comment predicted this phase would need to.
- **H10 closed**: `check_transfer_integrity()`'s "exactly one owner" rule relaxed to "one owner, or both legs' accounts share a household" — a transfer from a private account into a partner-owned shared account is structurally possible now. `transactions.owner_id` still always mirrors its account's owner (the composite FK forces it, unchanged); `created_by` records who actually entered it.
- **H5 closed**: `net_worth(p_scope account_scope)` — `total` is always `me + household`, summed from `account_balances_base` under two disjoint `WHERE` clauses, never subtraction. Each branch renders `NULL` (→ `—`) the instant any in-scope row has a missing rate, never a silently-partial `SUM`; an empty scope is a legitimate, distinguishable `0`.
- `create_household()`, `share_account()`, `unshare_account()` — all `SECURITY DEFINER`, owner-only for share/unshare. `unshare_account` is confirmed **not** a fork: it deletes one `household_accounts` row; ownership never moved, so there's nothing to copy. Fork stays Phase 19's problem.
- `accounts_with_balances` gained `is_shared` (append-only column, per Phase 3's `CREATE OR REPLACE VIEW` ordering rule) — the client's shared/private indicator reads this instead of a second round trip per screen.
- `supabase/tests/07_households.sql` — 26 new pgTAP assertions with two fixture users, different base currencies (EUR/USD) so a viewer-scoped-conversion regression can't hide behind both fixtures sharing one currency. The running app is single-member-household until Phase 19's `accept_invite` exists; "B joins A's household" is simulated by inserting the second `household_members` row as `postgres` — the exact precedent this suite exists to establish. Notably had to force `check_transfer_integrity`'s `DEFERRABLE INITIALLY DEFERRED` trigger to actually fire mid-test (`set constraints all immediate`) — without that, the H10 cross-owner-transfer assertion would have passed vacuously regardless of whether the relaxed SQL was even correct, since the whole test file is one never-committed transaction.
- **Hosted**: migration pushed (`supabase db push`), types regenerated (`--swift-access-control public`) and copied into `Generated/SupabaseSchema.swift`.
- **Client**: `KeepoCore/HouseholdRepository.swift` (create/share/unshare/fetchMine/fetchMembers/fetchSharedAccountIds/netWorth) plus `AccountRepository.fetchAllOwnedByMe` (a plain `accounts` table query filtered by `owner_id` — avoided a second migration just to expose ownership on the enriched view). New `App/SettingsView.swift` (4th tab): Household section — create household, member list (labelled "You" / "Household member"; no display-name system exists yet to say more), and a per-account share/unshare `Toggle` list restricted to accounts the caller actually owns. Shared/private indicator (a small `person.2.fill` icon) added to `AccountRowView`. `TransactionFormView` now shows "Added by your household member" in edit mode when `created_by` differs from the viewer. `StubAuthProvider` gained a Debug-only second identity (`KEEPO_DEV_USER=b` env var → `dev-b@keepo.local`) — it previously hardcoded one fixed email, so the app itself could never have a second user; unblocks manual household/conflict testing for later phases without touching pgTAP's own (separate) fixture identities.
- `app-architecture.md` §3's "Household access model" section updated in place — it previously described the *planned* predicate upgrade in future tense ("When households ship, `can_read_account`'s body gains..."); now quotes the actual shipped body and points at this migration/log for the two hazards it exists to close.

## Notes for the next phase

- Two-member household behavior (shared rows appearing for the *other* member, cross-owner transfers, viewer-scoped currency) is verified exclusively by pgTAP right now. Phase 19's `accept_invite` is what first makes a real second member reachable from the running app; until then, manual two-user testing needs either direct SQL against `household_members` (as this phase's pgTAP suite does) or the new `KEEPO_DEV_USER=b` switcher plus two simulator instances signed in separately.
- `HouseholdRepository.netWorth` and `AccountRepository.fetchAllOwnedByMe` exist and are exercised only indirectly (netWorth isn't called from any screen yet — that's Phase 8's Home dashboard). Both are thin wrappers with no logic of their own; nothing to regress.
- The member list in Settings has no display name to show ("You" / "Household member") — `profiles` carries no name/email column, and none was added this phase since no screen has needed one yet. Worth deciding whether a display name belongs on `profiles` or is derived from `auth.users.email` before Phase 19's invite flow needs to show "invited by ___".
- `accounts_with_balances.is_shared` and the household-membership `EXISTS` subqueries added to `can_read_account`/`accounts_select`/`accounts_update`/`net_worth` are all uncached per-row subqueries — fine at this data volume (a handful of accounts per user), worth a second look only if a future phase's query planner output suggests otherwise. No index was added on `household_accounts.household_id` beyond its role in the composite PK — add one if `household_accounts_account_id_idx` (already present) turns out not to be enough once query patterns are known.
