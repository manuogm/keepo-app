# Phase 19 — Household lifecycle: invites, leave, fork, erasure

## Delivered

- `create_invite()` / `accept_invite(p_token)`. The token is `encode(gen_random_bytes(16), 'hex')`, returned to the caller exactly once; only `encode(digest(token, 'sha256'), 'hex')` persists. 7-day expiry, single-use (`household_invites.status` flips to `accepted`), and the existing Phase 7 `enforce_household_member_cap` trigger — not re-implemented — is what actually blocks a third member.
- `merge_household_categories(p_member_a, p_member_b)` — exact case-insensitive name+kind match only. Called from `accept_invite` with both member ids passed explicitly rather than derived from `household_members.joined_at` ordering (see Finding 1).
- `fork_category_id(p_new_owner, p_original_category_id)` — same-name/kind match first, falls back to the new owner's `is_default` category; never returns null for a real category.
- `fork_household_accounts(p_household_id, p_member_a, p_member_b)` — the core split, shared by `leave_household()` and `erase_own_account()`. Runs the forkable-table registry check first (raises if any `public` base table with an `account_id` column isn't in `fork_handled_tables`), then for every account in `household_accounts` for that household: clones it into two fresh private accounts (one per member), duplicates transactions/balance_snapshots/reconciliations/recurring_rules onto *both* copies, repoints card_mappings/csv_import_batches/csv_import_candidates onto whichever copy their own `owner_id` maps to, drops the account's `net_worth_daily` cache rows, deletes the `household_accounts` row, and archives (never deletes) the original.
- A forked transfer leg cannot keep its `transfer_group_id` — the sibling leg's account usually isn't part of the same fork, and `check_transfer_integrity`'s deferred constraint requires exactly 0 or 2 legs per group. Every forked transfer leg becomes a `source = 'adjustment'` entry (category = the new owner's own `adjustment_expense`/`adjustment_income` system category) carrying the same signed amount — the new copy's balance is correct from the moment it's created; only "this used to be a transfer" provenance is lost. Documented at length in the migration's own header comment.
- `leave_household()` — forks (if there's another member; a no-op fork for a single-member household), then deletes only the caller's own `household_members` row. `erase_own_account()` — same fork, then scrubs the caller's own resulting copy's free-text fields (`merchant_raw`/`merchant_normalized`, `card_identifier`, import `filename`/`raw_row`) without ever touching the other member's copy.
- `fork_handled_tables` (table_name, handling) — `duplicate_to_both` (transactions, balance_snapshots, reconciliations, recurring_rules), `repoint_by_owner` (card_mappings, csv_import_batches, csv_import_candidates), `cache_recompute` (net_worth_daily), `deleted_on_leave` (household_accounts). `fork_household_accounts` genuinely queries `information_schema` and raises if a table falls outside this list — proven by a pgTAP test that adds an unregistered table inside a savepoint, confirms `leave_household()` refuses to run, then rolls back.
- `household_events` (append-only, `member_joined`/`member_left`/`member_erased`, `SECURITY DEFINER`-only writes) + `notify_household()` calling the new `notify-household` Edge Function through the existing `ops_http_post` helper (Phase 13) — a real no-op transport, gated by vault secrets that don't exist in any environment yet, degrading to an `ops_events` log entry exactly like a missing FX-sync secret.
- KeepoCore: `HouseholdRepository` gained `createInvite`/`acceptInvite`/`leave`/`eraseOwnAccount`/`fetchEvents`. App: `HouseholdView` (moved the Household section out of `SettingsView`, which had grown too many concerns to hold it inline) with invite generate/share, join-by-code, and leave/erase behind a `confirmationDialog` + `session.stepUp(reason:)` immediately before the RPC. `HouseholdViewLoader` factored out purely to keep `HouseholdView` under the type-body-length lint threshold.

## Findings

1. **`now()` is frozen for an entire transaction — including across two `INSERT`s moments apart in the same pgTAP test file.** The first draft of `merge_household_categories` derived "who joined first" from `household_members.joined_at` (`order by joined_at asc/desc limit 1`). Two members joining within the same test-file transaction can get an identical `joined_at`, making the ordering pick unpredictably — including, once, both slots resolving to the same user, which silently skipped the merge (the function's own `if v_member_a = v_member_b then return` guard fired). Fixed by having `accept_invite` pass both member ids explicitly (`invited_by`, `auth.uid()`) — no ordering dependency, no hazard in production either. `supabase/tests/_helpers.psql`'s own documented `now()`-freezing gotcha (from earlier phases) predicted exactly this class of bug; this is the first time it bit a *derived-from-timestamp* decision rather than a *comparison against* one.
2. **`information_schema.columns` includes views, not just base tables.** The forkable-table registry's first draft raised on every run — `account_balances`, `transactions_with_details`, `needs_review`, `accounts_with_balances`, `account_balances_base`, and `accounts_sync_status` all surface an `account_id` column (they're `SELECT`s that alias or pass one through) despite holding no data of their own. Fixed by joining to `information_schema.tables` and filtering `table_type = 'BASE TABLE'`.
3. **A table with RLS enabled and zero policies denies everything to every non-owner role, regardless of `GRANT`s.** `fork_handled_tables` had `enable row level security` and a `grant select ... to authenticated` but no `CREATE POLICY` — the grant is necessary but not sufficient; without a policy, PostgreSQL's default is deny-all for RLS-enabled tables. The pgTAP suite's own direct `SELECT` (run as `authenticated`, unlike `fork_household_accounts`'s internal query which runs as the table-owning `postgres` role and bypasses RLS entirely) returned zero rows, which is what actually surfaced this — the SECURITY DEFINER path had been silently fine the whole time. Added `fork_handled_tables_select ... using (true)` — this table is a static reference list, not sensitive, same posture as `currencies`.
4. **plpgsql resolves a bare identifier against declared variables before table/lateral columns.** An early draft named a `LATERAL (VALUES ...) AS fork(...)` alias column the same as the function's own declared `v_new_for_owner` variable, intending to reference the lateral row in a `SELECT` list — PostgreSQL silently resolved every reference to the *variable* instead, which is `NULL` at that point in an unrelated code path, not an error. Confirmed only by reading the generated SQL plan; renamed every lateral alias to names with no chance of colliding with a declared variable (`fork_owner`, `fork_account_id`) and added a comment warning the next person editing this function.
5. **A test asserting "the other member's copy is untouched" needs to exclude the archived original explicitly.** `erase_own_account`'s pgTAP assertion for "A's own copy still has merchant_raw" initially matched 2 rows instead of 1 — the query joined on `owner_id` + account `name` without excluding `archived_at is not null`, so it matched both A's *new* forked copy and the *original* (now-archived) account, which A still legitimately owns and which was never touched. Every "does the fork exist correctly" assertion in the suite now filters `archived_at is null` where relevant.

## Notes for the next phase

- Phase 20's `AppleAuthProvider` swap-in is unaffected by anything here — `session.stepUp(reason:)` (the mechanism `HouseholdView`'s leave/erase now depend on) was already provider-agnostic since Phase 17.
- `notify_household_url`/`notify_household_secret` need real Vault values before `notify-household` does anything beyond logging — same pattern as `fx_sync_url`/`fx_sync_secret` and `alert_operator_url`/`alert_operator_secret` before it. Not urgent: the no-op transport degrading to an `ops_events` entry is itself the intended Phase 19 behavior.
- Realtime (cache-invalidation-only signal, per the original plan text) and the in-app foreground banner were both descoped this pass in favor of plain polling and an in-screen event list. Worth reconsidering once Phase 20 gives APNs a real transport to invalidate against — a push arriving is a much more natural trigger for a Realtime-style refetch than anything polling-based.
- The not-self guard in `accept_invite` is currently unreachable through the public API (an inviter is always already a household member, so the "already a member" check fires first for any self-acceptance attempt) — kept as defense-in-depth, not covered by pgTAP for that reason. If `accept_invite`'s ordering ever changes, revisit whether this becomes reachable and worth testing.
