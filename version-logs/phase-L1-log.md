# Phase L1 — Money as fixed-point Int64 (bigint e4)

Part of the local-first rebuild (`keepo-local-first-plan.md`), not the Phase 5–20 spec build. Converts every money column and every Swift money value from `numeric(20,4)`/`Decimal` to `bigint`/`Int64` at fixed scale 4 (`_e4` suffix) — Int64 arithmetic is bit-identical across Postgres, SQLite, and Swift, removing the cross-language rounding-drift risk that was the original objection to a local-first store. `fx_rates.rate_to_eur` is deliberately excluded — it's a conversion factor, not an amount, and stays `numeric(20,4)`.

## Delivered

- `supabase/migrations/20260815100000_money_as_integers.sql` — 8 columns renamed with `_e4` suffix and retyped to `bigint`; `account_balance_on`/`fx_convert` rebuilt (bigint in/out, rounds half-away-from-zero only at `fx_convert`'s final cast — the one inexact operation); 5 views recreated `with (security_invoker = true)`; ~18 functions ported (explicit `::bigint` casts wherever `sum(bigint)` — which returns `numeric` — feeds a `RETURNS TABLE`); `set_account_balance` gained `p_expected_version` with an idempotency-before-version-check body so an outbox retry with a now-stale expected version still succeeds if its client-generated id was already applied; `service_role` grants restored on 9 functions (`DROP FUNCTION` silently drops all existing grants, not just the ones being changed).
- `supabase/tests/22_money_representation.sql` (new) — rounding-contract, JPY round-trip, JPY `minor_unit = 0`, and large-balance (~€100bn) exactness assertions. 18 existing pgTAP files mechanically rewritten (column renames, ×10000 value scaling); `21_set_account_balance.sql` fully rewritten to track account version numbers through the idempotency-vs-conflict sequence.
- KeepoCore: `MoneyFormatter`/`AmountParser`/`AmountFormatter` ported to `Int64`; `AmountParser` gained `parseRate(_:locale:)` as the un-scaled counterpart to `parse(_:)`, for the ratio-typed fields (`withdrawal_rate`, `real_return_rate`) that stay `Decimal`. `PendingOverlay` ported to `Int64` — exact, no rounding needed at all where `Decimal` needed `.plain` rounding. `LocalFxConvert` mirrors the server's exact rounding contract. `CaptureIdentity.externalId` ported `amount: Decimal` → `Int64` (pure client-side hash input, no server dependency on the string format persisting across versions, so the change is safe going forward).

## Findings

1. **`sum(bigint)` returns `numeric`, not `bigint`.** Broke 4 `RETURNS TABLE(... bigint)` functions using inline `sum(...)` in `RETURN QUERY SELECT` — plpgsql requires exact structural type match there, unlike `SELECT ... INTO` a local variable, which implicit-casts. Fixed with explicit `::bigint` casts. Worth remembering for any future `RETURNS TABLE` function summing a bigint column.
2. **`DROP FUNCTION` drops every grant, not just the ones tied to the changed signature.** A function originally granted to both `authenticated` and `service_role` came back granted to `authenticated` only after a routine `DROP + CREATE OR REPLACE`, because the migration's grant statements only re-added what the diff seemed to require. Caught by a pgTAP test running as `service_role` ("permission denied for function fx_convert"), not by manual review. Now grep all original migrations for `grant execute ... to authenticated, service_role` before rewriting any function's grants.
3. **Optimistic-concurrency version checks and idempotent-retry-safety conflict unless ordered correctly.** Adding `p_expected_version` to `set_account_balance` meant a retried outbox write (same client id, stale captured `expectedVersion`) would fail once the *first* attempt had already succeeded and bumped the version. Fixed by checking idempotency (does this id already exist?) before the version check — a replay short-circuits to success before ever comparing versions. General pattern for any future versioned + idempotent RPC.
4. **A missing `security_invoker = true` on a recreated view is a real RLS-bypass bug, not a lint nit.** `DROP VIEW` + `CREATE VIEW` silently loses this option if it isn't re-specified. Caught by grepping existing migrations for the pattern before pushing, not by any automated check — no pgTAP assertion currently enforces this for views the way the Phase 5 schema-wide checks do for tables/functions. Worth a follow-up pgTAP assertion in a future phase.
5. **A systematic `pg_proc.prosrc` regex scan found 7 functions a manual read-through missed.** The first pass fixed every function with an *explicit* `numeric(20,4)` local variable; it missed functions accessing renamed columns through bare `record`/`%ROWTYPE` field access (`v_candidate.amount`, `new.amount`, `t.amount`) — no local variable to notice. `select proname from pg_proc where prosrc ~ '\mamount\M|\mopening_balance\M|...'` is the reusable check for "did this migration actually touch every function that references a renamed column."
6. **BSD/macOS `sed` silently no-ops on `\b` word boundaries.** `sed -i '' -e 's/\bfoo\b/.../''` does nothing — no error, no match. Substring-anchored patterns or a Python `re`/exact-match script are the reliable alternative on this platform.
7. **A blanket rename script can miss differently-named properties carrying the same value.** An early `sed` pass renaming `amount: Decimal)` → `amount: Int64)` didn't touch `payload.fromAmount`/`payload.toAmount`, producing a garbled downstream error ("cannot convert value of type 'Float16'") that had nothing obviously to do with the real cause. Fixed with a precise manual `Edit`, not another broad `sed` pass. Automated renames need a final targeted grep for every property name touching the same underlying value, not just the literal string replaced.
