# Post-launch UX overhaul — transfer icon, offline banner, Dashboard, Insights/FI removal, Accounts, Transactions

Not phase-numbered — a user-requested batch of six UX changes on top of the already-shipped v1 feature set, executed as one combined migration + one combined implementation pass per the user's explicit restructuring of the original per-item plan.

## Delivered

1. **Transfer icon fix** — `CategoryIconView` gained an `init(icon:color:)` overload that renders a single explicit glyph, bypassing the `category == nil → "questionmark"` placeholder fallback. `TransactionRow` now calls it directly for transfers (`"arrow.left.arrow.right"`) instead of overlaying that glyph on top of the placeholder — the two-icons-stacked bug is gone.
2. **Offline banner** — `OfflineStatusBar` is now a tappable, dark-red-text, `.regularMaterial` tile (was a bare `HStack`, `.allowsHitTesting(false)`); tapping opens new `OfflineInfoSheet` (grouped, icon+color "works / needs connection / unavailable offline" list). `RootView` switched from `.overlay(alignment: .bottom)` + measured `tabBarHeight` to `.safeAreaInset(edge: .bottom)`, which both positions the tile above the tab bar and reserves the space in every descendant scroll view — removed the now-unneeded `TabBarHeightKey` preference-key plumbing entirely.
3. **Dashboard restructure** — tab icon `house` → `chart.line.uptrend.xyaxis`. The toolbar's Insights link became a bell button opening `NeedsReviewView` as a `.sheet` with `.presentationDetents([.medium, .large])` (system sheets already dim the presenter — no bespoke overlay needed). `NeedsReviewView` was fully-built dead code (zero call sites, confirmed via grep) from earlier work this cycle — reused as-is rather than rewritten. The inline Needs Review section and its state were stripped out of `TransactionsListView`/deleted (`TransactionsListView+NeedsReview.swift`), and the tab badge moved from Transactions to Dashboard. Net worth became a card (title + `BalanceHeaderView` + axis-free chart) pushing to new `NetWorthDetailView` (full chart with axes) — both share one `NetWorthChartView(seriesPoints:showAxes:)` rather than duplicating the `Chart` code.
4. **Insights + FI removed entirely** (user: "I do not want to ship this feature for now") — see the dedicated section below.
5. **Accounts screen overhaul** — accounts gained `icon`/`color` columns (same pattern as categories; `AccountAppearance.defaultIcon(forSubtype:)` + reused `CategoryAppearance.randomColor()`), threaded through create/update payloads, the outbox local-write echo, and a new icon-grid + `ColorPicker` in `AccountFormView`. Archived accounts collapsed out of the inline list into an "Archived (N)" link → new `ArchiveAccountsView` (My Profile → Data & Privacy → Data), which offers unarchive (no confirmation) and a destructive, non-reversible delete (`AccountRepository.delete`, online-only — the "does this account still have transactions" check is a live one, mirrored locally via new `AccountLocalWrite.delete` once the RPC succeeds, same pattern as `CategoryLocalWrite`'s category delete). Archiving now always confirms first ("Archiving an account will remove it from your total balance but will not delete the account or the transactions associated") from both trigger points — the list's swipe action and a new archive/unarchive button inside the edit sheet.
6. **Transactions screen merge** — `TransactionsListView`'s capped "Recent" list and `TransactionRegisterView`'s separate full day-grouped register (week/month/year only) became one screen: `Period` extended with `.day`/`.custom`, day-grouping kept, `TransactionRegisterView.swift` deleted. Toolbar: `.searchable(isPresented:)` driven by a new magnifying-glass button (replacing the always-visible search bar), "+" stays primary. `TransactionFilterView` dropped its own date-range section (period now owns date bounds; the sheet is account/category/kind only). `TransactionFormView`'s edit mode gained an explicit destructive "Delete Transaction" button (new `TransactionFormView+Delete.swift`), sharing the same `submitDeleteTransaction`/`submitDeleteTransfer` outbox calls the list's swipe action already used.

## Insights/FI removal — full scope

One combined migration (`20260819100000_remove_fi_add_account_appearance.sql`) did everything: dropped the four Insights RPCs (`spending_by_category`, `income_expense_series`, `savings_rate`, `unrealized_gain`) and `fi_metrics`; dropped `fi_settings`; rewired `pull_changes`/`handle_new_user`/`ensure_user_bootstrap` off it; dropped `accounts.counts_toward_fi` and added `icon`/`color` in its place, which meant also redefining `update_account` (parameter list), `accounts_with_balances` (view column), and `fork_one_account` (household-leave/fork's two INSERT column lists) — none of which the original request scope mentioned, only found via `pg_proc`/`pg_depend`/`pg_views` introspection against hosted before writing the migration.

App layer: deleted `InsightsView.swift`, `FISettingsView.swift`, `InsightsRepository.swift`, `FIRepository.swift` outright. In the local-first machinery, `LocalMoneyConversionFI.swift` was split (it mixed Budgets — kept — with FI — removed): renamed to `LocalMoneyConversionBudget.swift`, keeping only `budgetProgress`. `LocalMoneyConversion.swift` lost `spendingByCategory`/`incomeExpenseSeries`/`accumulate`/`savingsRate`/`incomeAndExpense`/`netWorthCountingTowardFI` and the `countsTowardFiOnly` flag on `scopedAccountIds`. `LocalMoneyQueries.swift` lost `categorizedNativeTransactions`/`unrealizedGain` (Insights-only; had no other callers). `LocalMoneyTypes.swift` lost `CategorySpendingLocal`/`IncomeExpensePointLocal`/`FIMetricsLocal`/`FISettingsLocal` and the now-unused `monthStart`/`weekStart`/`isoCalendar` helpers (only `incomeExpenseSeries` used them). `LocalStore.swift`'s GRDB schema (`LocalSchemaV1`, edited in place under its existing "v1" migration name — this is a rebuildable local cache, not user data needing a migration path, confirmed via `registerMigration` having exactly one call site across the whole app) dropped the `fi_settings` table and swapped `accounts.counts_toward_fi` for `icon`/`color`. `SyncApply.swift`'s table/column/primary-key whitelists lost `fi_settings` and gained `icon`/`color` on `accounts`. `AccountFormView` lost its "Counts toward FI" toggle.

`app-architecture.md` and `keepo-v1-master-plan.md` amended in place (Screens table, tables list, sync_seq table list, the `pull_changes` precision-fix note). Budgets — reachable from Settings, zero code references to Insights/FI either direction — was confirmed untouched throughout.

## Findings

1. **Postgres `CREATE OR REPLACE VIEW` can only append trailing columns, never remove one from the middle of the output list.** `accounts_with_balances` needed `counts_toward_fi` gone and `icon`/`color` added at a specific position — required an explicit `DROP VIEW` + fresh `CREATE VIEW` (with `grant select ... to authenticated` re-added afterward, since a drop clears grants) rather than a replace.
2. **`supabase db push`'s real strict-transaction behavior differs from `supabase db reset`'s in a way that only bites in one of the two.** The migration's original ordering ran the `icon`/`color` backfill `UPDATE`s before the later `ALTER TABLE accounts DROP COLUMN counts_toward_fi` — fine under `db reset` (284/284 pgTAP passed locally), but `db push` failed with Postgres error 55006 ("cannot ALTER TABLE because it has pending trigger events"): an `UPDATE` queues the table's deferred sync-seq trigger for end-of-transaction, and a same-transaction `ALTER TABLE` on that table is refused while an event is still pending. Fixed by moving every backfill `UPDATE` to run after every `ALTER TABLE` on that table within the migration. Confirmed via `supabase db query --linked -f <file>`, which surfaces the real underlying Postgres error — `db push`'s own error only echoes the failing statement text with no reason, and `db push --debug` adds nothing extra.
3. **`supabase gen types swift` can leave a stray non-Swift line (`Connecting to db 5432`) at the very top of its output** when its own connection-status log line and the actual `stdout` type payload land in the same captured stream — this broke the build with "Expressions are not allowed at the top level" at `SupabaseSchema.swift:1:1` on the very first full `xcodebuild` after the type regeneration, despite the regeneration itself having been "verified" earlier via `grep -c countsTowardFi` (which doesn't parse the file, so a leading garbage line doesn't show up in a substring count). **After any `supabase gen types` redirect, actually build the project before considering the regeneration verified — a grep on the diff is not a substitute for compiling.**
4. **A `struct`'s member marked `private` is invisible to that same type's own extension in a different file** — routine for this codebase's established "split for file-length" convention, but easy to trip when adding a *new* cross-file extension for the first time on a screen (`TransactionsListView`'s `range` computed property, `TransactionFormView`'s `editingId`/`editingFromVersion`/etc., `dismiss`) — all had to move from `private` to bare (internal) access, matching the "Not `private` — read from X.swift" comment convention every other split file in this codebase already uses.
5. **A `var` captured by value into a GRDB `dbQueue.read { }` closure trips Swift 6 strict concurrency ("reference to captured var ... in concurrently-executing code") even though the value is only read, never mutated, inside the closure.** Building the period-derived filter as a mutated local `var` and then closing over it failed; wrapping the mutation in an immediately-invoked closure that returns a `let` fixed it — the closure needs to close over something immutable, not just something that happens not to be mutated at the use site.
6. **`xcodegen generate` strips the committed `DEVELOPMENT_TEAM` signing setting on every run, confirmed again this pass** — consistent with the L3 lesson already on record; needed restoring twice in one session (once after the initial `xcodegen generate`, again after adding a same-session extension file required a second regeneration for the new file to be picked up by the folder-based `sources` glob).
7. **SwiftLint's `function_parameter_count` rule does not fire on `init` declarations, even well past the default 5-parameter threshold** (a 9-parameter `CreateAccountPayload.init` triggered no warning) — a `// swiftlint:disable:next function_parameter_count` comment added preemptively above one is flagged as `superfluous_disable_command` instead. Don't add the disable comment on an initializer at all; only regular functions need it.

## Notes for whoever picks this up next

- The Insights/FI removal is deliberate and pre-launch (the user's own words: "I do not want to ship this feature for now") — not a scope cut due to a problem found while building it. If Insights is rebuilt later "from scratch" (the user's stated intent), the deleted RPCs/repository/view are a reasonable reference for what existed, but nothing here should be un-deleted wholesale — rebuild against whatever the new design actually needs.
- `LocalMoneyConversionBudget.swift` (renamed from `LocalMoneyConversionFI.swift`) now holds only `budgetProgress` — if Budgets ever grows a second local-money function, this file is the natural home for it, consistent with the file-per-concern split the rest of `LocalMoneyConversion*` already uses.
- `AccountAppearance` intentionally does not duplicate `CategoryAppearance.randomColor()` — accounts and categories share one color palette by calling the same function, per CLAUDE.md's reuse principle. If accounts ever need a genuinely different palette, that's a deliberate divergence to introduce explicitly, not something to backfill quietly.
