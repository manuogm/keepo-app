# Phase 18 — CSV import & export

## Delivered

- `csv_import_batches`/`csv_import_candidates` + `import_candidate_status` enum. `import_csv_rows(p_account_id, p_filename, p_rows jsonb)` is the one write for an entire parsed statement — inserts the batch and every candidate in one round trip, with matching (exact amount, same account, occurred_at within ±3 days of an existing non-deleted transaction) computed inline per row. A match is informational only (`matched_transaction_id`, surfaced in Needs Review as "possible duplicate") — it never blocks or auto-rejects a row; `accept_import_candidate()` always inserts a genuinely new, confirmed transaction (`source = 'csv_import'`) regardless of match state, and `reject_import_candidate()` only ever flips `status`, matching the spec's "CSV carries no transaction ids, so nothing is ever blind-inserted."
- Both tables key their RLS off `can_write_account(account_id)`, not raw `owner_id` equality — proactively household-aware from creation, since this table is new and there's no excuse to hardcode ownership the way accounts/transactions originally did (H2/H3). `owner_id` is the *account's* owner (trigger-derived on `csv_import_batches`, copied through by `import_csv_rows` onto `csv_import_candidates`), matching `transactions`' own composite-FK-forced convention — the importer and the account owner can be different household members.
- `resolve_category_for_merchant(p_owner, p_merchant_normalized, p_kind)` — factored out of Phase 12's `capture_transaction`, which had this exact merchant-learned-category-or-fallback lookup inlined. `accept_import_candidate` is the second genuine caller (income rows use the kind's `is_default` category as fallback, since no `uncategorized_income` system category exists; expense rows keep capture's original `uncategorized_expense` fallback, confirmed byte-for-byte behaviorally unchanged by the untouched Phase 12 pgTAP suite).
- `export_audit_log` + `log_export(p_account_ids, p_row_count)` — `SECURITY DEFINER`, zero grants to `authenticated` at all (same "write only through a vetted function" precedent as `sync_conflicts`/`fx_rates`). No new read RPC for export itself — the client builds the CSV from `transactions_with_details` rows already reachable through the normal RLS-scoped path (`ExportRepository.fetchTransactions`, scoped server-side via `.in("account_id", ...)`).
- `check_transfer_rate_divergence(p_from_currency, p_to_currency, p_from_amount, p_to_amount, p_occurred_at)` — a pure read RPC comparing the transfer's own implied rate against `fx_convert`'s market rate for that day. Deliberately **not** inside `create_transfer`: that RPC's signature and every existing caller (including the Phase 11 idempotent-leg-id path) stay untouched. The client calls it once, before submitting, and only for cross-currency transfers; >10% divergence surfaces a "Cancel" / "Use Anyway" alert, never a server-side block. A missing market rate (empty result set) is treated as "nothing to warn about," not "diverges" — same null-propagation spirit as money rule 5, applied to a UX warning rather than a stored value.
- `needs_review` gained its fifth and (per the original spec list) final planned branch: `csv_import_candidate`, for still-pending rows.
- KeepoCore: `CSVImportParser` (header-driven column detection for date/amount/description with a few synonyms, positional fallback with no recognizable header, RFC-4180-subset quoting so a comma inside a quoted merchant field never splits a row; reuses `AmountParser` rather than a bespoke numeric parse). `ImportRepository` (`importRows`/`fetchCandidates`/`accept`/`reject`, reusing `MerchantNormalizer` from Phase 12 to compute `merchant_normalized` client-side exactly as capture does). `ExportRepository` (`fetchTransactions`, `csv(from:)`, `logExport`). `TransactionRepository` gained `checkTransferRateDivergence` + the `RateDivergence` decodable.
- App: `CSVImportView` (account picker, `.fileImporter` restricted to `.commaSeparatedText`/`.plainText`, parse-then-review-count, submit) and `ExportView` (per-account toggles, calls `session.stepUp(reason:)` immediately before building the CSV, then `logExport`, then presents a `UIActivityViewController` share sheet) — both reached from Settings' new "Data" section. `NeedsReviewView` gained the `csv_import_candidate` case: swipe-right "Accept", swipe-left "Reject", `doc.text.magnifyingglass` icon. `TransactionFormView`'s transfer save path gained a divergence pre-check before queuing through the outbox.

## Findings

1. **A genuine second caller is what makes an extraction correct, not premature.** `resolve_category_for_merchant` existed as inlined logic in `capture_transaction` since Phase 12 and was left alone then — CLAUDE.md's own two-call-sites-stay-duplicated rule. `accept_import_candidate` needing the identical lookup is the third call site's worth of signal in spirit (capture is the first real caller, CSV import the second genuinely distinct one), so extracting now rather than copying the inline block again is the correct side of that rule, not a violation of "no speculative abstraction."
2. **A `Binding` crosses file boundaries freely even when the underlying `@State` is `private`.** `TransactionFormView.swift` crossed the project's 400-line file-length lint threshold once the divergence-alert UI and its pre-check landed. Extracting an `extension TransactionFormView` into a second file was not an option (Swift's `private` is file-scoped, and `fileprivate` is too) — but a `ViewModifier` taking `@Binding var divergence: RateDivergence?` needs no access to the view's own private storage at all, since `$divergenceWarning` is a value, not a reference to the property's access control. `TransferDivergenceAlert.swift` (the modifier + the pure `TransferDivergenceCheck.evaluate` async function) and `TransactionFormCache.swift` (the two payload-cache fallbacks, needing only `session`, which is `let` not `private`) both used this to get `TransactionFormView.swift` from 443 to 396 lines without changing any property's access level.
3. **`PayloadCache.load` is `@MainActor`-isolated** (inherited from `SessionStore`'s own isolation) — `TransactionFormCache`'s two static functions needed an explicit `@MainActor` annotation on the enum itself once moved to a standalone file; in the original file they inherited the view's own implicit main-actor context and the compiler never flagged it.
4. **`supabase gen types swift --local ... > file` captures the CLI's own stdout noise** ("Connecting to db 5432") as literal line 1 of the generated Swift file — invisible until `swift build` fails with "expressions are not allowed at the top level" pointing at that exact line. Also: this project's actual generated-types file is `Generated/SupabaseSchema.swift` (tracked since Phase 1); redirecting to a differently-named file this session created a second, untracked file defining the same `PublicSchema` enum, which fails as "ambiguous for type lookup" the moment both are compiled. Fixed by deleting the stray file and regenerating into the correct tracked path, then stripping the stray first line.
5. **`fx_rate_on`'s `rate_to_eur` convention reads as "units of that currency per 1 EUR," not "EUR per unit."** `fx_convert(1, 'EUR', 'USD', date)` with a `USD` rate of `0.90` returns `0.90`, meaning 1 EUR buys 0.90 USD under that fixture rate — the pgTAP test's first draft assumed the opposite direction (dividing instead of multiplying) and had to be corrected once `check_transfer_rate_divergence`'s own "market rate" assertion failed with the wrong expected value. Worth restating precisely here since it's easy to get backwards a second time.
