# Phase 8 — Home dashboard & net worth trajectory

## Delivered

- Migration `20260806140000_home_net_worth.sql`: **H11 closed** — extracted `account_balance_on(p_account_id, p_date)`, the one ledger/valuation `CASE`, parameterized by date via `least(p_date + 1 day, now())` — a single expression that reduces to exactly `occurred_at <= now()` for `p_date = current_date` (preserving the future-dated guard byte-for-byte) while correctly answering "balance as of an arbitrary past day" for the trajectory. `account_balances` is now a one-line wrapper; pgTAP asserts it's byte-identical to calling the function directly, not trusted by inspection.
- `net_worth_daily` (per account, per day, in that account's own currency) + `refresh_net_worth_daily(p_user, p_from, p_to)` — built exactly as `app-architecture.md` specified, not the "function only" alternative considered during planning. RLS mirrors `can_read_account` rather than `owner_id = auth.uid()` — a design decision the doc didn't spell out but the household model requires: a member must be able to read a shared account's *history* for `household`/`total` scopes, not just its current balance. No `pg_cron` exists yet (Phase 13), so the client calls `refresh_net_worth_daily` itself before reading a trajectory; the RPC restricts callers to refreshing their own data (`auth.uid() = p_user`), except under `service_role` (`auth.uid()` is null there), which is exactly how Phase 13's cron will call it later without this check ever standing in its way.
- `net_worth_series(p_scope, p_from, p_to)` — the read side. Per-day null propagation mirrors `net_worth()`: any unconvertible account in scope renders that day `NULL` (→ `—`), never a silently-partial `SUM`; a day with zero accounts in scope simply isn't a row in the result (`GROUP BY` can't produce an empty group) rather than a fabricated `0`.
- **H15 closed**: `fx_convert` short-circuits to the input amount when `p_from = p_to`, no `fx_rates` row required at all for a same-currency "conversion."
- **Found and fixed a real fixture-identity collision** (not part of the original hazard list): `supabase/seed.sql` and the pgTAP suite's own fixtures had been using the *same* two user ids since Phase 5, despite `_helpers.psql`'s header comment already (incorrectly) claiming they were distinct. Invisible through Phase 7 because no test before Phase 8 aggregated "everything a fixture user owns" — `net_worth_series` is the first thing that does, and it started summing seed.sql's pre-loaded accounts into what were supposed to be tightly-scoped assertions. Fixed by giving `seed.sql`'s two users new ids (`99999999-.../88888888-...`), matching what the comment already said should be true; zero changes needed to any of the 7 existing pgTAP files.
- `supabase/tests/08_home_net_worth.sql` — 17 new assertions: the historical series at several points including the future-dated guard from two directions (today's balance unaffected by a future transaction; a query *about* a future date still can't see beyond `now()`); the byte-identical wrapper check; `net_worth_daily`/`refresh_net_worth_daily` materializing correctly; all three scopes summing correctly once an account is shared; the same-currency short-circuit with zero `fx_rates` rows; a day with an unconvertible account rendering `NULL`; a rate seeded 10 days back carrying forward across a full 8-day range with zero `NULL` days.
- **Hosted**: migration pushed, types regenerated and copied into `Generated/SupabaseSchema.swift`.
- **Client**: `KeepoCore/DateBucketing.swift` (weekly ≤ 90 days / monthly beyond, keeping the *last* point per bucket — a net worth trajectory is a running balance, not a flow) with 5 unit tests. `HouseholdRepository` gained `refreshNetWorthDaily`/`netWorthSeries` (`NetWorthPoint` — no generated type exists for a table-returning RPC, so this is a small hand-written `Decodable`). New `App/HomeView.swift` (first tab): Total/Me/Household segmented picker, `BalanceHeaderView` hero figure, Swift Charts trajectory over a fixed trailing 90-day window. New `App/BalanceHeaderView.swift`, a shared component per `app-architecture.md`'s table, available to Accounts/Sync Ritual later without having been retrofitted onto them now. `RootView` gained the app-switcher privacy curtain (`scenePhase != .active` overlay, covering both `.inactive` and `.background` since the OS snapshot is taken the instant the scene stops being active) and Home as the first tab.
- **Deliberate interpretation call**: `app-architecture.md` §5's "gaps filled with real zeroes, never omitted" rule is written for bar/category charts (so evenly-spaced bars don't imply evenly-spaced dates). Applied literally to the net-worth *line* chart, it would render an unknown value as `0` — a direct violation of money rule 5. The trajectory instead leaves a real gap in the line for any day with no data or an unresolvable rate, and shows an explicit "No trajectory yet for this scope" message when the whole range is empty (e.g. an un-shared `household` scope), rather than a flat, misleading `$0` line.

## Notes for the next phase

- This phase closes the plan's human review stop #2 (Phase 7 + 8 together) — households' access model is now observable as real numbers on the Home hero metric and scope picker, not just passing assertions.
- `net_worth_daily` currently only gets refreshed by the client hitting Home. A user who never opens Home has a stale/empty trajectory — harmless today (nothing else reads the table), but Phase 13's cron is what makes this actually reliable, not optional polish.
- `BalanceHeaderView` was built once and is available to Accounts/Sync Ritual per the architecture doc's shared-component table, but neither was retrofitted to use it this phase — each still renders its own totals inline. Worth revisiting once either screen actually wants a single hero figure of its own.
- The seed-vs-pgTAP fixture id collision (see Delivered) is the kind of bug that stays invisible until a phase aggregates "everything a user owns" for the first time — worth keeping in mind for any future cross-account aggregate (Insights, Budgets) that a fresh `db reset` should be run before writing its first pgTAP assertions, to catch a similar collision early rather than debugging a confusing wrong-total failure.
- The 90-day trailing window is currently hardcoded in `HomeView`. A date-range picker is out of scope for this phase and not yet needed by any other screen — introduce one only when Insights (Phase 15) or a user-facing range control actually asks for it.
